## 1. 何が問題だったか

AI コードレビューの巡回が収束しなかった。**「指摘が出なくなるまで回す」が原理的に満たせない**——
レビューは巡回ごとの記憶を持たず毎回まっさらに読み直すため、**同じ品質でも読むたびに別の指摘が出る。**

## 2. 旧規則での実測（全履歴）

**対象: 25 PR / 242 巡回 / 702 件の指摘。**

| 指標 | 値 |
|---|---|
| 重大度の内訳 | 🔴 2 件 / 🟡 661 件 / 🟣 55 件（**合計 718 は総数 702 より 16 件多い。理由は未確認**。「記号の無い指摘があった」という仮説は、記号が無ければ合計は 702 より**少なく**なるはずで、**多い側のずれを説明できないため落とした**） |
| **🟡 が 0 件で終わった巡回** | **5%** |
| 帰結が「壊れる」 | 38.6% |
| 帰結が「誤読の余地」 | **59.3%** |

**「壊れる」が 0 件だった型**（＝直しても何も守られなかったもの）:

| 型 | 件数 |
|---|---|
| 位置に依存した参照（行番号・「後述」「直上」・手書きの件数） | 65 |
| PR のメタデータ（説明文・ラベル） | 51 |
| その他 | 39 |
| 表現・語調 | 19 |

**長引いた PR**: #51 が 14 巡（規則文書）、#40 が 12 巡（退会済み利用者の決定）、
#84 が 7 巡（失敗の名指し）。**規則文書の PR が最悪ケースである。**

**結論。** 巡回が終わらない主因は2つ。
**(1) 「誤読の余地」の指摘 416 件（59%）を直し続けたこと。**
**(2) 作業側の直し方**——指摘された1箇所だけを直す・同じ記述の一部だけを直す・修正と同時に説明を足す——**が次の指摘を生んだこと。**

## 3. 採った基準

> **この章は 2026-09-07 時点の到達点である。** その後に変わった点は
> **これ以降のすべての追記と [REVIEW.md](../REVIEW.md) にある。**
> **別のプロジェクトで採用するときは、この章と、これ以降のすべての追記を合わせて読む。**
> **節番号で範囲を切らない**——追記が増えるたびに列挙が漏れる（7.1）。
> **この章だけを写すと、その後に塞いだ穴が開いたままになる。**

**「正しい」ではなく「決めた範囲に収まっていれば、間違ってはいない」で切る**（依頼側の再定義）。

### 3.1 誰が見るかを3つに割る

> **下の表の「AI レビュー」の行は、後に「数え直さない」形に変えた**（r22。9 節の束8）。
> **見る対象の実体は 9.1 の許可列挙（A〜E）であり、表では数え直さない**——数え直した版が
> 9.1 から漏れるためである。**現行は [REVIEW.md](../REVIEW.md) 0章。**

| 誰が見るか | 何を見るか |
|---|---|
| **CI** | 書式を固定した宣言の照合（相対リンク・連番・件数・N経路・N種類）、lint・型・ビルド・テスト、依存の脆弱性 |
| **AI レビュー** | **意味の比較**（2文書で条件・キー・認可境界・値が違わないか、指示形のコメントが実態と合っているか、参照実装を写しても穴が無いか）、**依存の追跡**（踏むと壊れる条件、認可の網羅）、**判断の申告** |
| **誰も見ない** | 表現・語調・命名の好み・必要以上の複雑さ・相対の位置・行番号・固定書式に一致しない手書きの件数 |

**機械が確実に判定できることを AI に投げない。** 非効率であり、指摘もぶれる。
**逆に、意味の比較と依存の追跡は機械にできない。**

### 3.2 レビューを許可列挙にする

**禁止列挙は、記憶を持たないレビュアーには効かない**（実測: 242巡回・🟡661件）。
「列挙に無いものは報告しない」に反転する。

### 3.3 🔴 の閾値

> **下記の2条件は「食い違い」の側にだけかかる。** その後、**欠落の側にも 🔴 を定めた**——
> **品質属性（C）の「決めるべきものが書かれていない」**と、
> **決定の到達（D）の「実装者が開くファイルに決定が書かれていない」**がそれである（r13・r17・r21。9〜11 節）。
> **現行は [REVIEW.md](../REVIEW.md) 1章と 9.2。**

**外的要因（認可・秘密・法令・顧客要望・セキュリティ観点・要件の区分）は、条件なしで 🔴。**
**食い違いか欠落かを問わない。**

**それ以外の食い違いが 🔴 になるのは、次の2つを同時に満たすときだけ。**

> **(a) 上流の成果物に書かれており、かつ**
> **(b) その食い違いが、下流の選択を変える。**

**判定の1問**: **「その記述に、そのまま従った結果が壊れているか」。**

**動線**（上流 → 下流）:

```
課題文 → 要件定義書 → 機能一覧 → schema の docblock / 参照実装 → 実装
規則文書 → 作業のやり方
scripts のコメント → 次に触る人の変更
```

**(a) だけでは切れない。** 文書中心のリポジトリではほぼ全部が上流であり、範囲が元に戻る。
**「実装に関わるか」でも切れない。** それでは文書のほとんどが 🔴 になる。

### 3.4 巡回を有限にするもの

- **🟡 は直さない。** イシューに記録して節目へ
  （**その後、設計の提案①②だけを例外にした**——現行は [REVIEW.md](../REVIEW.md) 1章）
- **巡回数の上限は置かない。** **数で切るのは逃げであり、閾値が有限性を担う**（依頼側の判断）
- **打ち切りは理由で決める。** 「直す方法が無い」「判断が人に属する」のときだけ。
  **回数は判定の材料であって条件ではない。** 同じ束が5巡以上になったら**要因を報告する（止めない）**

## 4. 整合性の単位（この作り直しの核）

- **整合性を取る単位は「同じ規則・決定・記述が当たる箇所の全体」。** 編集した近傍でも、全文書でもない
- **「壊れている」の判定単位は「規則の適用状態」。** 1箇所でも欠けていれば**その規則が未適用**であり、
  「その1箇所が壊れている」ではない。**修正の単位は適用先の全体**
- **「1 PR 1目的」の「目的」は「1つの規則・決定を、その適用先全体に当てること」。**
  ファイルや機能を跨いでも1目的。適用先が PR の目的を超えるなら**規則単位の別 PR に分ける**
- **レビュー側も同じ単位で報告する。** 規則の未適用を1箇所見つけたら、**適用先を列挙して1件として**報告する

## 7. 繰り返し効いた教訓（**ここが一番移植価値が高い**）

### 7.1 列挙で書かない

**規則の適用範囲を各所で列挙すると、足し漏れた項目がそのまま穴になる。**

実測: 「認可・秘密の 🟣 は 🔴 と同じ扱い」は**3巡続けて足し漏れた**——
手順に足す → **上限**の側が開く → 上限に足す → **順序**の側が開く。
「どの PR でも見る」の列挙も**2巡続けて落ちた**——オーナーの閲覧範囲 → セキュリティ12観点。
**セキュリティ12観点が落ちた状態は、実装 PR で XSS・SQLi の指摘が 🟡 に落ちる穴だった。**

**手当は「実体を1箇所に置き、各所は参照で指す」。**
**「以降で中身を挙げている箇所は言い換えであって、適用先の全部ではない」と明記する。**

**もう一つの形は「見る側を列挙せず、見ない側だけを限定する」。**
除外の側は数が少なく、足し漏れても範囲が広がる方向にしか倒れない。

### 7.2 適用先を探す grep は、規則の「移す先」ではなく「移す元」で引く

「🟣 を 🔴 と同じに扱う」という規則の適用先を `grep 🟣` で探すと**見つからない。**
**探すべきは 🔴 を扱っている箇所である。**（レビュアーの指摘。3巡目でこれに気づいた）

### 7.3 台帳に挙げただけの適用先は「適用済み」に見える

台帳は次の巡回が**指摘より先に読む**。
「適用先に挙げたが実文に当てていない」箇所は、**次の巡回が「適用済み」と判断して直さない。**

**この実測から導いた運用は2つある**——「台帳の適用先に挙げたら、同じ push のうちに実文へ当てる」と
「台帳の事実誤りは、重大度によらず気づいた時点で直す」。
**どちらも [CLAUDE.md](../CLAUDE.md)「台帳の運用」1・2 として規則になった**（#159。2026-09-09）。
**ここに残すのは実測（r7・r9）だけである。**

**3つ目は、別の実測から出た。** PR #165 の第6巡で、**台帳の束の欄に「適用先は2箇所」と
書いてあったのに、新しい内容を足すときにその欄を見ず、片方にだけ当てた。**
束の欄は「読むもの」であって「引き直すもの」だと分かっていなかった。
**[CLAUDE.md](../CLAUDE.md)「台帳の運用」3 として規則になった**（#159。2026-09-09）。

**規則文書へ移すまで届かなかった理由が、7.3 の型そのものだった**——
巡回の作業側が台帳を書くときに開くのは `CLAUDE.md` であり、**この文書は開かない。**

### 7.4 3巡続けて足し漏れたら、足していく形そのものを疑う

回数は打ち切りの条件ではないが、**「直し方が間違っている」ことの兆候ではある。**

### 7.5 ソースの字面ではなく、描画後の形で確認する

Markdown の**遅延継続**により、番号付きリストの直後に空行なく段落を置くと、
**その段落は項目の中に描画される。** 「マージを巡回の外へ出す」修正が、
ソースでは出ているのに読まれる形では出ていなかった（1巡を消費）。

```
grep -n "実測\|巡回\|巡した\|巡目\|[0-9]件\|[0-9]%" REVIEW.md CLAUDE.md
grep -n "実際に\|(#[0-9]\|（#[0-9]" REVIEW.md CLAUDE.md
```

**数字を伴わない経緯は1つ目の網に掛からない**（例: 「実際に…食い違った（#62）」「（#46 で確認）」）。
**2つの `grep` でも足りない前提で、上の基準に照らして通読する。**

**この文書 → 規則文書の引き方。**
**`grep` では引けない**——「規則文書に無い」ことは、その文書を読まないと分からないためである。
**この文書を通読し、「〜する」「〜しない」と作業を指示している記述を拾い、
規則文書に同じ趣旨があるかを1つずつ確かめる。**
冒頭の申告が挙げているのは**例であって、全部ではない**。
**1箇所でも残れば、その規則は未適用である**（[REVIEW.md](../REVIEW.md) 9.3）。
**「減らす」は「移す」であって「消す」ではない。**

## 16. 方針の適用範囲を、確かめずに広く読んだ（2026-09-09）

**[README](../README.md) の「依存の版を上げない方針」を、脆弱性の修正まで拒む方針として読んだ。**
実際にはその方針が挙げる却下の実例3件は**すべて「新しい版が出たから上げる」**であり、
**脆弱性を理由とした更新は1件も無かった。**

**依頼側の指摘**: 「この README の依存の版を上げない方針っていうのは、バージョンを勝手に
上げないっていう話じゃないの？」——**方針の根拠（実例3件）を読み直せば、その場で分かった。**

**同じ形の失敗が3つ並んだ。**

| # | 誤り | 確かめれば消えたもの |
|---|---|---|
| 12 | 「聞く」側で、選択肢の一方を確かめずに判定を仰いだ | 公式文書1ページ |
| 13 | 「壊れる」を前提に置き、壊れない形を探さなかった | 設計の選び直し |
| **16** | **方針の適用範囲を、根拠を読まずに広く取った** | **同じ節の実例3件** |

**共通するのは、根拠を読まずに結論の側を採ったことである。**
12 は問いを立てる前、13 は代償を書く前、16 は方針を適用する前。**いずれも一次情報が手元にあった。**

**手当**: README の当該節に、**却下する対象を1文で書いた**
（「この方針が却下するのは『新しい版が出たから上げる』だけである。脆弱性を塞ぐための更新は、
この方針の対象ではない。取り込む」）。**実例からの推測に任せず、範囲を明文にした。**

**塞ぎ方の表（直接の依存 → 上げる／依存の依存 → `overrides`／上流が未対応 → 名指しで通す）のうち、
3つ目は同じ PR の中で実際に使った**——`multer` の3件を `scripts/audit-allowlist.json` に置いた（#166）。

**一度回して分かったのは、書いたときの形が実行できないものだったことである。**
最初は「advisory を名指しで**一時除外**する」と書いたが、**`npm audit` にその指定は無い**
（npm 11.13.0 の `--help` で確認）。**`--json` の出力を自前で判定する形に置き換えた。**
`audit.yml` のコメントが既にその事実を書いていたのに、読まずに書いた——**この節の失敗と同じ形である。**

**回してもう1つ分かったのは、通す仕組みには落とす条件が2つ要ることである。**
「許可していない high が残る」だけでは足りず、**「許可した id が出なくなった」でも落とさないと、
上流が直っても許可が残り続ける。** そして**そのとき CI は緑のまま**であり、誰も気づかない。
