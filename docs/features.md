# 機能一覧

各機能の受け入れ条件と、実装時に判断が要る点を記す。
「何を作らないか」は [要件定義書](requirements.md) 3.4 にある。

実装の順序は下記の章立てのとおりとする。**前の章が動かないと次が検証できない依存関係**になっている。

---

## 凡例

### 区分 — その機能がどこから来たか

| 区分 | 定義 |
|---|---|
| **要求** | 課題文に明記されている機能 |
| **派生** | 要求を満たすために技術的に不可避な機能。「根拠」欄に**どの要求が成立しないか**を記す |
| **提案・承認済** | **提案し、承認を得た上で実装する**機能。「根拠」欄に**承認の記録**を記す |

区分を設ける理由は [要件定義書](requirements.md) 3.0 に記す。

### 優先度 — 実装順序の依存関係

**期限管理の指標ではない。** 明確な期限は設けていない（[要件定義書](requirements.md) 5）。

| 優先度 | 意味 |
|---|---|
| **Must** | 他の多くの機能がこれに依存する。先に動かす必要がある |
| **Should** | 要求に含まれるが、他の機能から依存されない |
| **Could** | 提案・承認済の機能。要求の実装が済んでから着手する |

## 1. 認証とユーザー基盤

### 1.1 新規登録（F-01 / F-03）

| 項目 | 内容 |
|---|---|
| 入力 | ユーザーID / パスワード / 表示名 |
| ユーザーID | 英数字とアンダースコアのみ、3〜30文字。**一意**。メンションの `@` に続く識別子として使う |
| パスワード | 8文字以上。**Argon2id** でハッシュ化して保存する |
| メールアドレス | **取得しない**（[要件定義書](requirements.md) 3.4） |

**受け入れ条件**

- 既に使われているユーザーID では登録できない
- パスワードは**平文でもハッシュでも**レスポンスに含まれない
- パスワードがログに出力されない
- 新規登録に発信元単位のレート制限がかかる
- **登録の完了時にリカバリーコードが1度だけ表示され、控えたことの確認を経ないと先に進めない**（F-37）
- **新規登録を設定で停止できる**（[要件定義書](requirements.md) 5.1。公開方針を変える際に
  コード変更を要しない状態にしておくため）

#### リカバリーコード（F-37）

メール送信を対象外にしているため（[要件定義書](requirements.md) 3.4）、**メールによる
パスワードリセットは提供できない。** 何も用意しなければ、パスワードを忘れた時点でアカウントは死ぬ。
その唯一の復旧手段として、**オフラインで保管するリカバリーコード**を発行する。

| 項目 | 内容 |
|---|---|
| 発行 | **新規登録の完了時に1度だけ表示する。** 以後は再表示できない |
| 保存形式 | **コード自体は保存せず、パスワードと同様に Argon2id でハッシュ化して保存する** |
| 用途 | コードとユーザーID の提示により、パスワードの再設定を行う |
| 使用後 | **使い捨てとし、使用したコードは無効化する。** 再設定の完了時に新しいコードを発行する |

**受け入れ条件**

- **リカバリーコードが平文でデータベースに保存されない**
- 一度使用したコードが再利用できない
- コードの照合にレート制限がかかる（**総当たりの対象になるため**）
- 登録画面に「**コードを失うと復旧できない**」ことが明示される

> **リカバリーコードを紛失した場合、そのアカウントは復旧できない。** これは
> メール送信を持たない構成の帰結であり、**仕様として利用者に伝えないまま復旧不能にするのは
> 不誠実である**ため、登録画面に明示する。

### 1.2 ログイン / ログアウト（F-02）

| エンドポイント | 内容 |
|---|---|
| `POST /auth/login` | ユーザーID とパスワードで認証する |
| `POST /auth/refresh` | リフレッシュトークンから新しいアクセストークンを得る |
| `POST /auth/logout` | リフレッシュトークンを失効させる |

**受け入れ条件**

- 認証失敗時、「ユーザーID が存在しない」と「パスワードが違う」を**区別しない**
  （区別すると、どのユーザーID が登録済みかを外部から総当たりで調べられる）
- ログイン試行にレート制限がかかる（発信元単位・アカウント単位）
- リフレッシュのたびにトークンがローテーションされる
- ログアウト後、リフレッシュトークンが再利用できない
- **リフレッシュトークンの Cookie が `HttpOnly; Secure; SameSite=Strict; Path=/api/auth` である**
- **`/auth/refresh` と `/auth/logout` は、カスタムリクエストヘッダーが無いリクエストを拒否する**
- **`Origin` / `Sec-Fetch-Site` が許可されたものでない場合、上記2つのエンドポイントが拒否する**

> **Cookie を使うのはこの2つのエンドポイントだけである。** 他の API はすべて
> `Authorization` ヘッダーで認証するため、ブラウザが認証情報を自動送信せず、CSRF が成立しない。
> **専用の CSRF トークン機構を持たない判断とその代償**は
> [要件定義書](requirements.md) 4.3 に記す。

### 1.3 プロフィール設定（F-04）

- 表示: アバター画像 / 表示名 / ユーザーID / ステータス（絵文字＋テキスト）
- 編集: アバター画像 / 表示名 / ステータス
- **ユーザーID は変更できない**（メンションの参照先が壊れるため）

**受け入れ条件**

- アバター画像は F-28 の検証（サイズ・形式・マジックバイト）を通る
- ステータスは絵文字1つとテキスト（最大100文字）で構成される

### 1.4 サーバー側の認可検証（F-05）

**この機能は画面を持たない。** すべての API と WebSocket イベントに適用する横断的な仕組みである。

**受け入れ条件**

- **フロントエンドを経由せず API を直接呼んでも、権限のない操作は拒否される**
- 「自分のメッセージのみ編集・削除できる」がサーバー側で検証される
- 「オーナーのみが招待・キック・チャンネル操作を行える」がサーバー側で検証される
- 権限のない操作は 403 を返す。**404 と使い分ける**
  （存在を隠すべきプライベートチャンネルは 404、権限不足は 403）

### 1.5 アカウントの削除（F-36）

設定画面から、利用者が自分のアカウントを削除できる。

| 項目 | 決定 |
|---|---|
| 実行できる人 | **本人のみ** |
| 確認 | **パスワードの再入力**を求める |
| 過去のメッセージ | **残す。** 削除すると会話の文脈が壊れるため（キック時と同じ扱い） |
| 表示名 | 削除済みの利用者として表示する（メンションの参照先も同様） |
| ユーザーID | **再利用させない。** 過去のメンションが別人を指すことを防ぐ |
| オーナーの場合 | **ワークスペースにオーナーが不在になるため、削除できない。** オーナー権限の委譲を対象外としているため（[要件定義書](requirements.md) 3.4） |

**受け入れ条件**

- 本人以外がアカウント削除 API を呼ぶと 403 が返る
- 削除後、そのアカウントでログインできない
- **削除した利用者の過去のメッセージが残り、会話が読める状態を保つ**
- ワークスペースのオーナーであるアカウントは削除できず、理由が画面に表示される

> **これは論理削除である。** 本文はデータベースに残り続ける（[要件定義書](requirements.md) 3.4 / 6.2）。
> **「削除した」という利用者の認識と、実際の保持状態が一致しない。**
> 実運用では、削除の求めに応じるための物理削除の仕組みが別途必要になる。

## 2. ワークスペースとメンバー管理

### 2.1 ワークスペース（F-06 / F-07）

- 誰でも作成できる。**作成者がオーナーになる**
- 1人の利用者が複数のワークスペースに所属できる
- サイドバーでワークスペースを切り替える

**受け入れ条件**

- ワークスペースを作成すると、作成者がオーナーとして所属した状態になる
- 所属していないワークスペースの情報は取得できない（404）

### 2.2 招待とキック（F-08 / F-09）

| 操作 | 実行できる人 | 内容 |
|---|---|---|
| ワークスペースへの招待 | **オーナーのみ** | ユーザーID を指定。**招待された利用者が承諾して初めて参加する**（F-38） |
| **ワークスペースからの退出** | **メンバー本人** | 自分の意思で抜けられる（F-38）。**オーナーは退出できない** |
| ワークスペースからのキック | **オーナーのみ** | **所属していた全チャンネルから自動的に外れる** |
| チャンネルからのキック | **オーナーのみ** | そのチャンネルのみから外す |
| プライベートチャンネルへの招待 | **そのチャンネルの参加者なら誰でも** | 招待先は同一ワークスペースのメンバーに限る |

**受け入れ条件**

- メンバーがワークスペースへの招待・キック API を呼ぶと 403 が返る
- キックされた利用者の**過去のメッセージは残る**
- キックされた利用者は、そのワークスペースのデータに一切アクセスできなくなる
- プライベートチャンネルへの招待で、ワークスペース外の利用者は指定できない

#### 招待の承諾と退出（F-38）

**承諾フローを設けない場合、利用者は知らないワークスペースに勝手に追加される。**
退出の導線も無ければ、**「追加される一方で、抜けられない」**状態になる。この2つは同じ問題の
表と裏であるため、まとめて F-38 とする。

| 状態 | 内容 |
|---|---|
| 招待済み（未承諾） | 招待された側に通知が出る。**この時点ではワークスペースに所属していない** |
| 承諾 | 参加が成立する。パブリックチャンネルの一覧が見えるようになる |
| 辞退 | 招待が消える。**オーナーは再度招待できる** |
| 退出 | **所属していた全チャンネルから外れる。** 過去のメッセージは残る（キックと同じ扱い） |

**受け入れ条件**

- **承諾していない招待の段階では、ワークスペースのデータを一切取得できない**（404）
- 退出したあと、そのワークスペースのデータにアクセスできない
- **退出した利用者の過去のメッセージは残る**
- **オーナーが退出しようとすると拒否され、理由が画面に表示される**

> **オーナーが退出できないのは、オーナー権限の委譲とワークスペースの削除を対象外にしている
> ためである**（[要件定義書](requirements.md) 3.4）。**その結果、ワークスペースを作った利用者は
> そこから抜けられない。** 実運用に移す場合は、権限の委譲かワークスペースの削除が必要になる。

> **参加の記録は物理削除である。その代償を記録する**（[CLAUDE.md](../CLAUDE.md) 4）。
> 退出・キック・チャンネルからの離脱は、参加の記録を**消す**。論理削除にしない。
> **その結果、「いつ誰が抜けたか」は後から追えない。**
> メッセージ（3.4 で論理削除と決めている）とは扱いが違う。
>
> 論理削除にすれば追えるが、**可視性を判定するすべての箇所に「抜けていないこと」の
> 条件が増える。1箇所でも書き漏らすと、抜けた利用者にデータが見え続ける。**
> 追跡できることより、判定を単純に保つことを採った。
> 監査の記録が要る運用に移す場合は、参加の履歴を別に持つ必要がある。

## 3. チャンネル

### 3.1 チャンネル作成（F-10）

| 種別 | 見え方 |
|---|---|
| **パブリック** | ワークスペースのメンバーなら誰でも一覧に見え、**自由に参加・退出できる** |
| **プライベート** | 参加者だけに見える。**一覧にも検索にも出ない** |

- **作成・アーカイブはオーナーのみ**（課題文の権限要件）

**受け入れ条件**

- メンバーがチャンネル作成・アーカイブ API を呼ぶと 403 が返る
- **非参加者がプライベートチャンネルを取得しようとすると 404 が返る**（403 ではない。存在を隠す）
- プライベートチャンネルはチャンネル一覧 API のレスポンスに含まれない
- **オーナーであっても、参加していないプライベートチャンネルのメッセージは取得できない**
- **オーナーは、参加していないプライベートチャンネルの参加者一覧は取得できる**

> **参加者一覧だけを見せる理由。** オーナーはチャンネルからのキック権限を持つが、
> **誰がいるか見えなければキックすべき相手を特定できず、課題文が求める管理者権限が機能しない。**
> 一方でメッセージまで見せると「プライベート」が名目だけになる。
> **境界は「人の出入りの管理」と「会話の閲覧」の間に引く**（[要件定義書](requirements.md) 3.5.1）。

### 3.2 チャンネルのアーカイブと復元（F-35）

**削除ではなくアーカイブとする。** オーナーは参加していないプライベートチャンネルのメッセージを
閲覧できないため、削除を認めると **中身を一切知らないまま他人の会話をまるごと失わせる**
操作が成立してしまう。

| 項目 | 決定 |
|---|---|
| 実行できる人 | **オーナーのみ**（課題文の権限要件どおり） |
| アーカイブ後 | チャンネル一覧から外れる。**参加者は読めるが、投稿はできない** |
| 復元 | **オーナーが復元できる。** 復元すると投稿可能な状態に戻る |
| 物理削除 | **行わない**（[要件定義書](requirements.md) 3.4） |

**受け入れ条件**

- メンバーがアーカイブ・復元 API を呼ぶと 403 が返る
- **アーカイブされたチャンネルに投稿しようとすると拒否される**
- アーカイブされたチャンネルの**過去のメッセージは検索結果に出る**（参加者に限る）
- 復元後、投稿できる状態に戻る

> **課題文の「チャンネルの追加・削除」との関係。** 利用者から見た「チャンネルを消す」操作は
> アーカイブとして提供する。**要求は満たしつつ、取り返しのつく形にした**という位置づけである。

#### アーカイブ時に名前へ振り分け番号を付ける（**提案・承認済。2026-09-04**）

**F-35 の実現方式についての決定であり、新しい機能ではない。** よって機能番号は与えない。

アーカイブしたチャンネルが名前を抱えたままだと、**同じ名前で新しいチャンネルを作れない。**
`general` をアーカイブした組織は、二度と `general` を作れないことになる。

| 項目 | 決定 |
|---|---|
| 採番 | **アーカイブの時点で、システムが自動的に番号を付ける**（`general` → `general-1`） |
| 番号の付け方 | 作成時の名前（基底名）ごとに、**その名前がまだ空いている最小の番号**を採る |
| 復元したとき | **番号は外れない。** `general-1` のままである |
| **再びアーカイブするとき** | **採番も改名も行わない。** 既に持っている番号と名前のままアーカイブする |
| 実行の単位 | **アーカイブ・採番・改名は同一トランザクションで行う。** 片方だけ実行された状態を作らない |

> **「最大の番号 + 1」ではない理由。** チャンネル名に制限は設けていないため、
> **利用者が自分で `general-1` という名前のチャンネルを作れる。**
> その状態で `general` をアーカイブすると、最大 + 1 では 1 を選び、名前が衝突して
> **アーカイブそのものが失敗する。** 改名の機能は無いため、そのチャンネルは
> **永久にアーカイブできない**状態になる。F-35 は Must であり、これは受け入れられない。
>
> 同時に2つをアーカイブすると、両方が同じ番号を選ぶことがある。
> **一意制約違反を捕まえて番号を進め、やり直す。**
>
> **採番するのは、まだ番号を持たないチャンネルだけである。** 復元したチャンネルは番号を
> 持ったままなので、再びアーカイブするときに採番し直さない。し直すと、**自分自身が
> `general-1` を使っているため次は 2 になり、アーカイブと復元を繰り返すたびに
> 名前がずれ続ける。**

**受け入れ条件**

- アーカイブしたあと、**同じ名前で新しいチャンネルを作れる**
- 復元しても名前は元に戻らない
- **アーカイブだけ、採番だけ、改名だけ、のいずれも成立しない**（データベースが拒否する）
- **利用者が先に `general-1` を作っていても、`general` をアーカイブできる**

> **この判断の代償を記録する**（[CLAUDE.md](../CLAUDE.md) 4）。
>
> 1. **アーカイブを解除しても名前が元に戻らないため、利用者から見ると
>    「別のチャンネルになった」ように見える。** 復元は名前の復元ではない
> 2. **過去のメンションやリンク、外部に共有された参照が指す名前と、現在の名前がずれる。**
>    参照が ID で解決されていれば辿れるが、名前で書かれたものは辿れない
>
> 採らなかった側の代償も記す。**アーカイブ時に改名しない**方式では、
> チャンネル名の一意制約をアーカイブ済みのものだけ除外する形にせざるを得ず、
> **「一覧に出ないのに、その名前は使えない」**という説明のつかない状態が残る。

## 4. メッセージ

### 4.1 投稿と一覧（F-11 / F-12）

- 投稿: テキスト（最大4000文字）＋ 添付（F-27）
- 一覧: **カーソルページネーション**。上方向に遡って読み込む

**受け入れ条件**

- `OFFSET` を使わない。カーソル（メッセージID または時刻）で位置を指定する
- 過去メッセージを読み込んでも**スクロール位置が飛ばない**
- 参加していないチャンネルのメッセージは取得できない（404）

### 4.2 編集と削除（F-13）

**受け入れ条件**

- 自分以外のメッセージを編集・削除しようとすると 403 が返る
- 編集したメッセージには「編集済み」が表示される
- 削除は**論理削除**。表示は「このメッセージは削除されました」に置き換わる
- **スレッドの親メッセージを削除しても、返信は保持される**
- 編集・削除は `message:updated` / `message:deleted` として他の利用者に即時配信される

### 4.3 Markdown 対応と XSS 対策（F-14 / F-15）

対応する記法: 太字 / 斜体 / 取り消し線 / リンク / 引用 / 箇条書き / インラインコード / コードブロック

**受け入れ条件**

- **HTML 文字列を生成せず、要素を直接構築する方式で描画する**（`dangerouslySetInnerHTML` を使わない）
- 生の HTML タグを含む入力が、HTML として解釈されない
- **`javascript:` などの危険なスキームのリンクが無効化される**
- 上記を検証する自動テストが存在する

## 5. リアルタイム配信（F-16）

**この章が動かないと、以降のほぼ全機能が「リロードしないと反映されない」状態になる。**

### 5.1 配信するイベント

| イベント | 内容 |
|---|---|
| `message:new` | メッセージの新規投稿 |
| `message:updated` | メッセージの編集 |
| `message:deleted` | メッセージの削除 |
| `reaction:changed` | リアクションの追加・取り消し |
| `unread:updated` | 未読件数の変化 |
| `typing:start` / `typing:stop` | 入力中インジケータ（F-34） |
| `presence:changed` | 在席状態の変化（F-22） |

**この7種類以外の変化は即時反映されない。**

### 5.2 受け入れ条件

- **接続確立時にトークンを検証する。** 無効なトークンでは接続できない
- **ハンドシェイク時に `Origin` を検証し、許可リストにないもの・`Origin` を持たないものを拒否する**
- **認証情報を Cookie で渡さない**（ハンドシェイクの `auth` で渡す）
- **上記2点を検証する自動テストが存在する**（許可外の Origin から接続できないこと）
- **イベントの送受信のたびに、送信元・宛先が該当チャンネルの参加者であることを確認する**
- **非参加者に、プライベートチャンネルのイベントが配信されない**
- 通信が切れた場合、自動的に再接続する
- 再接続後、切断中に発生したメッセージが補完される
- **複数のサーバーインスタンスに分かれて接続していても、全員にイベントが届く**
- イベント定義の型がフロントエンドとバックエンドで共有されている（2箇所に書かない）

> **WebSocket は同一オリジンポリシーの対象外であり、CORS でも守られない。**
> Socket.IO の `cors` オプションが効くのは HTTP long-polling のみである。
> 対策がなければ **Cross-Site WebSocket Hijacking（CSWSH）** が成立し、悪意あるサイトから
> 利用者のセッションで接続を確立される。**`allowRequest` による Origin 検証が必須である**
> （[要件定義書](requirements.md) 4.3）。

## 6. スレッド（F-17）

- 任意のメッセージに返信をぶら下げる。**1階層のみ**
- 親メッセージに「◯件の返信」と参加者のアバターを表示する

**受け入れ条件**

- スレッドの返信は、チャンネル本体の一覧に混ざって表示されない
- 返信件数がカウンタ列として保持され、一覧取得時に `COUNT` を発行しない
- **返信に対してさらにスレッドを作ることはできない**

## 7. 絵文字リアクション（F-18）

**受け入れ条件**

- 同じ絵文字を二重に付けられない（付け外しのトグル）
- **誰が付けたかが分かる**（ホバーで一覧を表示）
- リアクション数がカウンタ列として保持される
- 追加・取り消しが `reaction:changed` として即時配信される

## 8. ダイレクトメッセージ（F-19）

- **1対1のみ。** グループ DM は対象外（[要件定義書](requirements.md) 3.4）

**受け入れ条件**

- 自分が当事者でない DM は取得できない（404）
- 同じ相手との DM は1つに集約される（重複して作られない）

## 9. メンション

### 9.1 個人メンション（F-20）

- 入力欄で `@` を打つと候補が補完される
- **ユーザーID で解決する**（表示名は重複しうるため）

**受け入れ条件**

- メンションされた利用者に F-24 のバッジと F-25 のブラウザ通知が届く
- **そのチャンネルに参加していない利用者はメンションできない**
- 補完候補に、そのチャンネルの参加者以外が出ない

### 9.2 `@here` / `@channel`（F-21）と在席表示（F-22）

| 記法 | 通知先 |
|---|---|
| `@here` | そのチャンネルの**在席中の参加者** |
| `@channel` | そのチャンネルの**参加者全員** |

- 在席状態は **WebSocket の接続の有無**から判定する
- メンバー一覧に在席を表示する

**受け入れ条件**

- 在席状態を**色や記号だけで伝えない**。テキストの代替を併せて提供する
- 在席の変化が `presence:changed` として配信される

**判断が必要な点（実装時に決める）**

- **タブを開いたまま離席している利用者も「在席」と判定される。** 一定時間操作が無い場合を
  離席とみなすか、接続の有無のみで判定するか

## 10. 未読と通知

### 10.1 未読管理（F-23）

- チャンネルごとの未読を、サイドバーで太字表示する
- メッセージ一覧に「ここから未読」の区切り線を表示する
- **「利用者 × チャンネル」の既読位置を保持し、そこからの差分で未読を求める**（都度集計しない）

**受け入れ条件**

- **スレッド内の未読をチャンネル未読に含めるかを、利用者が設定で切り替えられる。既定は「含める」**
- 未読の変化が `unread:updated` として即時配信される
- **設定を「含めない」→「含める」に切り替えると、過去のスレッド返信のうち未読のものが未読として現れる**

> **設定の切替時は未読が復活する。** 既読位置を「利用者 × チャンネル」と「利用者 × スレッド」の
> 2系統で持つため、切り替えた瞬間に集計対象が変わる。**切替時に一括で既読扱いにすると、
> 読んでいないものが読んだことになる**ため、未読として現れる側を採る
> （[要件定義書](requirements.md) 3.5.2）。

### 10.2 メンション通知とブラウザ通知（F-24 / F-25）

**受け入れ条件**

- ブラウザ通知が出るのは**メンションと DM のみ**。通常のメッセージでは出さない
- **通知の許可を求めるのは、利用者が明示的に有効化したときのみ**（初回訪問でいきなり求めない）
- **許可が拒否された場合も、画面内のバッジで未読とメンションが分かる**
- タブを開いている間のみ通知される（プッシュは対象外）

### 10.3 通知一覧画面（F-26）

- 受け取ったメンション・DM を時系列で一覧表示する
- 既読化できる

**受け入れ条件**

- オフライン中に受けたメンションが、次回ログイン時に一覧で確認できる
- 通知から該当メッセージに移動できる

## 11. 添付ファイル

### 11.1 アップロード（F-27 / F-28）

**許可リスト方式とする。列挙した形式のみを受け入れる。**

| 種別 | 上限 | 許可する形式（これ以外は受け付けない） |
|---|---|---|
| 画像 | 10 MB | jpeg / png / gif / webp（**SVG は含めない**） |
| 動画 | 100 MB | mp4 / webm |
| 文書 | 25 MB | pdf / txt / csv / md / docx / xlsx / pptx |
| 圧縮 | 25 MB | zip |

**受け入れ条件**

- **サーバー側でマジックバイトを検証する。** 拡張子や申告された Content-Type を信用しない
- 上限を超えるファイルは拒否される
- **許可リストに無い形式は拒否される**（拒否リストではない）
- **SVG がアップロードできない**
- **アップロード用の署名付き URL の発行にレート制限がかかる**（投稿しなくても S3 の操作と行の追加が起きるため）
- **S3 のオブジェクトキーが `workspace/{ws}/channel/{ch}/{UUID}/{ファイル名}` の形式である**

> **拒否リストを採らない理由。** 「実行形式を除く」という書き方では、`.exe` を弾いても
> `.dll` `.jar` `.ps1` `.scr` `.msi` `.lnk` が残る。**拒否リストは必ず抜ける。**
> さらに「任意の形式」ではマジックバイトの検証がかけられない。

> **SVG を受け付けない理由。** SVG は画像ではなく **XML** であり、`<script>` を内包できる。
> 受け入れると保存型 XSS と XXE の経路になる。サニタイズによる受け入れも可能だが、
> それは**保険的対策**であり、**受け付けない構造にすることが根本対策**である
> （[要件定義書](requirements.md) 3.4）。

> **動画のサムネイルは生成しない。** `<video src="...#t=30">` により 30 秒地点の映像を
> 表示させる（[要件定義書](requirements.md) 3.5.2）。サーバー側に動画処理の基盤を持たない。
> **一覧では Intersection Observer で遅延読み込みし、画面外の `<video>` 要素は生成しない。**
> `#t=30` の表示にはブラウザが 30 秒地点までシークする必要があるため、画面外の分まで
> 要素を作るとスクロールのたびに読み込みが走る。

### 11.2 配信の認可（F-29）

**CloudFront の署名付き Cookie をチャンネル単位で発行する。**

```
① ブラウザがチャンネルを開く
② サーバーが「この利用者は、このチャンネルの参加者か」を判定する
③ OK なら workspace/{ws}/channel/{ch}/* に限って有効な署名付き Cookie を返す / NG なら 404
④ ブラウザは、そのチャンネルの添付を CloudFront から直接取得する
⑤ 期限が切れたら、チャンネルを開いている限りサーバーが Cookie を再発行する
```

**受け入れ条件**

- **非参加者がファイルの URL を直接指定しても取得できない**
- **非参加者に対して、そのチャンネルのパス配下に有効な Cookie が発行されない**
- **S3 バケットへの直接アクセスが遮断されている**（CloudFront 経由のみ）
- Cookie は期限切れ後に無効になる
- **チャンネルから外れた（キック・退出した）利用者は、次の再発行を受けられない**

> **署名付き URL ではなく Cookie を採る理由と、その代償**は
> [要件定義書](requirements.md) 4.3 に記す。要点は、**署名付き URL では
> 「長い動画を見ていて巻き戻すと 403 で止まる」**という壊れ方が起き、その回避実装が重いこと、
> および Cookie ならチャンネル単位で1回の発行に集約できることである。

> **認可の粒度がパス単位になる。** そのため **S3 のキー設計が認可の一部**になっている。
> `workspace/{ws}/channel/{ch}/...` の構造を崩すと認可が崩れる。

**判断が必要な点（実装時に決める）**

- **Cookie の有効期限を何分にするか。** 再発行はサーバー側で完結するため、
  短めに設定できる（15〜30 分を想定）

## 12. 検索

### 12.1 メッセージ検索（F-30 / F-31）

- **全文索引**（pg_bigm による 2-gram）で日本語を検索する
- **種別ごとに分類して表示する**: メッセージ / チャンネル / ユーザー / ファイル
- **絞り込み演算子**: `from:@ユーザーID` / `in:#チャンネル名`

**受け入れ条件**

- **検索対象が「自分が参加しているチャンネルと DM」に限定される**
- **非参加者のプライベートチャンネルの本文が、検索結果に一切現れない**
- **上記を検証する自動テストが存在する**（実装漏れが最も起きやすい箇所のため）
- 削除済みメッセージが検索結果に出ない
- 検索は1回のリクエストで種別ごとの結果を返す（段階的なフォールバックはしない）

## 13. 補助機能

### 13.1 コードスニペット（F-32）

- バッククォート3つで囲んだ範囲をシンタックスハイライトする
- 言語指定に対応する

### 13.2 ピン留め（F-33）

- チャンネルにメッセージを固定する
- ピン留め一覧を表示する

**判断が必要な点（実装時に決める）**

- ピン留めを外せるのは、ピン留めした本人か、オーナーか、参加者全員か

### 13.3 入力中インジケータ（F-34）

- 「○○さんが入力中…」を入力欄の上に表示する
- 一定時間入力が止まったら消える

**受け入れ条件**

- `typing` イベントが**過剰に送信されない**（キー入力ごとに送らない）
- 自分の入力中インジケータは自分には表示されない
