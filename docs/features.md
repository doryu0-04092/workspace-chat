## 凡例

### 区分 — その機能がどこから来たか

| 区分 | 定義 |
|---|---|
| **要求** | 課題文に明記されている機能 |
| **派生** | 要求を満たすために技術的に不可避な機能。「根拠」欄に**どの要求が成立しないか**を記す |
| **提案・承認済** | **提案し、承認を得た上で実装する**機能。「根拠」欄に**承認の記録**を記す |

区分を設ける理由は [要件定義書](requirements.md) 3.0 に記す。

### 優先度 — 実装順序の依存関係

**期限管理の指標ではない。** 明確な期限は設けていない（[要件定義書](requirements.md) 5）。

| 優先度 | 意味 |
|---|---|
| **Must** | 他の多くの機能がこれに依存する。先に動かす必要がある |
| **Should** | 要求に含まれるが、他の機能から依存されない |
| **Could** | 提案・承認済の機能。要求の実装が済んでから着手する |

## 1. 認証とユーザー基盤

### 1.1 新規登録（F-01 / F-03）

| 項目 | 内容 |
|---|---|
| 入力 | ユーザーID / パスワード / 表示名 |
| ユーザーID | 英数字とアンダースコアのみ、3〜30文字。**一意**（**大文字小文字を区別しない**。下記）。メンションの `@` に続く識別子として使う |
| パスワード | 8文字以上・**128文字以下**（文字数はコードポイントで数える。上限は決定・2026-09-11・依頼側。NIST SP 800-63B-4 3.1.1.2 の「最大長は少なくとも 64 文字を許す」を満たす）。**Argon2id** でハッシュ化して保存する。**ハッシュ化も照合（1.2 のログイン・F-37 の再設定）も、NFC に正規化してから行う**（同 3.1.1.2 の SHOULD。正規化は `apps/api/src/auth/secret-hash.ts` の中にあり、保存と照合は必ずそこを通す）。**最短を 8 文字のままにする**（決定・2026-09-11・依頼側）——**代償: 同 3.1.1.2 の「パスワードだけで認証するなら 15 文字以上」（SHALL）から外れる**。この構成は二段階認証を持たず、これに当たる |
| 表示名 | **1〜50文字。空白だけは不可**（決定・2026-09-11・依頼側。上限は列の型にも入れる。1.3 の編集も同じ） |
| メールアドレス | **取得しない**（[要件定義書](requirements.md) 3.4） |

#### ユーザーID の一意性は大文字小文字を区別しない（**派生**。2026-09-05 決定）

**区分は「派生」である**（[CLAUDE.md](../CLAUDE.md) 1）。承認を得た提案ではない。
判定基準は「これが無いと、どの要求が成立しないか答えられるか」であり、答えられる。
**区別したままでは F-20（メンション）と F-36（ユーザーID の再利用禁止）が成立しない。**
理由は下に挙げる。

**新しい機能ではない。** 上の「一意」が何を同じ ID と見なすかを決めていなかったため、
その解釈を定めるものである。よって機能番号は与えない。

区別する側を採ると、`owner` と `Owner` が**別のアカウントとして共存できる。**

- ユーザーID は**メンションの `@` に続く識別子**である（下記 9.1）。
  `@owner` と `@Owner` が別人を指す状態は、**表示上ほぼ見分けがつかない**
- `owner` が退会したあとに `Owner` を登録できる。F-36 の「ユーザーID を再利用させない。
  **過去のメンションが別人を指すことを防ぐ**」（下記 1.5）が、狙った範囲まで届かない
- ログインは完全一致になるため、登録時と違う綴りを打つと「パスワードが違う」と
  **区別できない失敗**になる（下記 1.2 の方針上、利用者に理由は返らない）

**判定の根拠は DB に置く**（[CLAUDE.md](../CLAUDE.md) 2）。
`lower("userId")` に対する一意索引 `User_userId_lower_key` を
マイグレーションに手書きし、[テスト](../apps/api/src/prisma-schema.test.ts)で検証している。
アプリ側の小文字化だけに頼らないのは、登録・招待・復旧と経路が複数あり、
**1箇所でも書き漏らせば綴り違いの二重登録がそのまま通る**ためである。

**代償**

- **綴りだけが違うユーザーID は同時に存在できない。** 使える ID の空間がその分狭くなる
- 列には**登録時の綴りをそのまま保持する**（表示のため）。したがって
  **照合する側も `lower()` で引く必要がある。** 素の等値比較で書くと、
  登録時と違う綴りでは引けず、上に挙げたログインの失敗がそのまま起きる
- チャンネル名には**この決定を適用しない。** 同一ワークスペースに `general` と `General` は
  共存できる。名前に制限を置かない方針（下記 3.2）を優先した。
  **代償は、一覧で紛らわしい2つが並びうること**である

**受け入れ条件**

- 既に使われているユーザーID では登録できない
- **大文字小文字だけが違うユーザーID では登録できない**（`owner` があれば `Owner` は不可）
- パスワードは**平文でもハッシュでも**レスポンスに含まれない
- パスワードがログに出力されない
- 新規登録に発信元単位のレート制限がかかる（**発信元の判定は ALB が CloudFront からのみ到達可能であることが前提**。[技術スタック](tech-stack.md) の ALB の行。**1時間に10回**。超えたら 429 と `Retry-After`。数値は実装時に決めた値・#245。状態は Valkey に置いてタスクをまたいで数え、**Valkey が止まっている間は各タスクのメモリで、上限をタスク数で割って数える**——決定・2026-09-11・依頼側。**代償**: 切り替えの時点で数え直しになり、Valkey 側とメモリ側が別々に上限まで数えるため、**1つの発信元が1時間に通せる数は最大で2倍まで緩む**（上限をタスク数で割るのは、各タスクが別々に数えて「上限 × タスク数」になる緩みを塞ぐためであり、この数え直しは塞がない）。**Valkey を重くできる攻撃者は、この緩みを狙って起こせる**（応答が 500ms を超えると迂回に入る）。**迂回中の上限をこれ以上は下げない**（決定・2026-09-11・依頼側: 平常の運転で正規の利用者が止まるほうを避ける）。迂回中は、偏って1タスクに届いた正規の利用者が「上限 ÷ タスク数」で止まり、記録数の上限に達した後の新しい発信元も止まる。停止の全体は [要件定義書](requirements.md) 4.2）
- **登録の完了時にリカバリーコードが1度だけ表示され、控えたことの確認を経ないと先に進めない**（F-37）
- **新規登録を設定で停止できる**（[要件定義書](requirements.md) 5.1。公開方針を変える際に
  コード変更を要しない状態にしておくため）

#### リカバリーコード（F-37）

メール送信を対象外にしているため（[要件定義書](requirements.md) 3.4）、**メールによる
パスワードリセットは提供できない。** 何も用意しなければ、パスワードを忘れた時点でアカウントは死ぬ。
その唯一の復旧手段として、**オフラインで保管するリカバリーコード**を発行する。

| 項目 | 内容 |
|---|---|
| 発行 | **新規登録の完了時に1度だけ表示する。** 以後は再表示できない |
| 形式 | Crockford の Base32（I・L・O・U を使わない32文字）で16文字＝80ビットを、4文字ずつハイフンで区切って表示する。照合では大文字にしてハイフンを除き、O を 0・I と L を 1 に読み替える（#245） |
| 保存形式 | **コード自体は保存せず、パスワードと同様に Argon2id でハッシュ化して保存する**（ハッシュに掛けるのは上の読み替えをした形） |
| 用途 | コードとユーザーID の提示により、パスワードの再設定を行う |
| 使用後 | **使い捨てとし、使用したコードは無効化する。** 再設定の完了時に新しいコードを発行する |
| 同時に持てる数 | **未使用のコードは1人につき1つだけ**（**派生**。下記） |

##### 未使用のコードを同時に2つ持てない（**派生**。2026-09-05）

**区分は「派生」である**（[CLAUDE.md](../CLAUDE.md) 1）。
判定基準「これが無いと、何が成立しないか」に答えられる。
**これが無いと、上の「使い捨てとし、使用したコードは無効化する」が成立しない。**
再発行の実装が古い行を無効にし忘れると、**有効なコードが2つ残る。**
復旧手段が増えることは、そのまま**総当たりの的が増える**ことである。

**判定の根拠は DB に置く**（[CLAUDE.md](../CLAUDE.md) 2）。部分一意索引
`RecoveryCode_single_unused_per_user`（`usedAt IS NULL` の行だけを対象にした
`userId` の一意索引）がこれを担保する。**古いコードを無効にしない限り、
新しいコードを発行できない**形になる。

**代償**（[CLAUDE.md](../CLAUDE.md) 4）

- **1人に複数のコードをまとめて配る方式には、この索引を落とさない限り変更できない。**
  「10個まとめて渡して1つずつ使う」という一般的な方式は、この決定では採れない
- 発行は**必ず古い行の無効化と同一トランザクションで**行う必要がある。
  分けると、一意制約違反で新しいコードを発行できない状態が残りうる

**受け入れ条件**

- **リカバリーコードが平文でデータベースに保存されない**
- 一度使用したコードが再利用できない
- **未使用のコードがある状態で、新しいコードを発行できない**
- **退会済みのアカウントは、リカバリーコードによる再設定の対象にならない**
  （照合に `deletedAt IS NULL` を含める）。
  **退会は論理削除で `User` の行が残るため、`lower("userId")` の照合はそのまま当たる。
  DB は止めない。** 下記 1.5 の「削除後、リカバリーコードによる再設定もできない」を
  支えているのは「退会処理が同一トランザクションで `usedAt` を埋める」という
  **アプリ側の規約1本だけ**であり、**退会処理が1件でもコードを取りこぼせば、
  退会済みアカウントの `passwordHash` を書き換えられる。**
  招待（下記 2.2）と同じく**読み取り側にも条件を置いて二重にする**
- **登録時と違う大文字小文字のユーザーID でも、リカバリーコードによる再設定ができる**
  （上記 1.1 の決定。照合は `lower("userId")` で引く。
  **Prisma のクライアントの等値比較では満たせない**ため `$queryRaw` で書く）。
  ここが当たらないと、**利用者からは「アカウントが復旧不能になった」ことと区別がつかない。**
  コードは1度しか表示されず、これが唯一の復旧手段だからである
- コードの照合にレート制限がかかる（**総当たりの対象になるため**）
  - 発信元単位は 1 時間に 10 回（数値は慣行。新規登録と同じ）。**アカウント単位はログインと同じく、連続した失敗 n 回に対し 2^(n-1) 秒（上限 15 分）の間は照合せずに 429 を返す**（決定・2026-09-11 をこの照合にも当てた）。**ログインの失敗とは別に数える**——同じに数えると、パスワードを忘れて何度か誤った利用者が、再設定まで待たされる
  - 失敗の理由（ID が無い・コードが違う・使用済み・退会済み）は区別せず 401（`invalid_credentials`）
- **再設定したら、その利用者のリフレッシュトークンをすべて失効させる**（OWASP Forgot Password Cheat Sheet「invalidate the sessions automatically」の側。**代償: 再設定した端末以外でも、ログインし直しになる。失効が止めるのは再発行だけであり、発行済みのアクセストークンは期限（15 分）まで使える**）
- 登録画面に「**コードを失うと復旧できない**」ことが明示される

> **リカバリーコードを紛失した場合、そのアカウントは復旧できない。** これは
> メール送信を持たない構成の帰結であり、**仕様として利用者に伝えないまま復旧不能にするのは
> 不誠実である**ため、登録画面に明示する。

### 1.2 ログイン / ログアウト（F-02）

| エンドポイント | 内容 |
|---|---|
| `POST /api/auth/login` | ユーザーID とパスワードで認証する |
| `POST /api/auth/refresh` | リフレッシュトークンから新しいアクセストークンを得る |
| `POST /api/auth/logout` | リフレッシュトークンを失効させる |

**受け入れ条件**

- 認証失敗時、「ユーザーID が存在しない」と「パスワードが違う」を**区別しない**
  （区別すると、どのユーザーID が登録済みかを外部から総当たりで調べられる）
- **退会済みのアカウントではログインできない**（照合に `deletedAt IS NULL` を含める）。
  下記 1.5 の受け入れ条件を、**照合の側で成立させる**。
  退会は論理削除であり、**素の照合は退会済みの行にそのまま当たる。DB は止めない**
- **登録時と違う大文字小文字を打ってもログインできる**（上記 1.1 の決定）。
  **一意索引が担保するのは「共存できないこと」だけで、照合が当たることは担保しない。**
  素の等値比較で実装すると索引はそのまま通り、症状は上の「区別しない」方針により
  **理由の分からないログイン失敗**になる。照合は `lower()` で引くこと。
  **これは Prisma のクライアントの等値比較では満たせない**（`schema.prisma` の
  `loginId` に理由を記した。`$queryRaw` で書く）
- ログイン試行にレート制限がかかる（**発信元の判定は ALB が CloudFront からのみ到達可能であることが前提**。[技術スタック](tech-stack.md) の ALB の行。発信元単位・アカウント単位）
  - 発信元単位は 15 分に 20 回（数値は慣行）
  - **アカウント単位は、連続して失敗した回数 n に対し 2^(n-1) 秒（上限 15 分）の間、照合せずに 429 を返す**（決定・2026-09-11・依頼側。OWASP Authentication Cheat Sheet の「失敗のたびに倍にする」形）。ユーザーID は大文字小文字を区別せず、**存在しない ID も同じに数える**。成功で数え直し、**最後の失敗から 24 時間で数え直す**（数値は慣行）
  - **採らなかった形: 一定回数でアカウントを締め出す**（NIST SP 800-63B-4 は連続した失敗を 100 回以下に抑えることを求める）。他人がパスワードを誤り続けるだけで本人を締め出せるため。**代償: 上限に達した後も 15 分に1回（1日およそ 96 回）は試せる。他人が失敗を送り続けると、本人も最大 15 分待たされる**
  - 回数は Valkey に置いてタスクをまたいで数え、**Valkey が止まっている間は各タスクのメモリで数える**（1.1 と同じ決定）。**代償: 切り替えの時点で回数は数え直しになり、止まっている間は同じ待ち時間に照合へ進める回数がタスク数まで増える**
- リフレッシュのたびにトークンがローテーションされる
  - 入れ替え済み（失効済み）のトークンが出されたら、盗まれたものとみなして**そのログインの系列のトークンをすべて失効させる**（RFC 9700 4.14.2）。同じトークンで同時にリフレッシュされた場合も、入れ替えに成功するのは1つだけで、後の側は再利用として扱う。**代償: 通信の再送などで正規の利用者が同じトークンを2回送ると、ログインし直しになる**
  - リフレッシュトークンの期限（14 日）は入れ替えのたびに延びる。**代償: 使い続ける限り、系列に上限の期限は無い**（再ログインを求めない）
  - 使えないトークン（無い・知らない・失効済み・期限切れ・退会済み）は区別せず 401（`invalid_token`）とし、Cookie を消す
- ログアウト後、リフレッシュトークンが再利用できない
- **リフレッシュトークンの Cookie が `HttpOnly; Secure; SameSite=Strict; Path=/api/auth` である**
  - 有効期間はアクセストークン 15 分・リフレッシュトークン 14 日（Cookie の `Max-Age` も 14 日）。どちらも数値は慣行（RFC 9700・OWASP に数値の推奨は無い）
- **`/api/auth/refresh` と `/api/auth/logout` は、カスタムリクエストヘッダーが無いリクエストを拒否する**
- **`Origin` / `Sec-Fetch-Site` が許可されたものでない場合、上記2つのエンドポイントが拒否する**

> **Cookie を使うのはこの2つのエンドポイントだけである。** 他の API はすべて
> `Authorization` ヘッダーで認証するため、ブラウザが認証情報を自動送信せず、CSRF が成立しない。
> **専用の CSRF トークン機構を持たない判断とその代償**は
> [要件定義書](requirements.md) 4.3 に記す。

### 1.3 プロフィール設定（F-04）

- 表示: アバター画像 / 表示名 / ユーザーID / ステータス（絵文字＋テキスト）
- 編集: アバター画像 / 表示名 / ステータス
- **ユーザーID は変更できない**（メンションの参照先が壊れるため）

**受け入れ条件**

- **アバター画像は、11.1 の添付と同じ段を通る**（決定・2026-09-11・依頼側。#227）——**ブラウザから S3 の隔離用のキーへ署名付き URL で直接 PUT し、サーバーが検証してから、検証した版に固定して配信用のキーへコピーする。サーバーは multipart を受けない。**
  **11.1 の受け入れ条件とテストの行（配信のヘッダーを含む）は、次の読み替えだけをして、アバターにそのまま当たる**——形式の許可リストは画像だけ（F-28）、参加者判定（発行時と、確定時のやり直し）は本人のプロフィールであることの確認（下の箇条）、キーの形式は下の箇条のもの、**配信（配信 URL の組み立て・署名付き Cookie の対象と発行する範囲・ビヘイビア）は下の配信の箇条のもの**。
  **確定で落ちたときに返すのは、本人に払い出されていない識別子への 404 だけである**（3.1 の2段階のコードは、チャンネルを持たないアバターには当たらない）
- **アバターのキーは、すべてサーバーが組み立てる**——隔離用のキーは `quarantine/avatars/{uid}/{UUID}/{ファイル名}`、配信用のキーは `avatars/{uid}/{UUID}/{ファイル名}`
  （`{uid}` は認証した本人の `User.id`（主キー。ログイン ID の `userId` ではない。差し替えで残った古いオブジェクトも、その利用者のものとして選べるようにする。[要件定義書](requirements.md) 6.2）、`{UUID}` はサーバーが発行する推測できない値、`{ファイル名}` は 11.1 と同じく許可リストで置換した値であり、配信用のキーでは、その拡張子を確定の段で検証した形式のものに付け替える）
- **アップロード用の署名付き URL の発行と確定を求められるのは、本人のプロフィールについてだけである**——他の利用者のアバターを差し替えられない。
  **確定で `avatarUrl` に入れるのは、サーバーが組み立てた配信 URL のパス（`/avatars/{uid}/{UUID}/{ファイル名}`）だけであり、利用者が渡した URL を入れない**
- **配信は CloudFront の `/avatars/*` のビヘイビアを通し、署名付き Cookie を要求する**——Cookie の対象は `/avatars/*`、`Path` 属性は `/avatars` であり、
  **ログインしている利用者に発行する**（ワークスペースやチャンネルの参加を問わない。アバターはどの画面にも出るため）。**`/avatars/*` はパスを剥がさずに渡す**（キーが `avatars/` で始まるため、剥がす関数は要らない。**オリジンへは正規化の前のパスが渡り、`avatars/` の外のキーに届かないかは未確認である**。[要件定義書](requirements.md) 4.3）
- **上記を検証する自動テストが存在する**——11.1 のテストの行を上の読み替えでアバターに当てたもの（確定で、本人に払い出されていない識別子に 404 を返すことを含む）、ログインしていない利用者が `/avatars/*` を取得できないこと、`avatarUrl` に利用者が渡した URL が入らないこと、`/avatars/*` の URL から `avatars/` の外のキー（添付の `workspace/...` と `quarantine/` を含む）を、[要件定義書](requirements.md) 4.3 の「確かめる URL の形」の URL でも取得できないこと
- ステータスは絵文字1つとテキスト（最大100文字）で構成される
- 表示名は1〜50文字で、空白だけは不可（1.1 と同じ。決定・2026-09-11・依頼側）

> **アバターの配信の代償**（決定・2026-09-11・依頼側。#227）。**配信 URL を知っていれば、ログインしている別のワークスペースの利用者でも取得できる**——署名付き Cookie の範囲を「ログインしている利用者」にしたためである。キーに推測できない `{UUID}` を入れる。**配信 URL には `{uid}` が載るため、URL を知る人には利用者の `User.id` と、UUIDv7 の先頭の時刻が分かる。**
> **ログアウト・退会の後も、発行済みの Cookie は期限まで有効である。**
> **アバターを差し替えても、古い配信用のオブジェクトは残る**（キーの `{uid}` で、その利用者のものとして選べる。配信用の接頭辞にはライフサイクルを置かない。[要件定義書](requirements.md) 4.2 の孤児オブジェクトと同じ代償）

**判断が必要な点（実装時に決める）**

- **ステータスの「絵文字1つ」の数え方と、絵文字とテキストを片方だけ設定できるか**（#283。#276 は Unicode の RGI_Emoji に当たる列1つ・それぞれ単独で設定でき null で消える形で実装した。**依頼側の判断を経ていない**）
- **`/avatars` の署名付き Cookie の有効期限と、発行・再発行の契機**（ログイン・トークンのリフレッシュ）
- **`/avatars/*` からオリジンへ渡る正規化の前のパスで、`avatars/` の外のキーに届かないことを、[要件定義書](requirements.md) 4.3 の「確かめる URL の形」の URL で実際に配信して確かめる**（[要件定義書](requirements.md) 4.3。**文書からは決まらなかった**）

### 1.4 サーバー側の認可検証（F-05）

**この機能は画面を持たない。** すべての API と WebSocket イベントに適用する横断的な仕組みである。

**受け入れ条件**

- **フロントエンドを経由せず API を直接呼んでも、権限のない操作は拒否される**
- 「自分のメッセージのみ編集・削除できる」がサーバー側で検証される
- 「オーナーのみが招待・キック・チャンネル操作を行える」がサーバー側で検証される
- 権限のない操作は 403 を返す。**404 と使い分ける**
  （存在を隠すべきプライベートチャンネルは 404、権限不足は 403）
- **404 の応答の本体が、存在を漏らさない。**
  `{ "message": "権限がありません" }` は**「そのチャンネルは存在する」と述べている。**
  **本文は「見つかりません」で揃える**（ステータスコードだけでは存在を隠せない）。
  **揃えるのは横断的な例外処理であり、各ハンドラは個別に文言を書かない**——
  **404 を返す受け入れ条件はこの文書の複数の節にあり、1箇所でも個別に書けば規則が破れる**
- **上記を検証する自動テストが存在する**——**404 の応答の本体が、存在を認める文言に
  なっていないこと。** **横断的な例外処理で揃える設計を採った以上、1箇所を個別の文言で
  上書きしても CI は緑のまま通る。** それを落とすテストが要る
- **可視性を判定する問い合わせは、要求する側（トークンの持ち主）自身が
  退会していないことも条件に含める。** `Membership` が残っていても、
  要求する側が退会済みなら通さない（**派生**。#57。理由と現状はこの節の但し書きに記す）
- **トークンから利用者を解決する時点で、その利用者が退会していないことを確かめる。**
  **退会済みのトークンは、読み取り・書き込みを問わず、すべての API と
  WebSocket イベントで拒否する**（**派生**。#90）。
  **API は 401 を返し、応答は無効なトークンと同じにする**（RFC 6750 の `invalid_token`。
  退会済みであることを応答から区別させない）。WebSocket はハンドシェイクで断る（5.2）。
  理由はこの節の但し書き（決定・現状の2段目）に記す
- **上記の入口の判定を検証する自動テストが存在する**——退会済みのトークンで、読み取りと書き込みの両方が拒否されること
- 入口の判定は**すべてのルートに既定で掛け、認証を要さないルートだけを明示して外す**（**派生**。#276。REST の仕様の `security: []` と一致させる）。
  **これが無いと、判定を付け忘れたルートで、この節の「フロントエンドを経由せず API を直接呼んでも、権限のない操作は拒否される」と、退会済みのトークンをすべての API で拒否することが成立しない。**
  トークンが無い要求は 401（`authentication_required`。`WWW-Authenticate: Bearer`）、使えないトークンは 401（`invalid_token`。`WWW-Authenticate: Bearer error="invalid_token"`。RFC 6750 3.1）。
  **仕様の形の検証（400）はトークンの確認より先に行う。代償: トークンを持たない要求にも、入力が仕様の形に合わないことが 400 で分かる**（送った値は応答に載せない。仕様で書けない検証はトークンの確認の後に行う）
- **メンバーがオーナー専用の操作（招待・キック・チャンネルの追加削除）を実行できないことを
  検証する自動テストが存在する**（[要件定義書](requirements.md) 4.8「必ずテストを書く箇所」の7）

> **退会済みの利用者自身が中身を読める経路を塞ぐ**（**派生**。#57）。
>
> 1.5 は `Membership` / `ChannelMember` の消し込みと、参加者一覧などの問い合わせに
> `User."deletedAt" IS NULL` を足すことで、**退会した利用者が参加者一覧に
> 居座ることを塞いだ。** しかしこれは「退会した利用者**について**」の可視性判定であり、
> 「退会した利用者**自身**がトークンを提示してきた場合」を判定しない。
> **後者を塞がない限り、退会した利用者は自分が参加していたプライベートチャンネルを
> そのまま読み続けられる。**
>
> **判定基準は「これが無いと、どの要求が成立しないか答えられるか」**
> （[要件定義書](requirements.md) 3.0）。答えられる:
> **アカウントの削除（F-36）が、実質「新しくログインできないだけ」に縮む**——
> 1.5 の受け入れ条件は「**削除後、そのアカウントでログインできない**」であり、
> **発行済みのアクセストークンには及ばない。**
>
> **決定・現状（1段目）: 可視性を判定する個々の問い合わせに、要求する側の `deletedAt IS NULL` を含める。**
> [prisma-schema.test.ts](../apps/api/src/prisma-schema.test.ts) の参照実装
> （`visibleChannels` / `channelMemberViewers` / `manageableChannels` / `channelMemberList` /
> `workspaceMemberList` / `mentionTargetByLoginId`）は、いずれも要求する側の所属
> （`Membership` または `ChannelMember`）の結合に
> `JOIN "User" viewer ON viewer."id" = ... AND viewer."deletedAt" IS NULL` を持つ
> （コメント「要求する側が退会していないこと」）。
> **API を実装する際は、この形（要求する側の `deletedAt` を条件に含める）を踏襲すること。**
> 個々の問い合わせに書く方式であるため、**新しい可視性の問い合わせを足すたびに、
> 同じ条件を書き忘れないこと。**
>
> **決定・現状（2段目）: トークンから利用者を解決する入口でも、退会済みを落とす**（#90）。
> **問い合わせ側の条件だけでは書き込み経路が塞がらない**——1.5 の**リフレッシュトークンの失効が止めるのは再発行だけ**であり、
> **失効前のアクセストークンで、メッセージ投稿・リアクション・招待の承諾を通せる。**
> 1.5 の受け入れ条件「**削除後、そのアカウントでログインできない**」が塞ぐのは新しいログインだけである。
> **2段構えにし、どちらか一方に寄せない**——入口の判定だけに寄せると、入口が API・ハンドシェイク・
> イベントの1件ごとに分かれているため、1箇所の実装漏れで読み取りが開く。問い合わせ側の条件だけに寄せると、書き込みが通る
>
> **例外は1つだけである**——**自身では認可を判定しない問い合わせ**。
> 9.1 の経路2（`mentionDisplayTarget`。表示時の参照先解決）がそれで、
> **呼ぶ側が「そのメッセージを読んでよいか」を先に決めており、読んでよいメッセージの本文に
> 現れる参照先だけを引く。** この決定が掛かるのは「**可視性を判定する**問い合わせ」であって、
> それ以外ではない。**「要求する側の条件は無くてよい」という前例として写さないこと**——
> 経路2 は単独の API として公開してはならない、という条件とセットである。
>
> **合わせて記録する。** 退会時に、その利用者が発行済みの**リフレッシュトークンを失効させる**
> 必要がある。「削除後、そのアカウントでログインできない」（1.5）が塞ぐのは**新しいログインだけ**
> であり、既存のリフレッシュトークン・アクセストークンはこれだけでは失効しない。
> 受け入れ条件は 1.5 に記す（トークンのテーブル自体は本書の現時点の範囲外であり、
> 条件の記録に留める）。

### 1.5 アカウントの削除（F-36）

設定画面から、利用者が自分のアカウントを削除できる。

| 項目 | 決定 |
|---|---|
| 実行できる人 | **本人のみ** |
| 確認 | **パスワードの再入力**を求める |
| 過去のメッセージ | **残す。** 削除すると会話の文脈が壊れるため（キック時と同じ扱い） |
| 表示名 | 削除済みの利用者として表示する（メンションの参照先も同様） |
| アバター画像 | **表示しない**（表示名と同じく、削除済みの利用者として表示する）。**S3 のオブジェクトは残る**（論理削除のみ。[要件定義書](requirements.md) 6.2） |
| ユーザーID | **再利用させない。** 過去のメンションが別人を指すことを防ぐ |
| オーナーの場合 | **ワークスペースにオーナーが不在になるため、削除できない。** オーナー権限の委譲を対象外としているため（[要件定義書](requirements.md) 3.4） |
| リカバリーコード | **削除と同一トランザクションで、未使用のコードを使用済みにする**（下記） |
| ワークスペース参加 / チャンネル参加 | **削除と同一トランザクションで `Membership` を消す**（**派生**。下記）。`ChannelMember` は外部キーで連鎖して消える |

> **`Membership` / `ChannelMember` も、退会しても自動では消えない**（**派生**。2026-09-05）。
> リカバリーコードとまったく同じ理由である。どちらも `ON DELETE CASCADE` で
> `User` を参照しているが、**退会は論理削除で `User` の行が残るため発火しない。**
>
> **区分は「派生」である**（[CLAUDE.md](../CLAUDE.md) 1）。
> これが無いと、**退会がキックより弱くなる。** 2.2 は、キックされた利用者について
> 「**所属していた全チャンネルから自動的に外れる**」「そのワークスペースのデータに
> 一切アクセスできなくなる」と定めている。より強い操作である退会だけが
> 参加を残すと、**退会した利用者が参加者一覧と配信の対象に残り続ける。**
>
> `Membership` を消せば `ChannelMember` は連鎖して消える。**これは DB が担保する**
> （`ChannelMember` の `(workspaceId, userId)` が `Membership` を参照する複合外部キー。
> 「ワークスペースからキックすると、チャンネル参加も消える」テストが同じ経路を見ている）。
>
> **代償**（[CLAUDE.md](../CLAUDE.md) 4）**: 退会後に「誰がいたか」を追えない。**
> `Membership` / `ChannelMember` を物理削除とした既存の代償（下記 2.2）と同じものが、
> 退会にも及ぶ。残す側を採れば追えるが、**退会した利用者と現役の利用者を
> 参加者一覧で区別する条件が、可視性を判定するすべての箇所に増える。**
> 1箇所でも書き漏らせば、退会した利用者が参加しているように見え続ける。

> **未使用のリカバリーコードは、退会しても自動では消えない。**
> 退会は論理削除であり `User` の行が残るため、`ON DELETE CASCADE` は働かない。
> 何もしなければ、**退会済みのアカウントのパスワードをリカバリーコードで再設定できる。**
> 上の「削除後、そのアカウントでログインできない」だけでは、**この経路は塞がらない。**
> 復旧はログインではないためである。
>
> **DB はこれを止めない。** 部分一意索引 `RecoveryCode_single_unused_per_user` が
> 見るのは `usedAt` だけで、`User.deletedAt` は見ない。
> **塞ぎ方は2段構えにする。列の追加は要らない。**
>
> 1. **書き込み側**: 削除の処理が、未使用のコードを同一トランザクションで使用済みにする
> 2. **読み取り側**: 復旧・ログイン・招待の照合に `deletedAt IS NULL` を含める
>    （上記 1.1 / 1.2、下記 2.2）
>
> **1 だけでは足りない。** 退会処理が1件でもコードを取りこぼした時点で、
> 退会済みアカウントの `passwordHash` を書き換えられる。
> 「経路が複数あり、1箇所でも書き漏らせばそのまま通る」は復旧にも当てはまる。
> **メンション（9.1）は経路ごとに違う。9.1 の書き分けに従うこと**
> （投稿時の宛先解決 `mentionTargetByLoginId` を表示時の参照先解決に転用しない）。
>
> **代償**（[CLAUDE.md](../CLAUDE.md) 4）**: `usedAt` が2つの意味を持つ。**
> 「使用した時刻」と「退会で無効化した時刻」が同じ列に入るため、
> **この列から「復旧が行われたか」は読み取れない。**
> `usedAt IS NOT NULL` を「復旧した」と読むと、**退会しただけの利用者が
> 「復旧した」ことになる。** 復旧の履歴が要るなら、別に記録が要る。

**受け入れ条件**

- 本人以外がアカウント削除 API を呼ぶと 403 が返る
- 削除後、そのアカウントでログインできない
- **削除後、リカバリーコードによるパスワード再設定もできない**
- **削除した利用者が、どのワークスペース・チャンネルの参加者一覧にも残らない。**
  **これも2段構えにする**（上の3経路と同じ理由）。
  書き込み側（退会処理が `Membership` を消す）だけだと、
  **退会処理が1件でも取りこぼした時点で参加者一覧に居座る。**
  **参加者一覧を返す問い合わせでも、`User."deletedAt" IS NULL` で除くこと**
- **削除した利用者の過去のメッセージが残り、会話が読める状態を保つ**
- ワークスペースのオーナーであるアカウントは削除できず、理由が画面に表示される
- **削除と同一トランザクションで、その利用者のリフレッシュトークンを失効させる**（**派生**。#57）。
  「削除後、そのアカウントでログインできない」（上記）が塞ぐのは**新しいログインだけ**であり、
  発行済みのリフレッシュトークン・アクセストークンはそれだけでは失効しない。
  **トークンのテーブルは本書の現時点の範囲外であり、条件の記録に留める**
- **削除の処理の中で、その利用者の WebSocket 接続を切る**（9.2。切断により全部の部屋から出る）。**トークンの失効だけでは、確立済みの接続は切れない**
  （認可の入口での判定は上記 1.4 を参照）

> **これは論理削除である。** 本文はデータベースに残り続ける（[要件定義書](requirements.md) 3.4 / 6.2）。
> **「削除した」という利用者の認識と、実際の保持状態が一致しない。**
> 実運用では、削除の求めに応じるための物理削除の仕組みが別途必要になる。

## 2. ワークスペースとメンバー管理

### 2.1 ワークスペース（F-06 / F-07）

- 誰でも作成できる。**作成者がオーナーになる**
- 1人の利用者が複数のワークスペースに所属できる
- サイドバーでワークスペースを切り替える

**受け入れ条件**

- ワークスペースを作成すると、作成者がオーナーとして所属した状態になる
- 所属していないワークスペースの情報は取得できない（404）
- **ワークスペースの参加者一覧は、退会済みの利用者を含まない**
  （`User."deletedAt" IS NULL` で除く。**派生**。#57。
  [prisma-schema.test.ts](../apps/api/src/prisma-schema.test.ts) の `workspaceMemberList` が
  参照実装）。**1.5 の受け入れ条件「削除した利用者が、どのワークスペース・チャンネルの
  参加者一覧にも残らない」が、チャンネル側と並んでワークスペース側にも当たる。**

### 2.2 招待とキック（F-08 / F-09）

| 操作 | 実行できる人 | 内容 |
|---|---|---|
| ワークスペースへの招待 | **オーナーのみ** | ユーザーID を指定。**招待された利用者が承諾して初めて参加する**（F-38） |
| **ワークスペースからの退出** | **メンバー本人** | 自分の意思で抜けられる（F-38）。**オーナーは退出できない** |
| ワークスペースからのキック | **オーナーのみ** | **所属していた全チャンネルから自動的に外れる** |
| チャンネルからのキック | **オーナーのみ** | そのチャンネルのみから外す |
| プライベートチャンネルへの招待 | **そのチャンネルの参加者なら誰でも** | 招待先は同一ワークスペースのメンバーに限る |

**受け入れ条件**

- メンバーがワークスペースへの招待・キック API を呼ぶと 403 が返る
- **招待の宛先ユーザーID が、大文字小文字を区別せずに解決される**
  （上記 1.1 の決定。照合は `lower("userId")` で引く。
  **Prisma のクライアントの等値比較では満たせない**ため `$queryRaw` で書く）。
  解決できないと「そのユーザーID の利用者はいない」になり、
  **招待した側は綴りを間違えたことに気づけない**（表示上ほぼ見分けがつかないことが、
  1.1 が大文字小文字を区別しないと決めた理由そのものである）
- **退会済みの利用者は、招待の宛先として解決されない**（照合に `deletedAt IS NULL` を含める）。
  退会は論理削除で `User` の行が残るため、**`lower("userId")` の照合はそのまま当たる。**
  **DB は止めない**（参照先の行は実在するので外部キーも通る）。塞がないと、
  退会済みの利用者を招待し直せて `Membership` が復活し、上記 1.5 の
  「**削除した利用者が、どのワークスペース・チャンネルの参加者一覧にも残らない**」が
  その場で破れる。しかもその利用者は**ログインできない**ため、
  **誰も使えないメンバーが一覧に居座る。**
  同じ経路の復旧（1.1）は「未使用のコードを同一トランザクションで無効化する」で
  塞いである。**招待だけがこの扱いから漏れていた。**
  **メンション（9.1）は経路ごとに違う。9.1 の書き分けに従うこと。**
- キックされた利用者の**過去のメッセージは残る**
- キックされた利用者は、そのワークスペースのデータに一切アクセスできなくなる
- **参加資格を失ったとき（ワークスペース・チャンネルからのキック、退出）は、その処理の中で、その利用者の接続を該当するチャンネルの部屋から外し、その利用者の接続が入っていた部屋にだけ在席の変化（`presence:changed`）を配る**（入っていなかった部屋へは配らない。配る条件は 9.2 の「在席の変化は利用者単位で配る」）——
  ワークスペースから外れたときは、そのワークスペースの全チャンネルの部屋から外す（9.2「部屋（Socket.IO の room）」）。
  **外さないと、確立済みの接続が部屋への配信を受け続ける**——1.4 の1件ごとの拒否は送信側の判定であり、部屋への配信は受信側を判定しない
- **上記を検証する自動テストが存在する**——キック・退出した利用者の接続が、そのチャンネルの配信を受け続けないこと、他の参加者の一覧で在席のまま残らないこと
- プライベートチャンネルへの招待で、ワークスペース外の利用者は指定できない

#### 招待の承諾と退出（F-38）

**承諾フローを設けない場合、利用者は知らないワークスペースに勝手に追加される。**
退出の導線も無ければ、**「追加される一方で、抜けられない」**状態になる。この2つは同じ問題の
表と裏であるため、まとめて F-38 とする。

| 状態 | 内容 |
|---|---|
| 招待済み（未承諾） | 招待された側に通知が出る。**この時点ではワークスペースに所属していない** |
| 承諾 | 参加が成立する。パブリックチャンネルの一覧が見えるようになる |
| 辞退 | 招待が消える。**オーナーは再度招待できる** |
| 退出 | **所属していた全チャンネルから外れる。** 過去のメッセージは残る（キックと同じ扱い） |

**受け入れ条件**

- **承諾していない招待の段階では、ワークスペースのデータを一切取得できない**（404）
- 退出したあと、そのワークスペースのデータにアクセスできない（**確立済みの WebSocket 接続も、そのワークスペースの全チャンネルの部屋から外す**。2.2 の受け入れ条件）
- **退出した利用者の過去のメッセージは残る**
- **オーナーが退出しようとすると拒否され、理由が画面に表示される**

> **オーナーが退出できないのは、オーナー権限の委譲とワークスペースの削除を対象外にしている
> ためである**（[要件定義書](requirements.md) 3.4）。**その結果、ワークスペースを作った利用者は
> そこから抜けられない。** 実運用に移す場合は、権限の委譲かワークスペースの削除が必要になる。

> **参加の記録は物理削除である。その代償を記録する**（[CLAUDE.md](../CLAUDE.md) 4）。
> 退出・キック・チャンネルからの離脱は、参加の記録を**消す**。論理削除にしない。
> **その結果、「いつ誰が抜けたか」は後から追えない。**
> メッセージ（3.4 で論理削除と決めている）とは扱いが違う。
>
> 論理削除にすれば追えるが、**可視性を判定するすべての箇所に「抜けていないこと」の
> 条件が増える。1箇所でも書き漏らすと、抜けた利用者にデータが見え続ける。**
> 追跡できることより、判定を単純に保つことを採った。
> 監査の記録が要る運用に移す場合は、参加の履歴を別に持つ必要がある。

## 3. チャンネル

### 3.1 チャンネル作成（F-10）

| 種別 | 見え方 |
|---|---|
| **パブリック** | ワークスペースのメンバーなら誰でも一覧に見え、**自由に参加・退出できる**（退出したら、その利用者の接続をチャンネルの部屋から外す。2.2 の受け入れ条件） |
| **プライベート** | 参加者だけに見える。**一覧にも検索にも出ない**（**オーナーの管理用一覧を除く。**下記の但し書き。会話の中身は返さない） |

- **作成・アーカイブはオーナーのみ**（課題文の権限要件）

**受け入れ条件**

- メンバーがチャンネル作成・アーカイブ API を呼ぶと 403 が返る
- **チャンネル名の長さは、アーカイブ時の接尾辞 `-<採番>` を付けても収まる範囲に制限する。**
  制限しないと、**INSERT は通るのにアーカイブだけが失敗する名前**が作れてしまい、
  改名の機能が無いため**そのチャンネルは永久にアーカイブできない**（F-35 は Must）。
  **数値の上限はまだ定めていない。定めるには提案と承認が要る**
  （[CLAUDE.md](../CLAUDE.md) 1）。事実上の上限については下記の但し書き
- **非参加者がプライベートチャンネルを取得しようとすると 404 が返る**（403 ではない。存在を隠す）。
  **ここでいう「取得」は、会話（メッセージ）を含む取得を指す。**
  **オーナーはこの 404 の対象から外れるが、返るのは管理用の範囲だけである**
  （`id` / 名前 / 種別 / 参加者数と参加者一覧。**メッセージ・添付ファイル・未読数・在席は返らない**。
  下記の但し書きの表と同じ）。**オーナーがメッセージを取得しようとすれば、
  参加していない以上 404 である**（次の行）
- プライベートチャンネルはチャンネル一覧 API のレスポンスに含まれない。
  **ただしオーナーには、管理のための一覧を返す**（下記の但し書き）
- **オーナーであっても、参加していないプライベートチャンネルのメッセージ・添付ファイル・未読数・在席は取得できない**
  ——**未読数は管理用の一覧（F-09）と同じレスポンスに乗せやすい。** 乗せても他の受け入れ条件は1つも壊れない
- **オーナーがそれら（メッセージ・添付ファイル・未読数・在席）を取得できないことを検証する自動テストが存在する**
  （[要件定義書](requirements.md) 4.8「必ずテストを書く箇所」の8）
- **参加者は、自分が参加しているチャンネルの参加者一覧を取得できる**（**在席は含めない**——参加者が求めた場合も、オーナーが求めた場合も。在席は 9.2 の部屋の側の経路だけで渡す）
- **パブリックチャンネルでも、参加していないメンバーは参加者一覧を取得できない**
  （下記の但し書き）。このとき返すのは **403** である。
  **パブリックチャンネルは一覧に出ており、存在を隠す対象ではない**（上記の凡例）
- **プライベートチャンネルの参加者一覧を、非参加者（オーナーを除く）が求めると 404 が返る**
- **コードは2段階で決まる。種別だけでは決まらない。**
  1. **そのワークスペースに所属していなければ、種別によらず 404**（上記 2.1
     「所属していないワークスペースの情報は取得できない」）。
     **ここを種別で分けると、ワークスペースの外の利用者に
     パブリックチャンネルの存在と `channelId` が有効であることが 403 として漏れる**
  2. 所属している場合にかぎり、**パブリックは 403 / プライベートは 404**
  
  プライベートを 403 に寄せると**存在が漏れ**、パブリックを 404 に寄せると
  **一覧に見えているチャンネルが「無い」と返る**
- **上記の2段階のコードを検証する自動テストが存在する**——所属していないワークスペース（404）・所属していてプライベートを非参加者（オーナーを除く）が求めた場合（404）・所属していてパブリック（403）の3つを分けて確かめる。
  **2段階を平坦な 404 として実装すると、パブリックの場合だけが落ちる**（分岐は片側だけ実装しても、片側だけを見るテストでは緑になる）
- **オーナーは、参加していないプライベートチャンネルの参加者一覧も取得できる**
  （**オーナーは例外の側であって、条件そのものではない。**
  オーナーだけが取得できる形にすると、参加者本人が自分のチャンネルの
  参加者一覧を取得できなくなる）

> **参加者一覧だけを見せる理由。** オーナーはチャンネルからのキック権限を持つが、
> **誰がいるか見えなければキックすべき相手を特定できず、課題文が求める管理者権限が機能しない。**
> 一方でメッセージまで見せると「プライベート」が名目だけになる。
> **境界は「人の出入りの管理」と「会話の閲覧」の間に引く**（[要件定義書](requirements.md) 3.5.1）。

> **チャンネル名の長さには、数値の上限を定めていない。**
> **しかし「上限が無い」わけではない。** 名前は一意索引
> `Channel_workspaceId_name_key`（B-tree）に載っており、
> **索引タプルには約 2704 バイトの上限がある。** 超える名前の作成は
> `index row size ... exceeds` で落ちる。**アプリ側の検証を通り抜けた入力が、
> 400 ではなく 500 になる。**
>
> **この事実上の上限は文字数では表せない。** 索引タプルの値は圧縮されるため、
> **同じ文字数でも中身によって通ったり落ちたりする**（実測: 同じ 6000 文字でも
> `x` の繰り返しは通り、乱数の16進文字列は落ちる）。
>
> **さらに、アーカイブ時の接尾辞 `-<採番>` の分を見込む必要がある。**
> 見込まないと、**作成は通るのにアーカイブだけが失敗する名前**が生まれ、
> 改名の機能が無いため**そのチャンネルは永久にアーカイブできない**（F-35 は Must）。
>
> **数値の上限を定めるなら、提案して承認を得てここに書くこと**
> （[CLAUDE.md](../CLAUDE.md) 1）。書いたうえで、列に `@db.VarChar(n)` を置く。
> 事実と帰結は [テスト](../apps/api/src/prisma-schema.test.ts) が固定している。

> **パブリックチャンネルの参加者一覧も、参加者とオーナーに限る**
> （**区分は保留**。2026-09-05 に暫定で閉じた）。
> **これは「決まっていなかったこと」を閉じる側に倒した記録であり、新しい機能ではない。**
>
> **区分を「派生」とは書けない**（[CLAUDE.md](../CLAUDE.md) 1）。
> 判定基準は「これが無いと、どの要求が成立しないか答えられるか」であり、
> **答えられない。** 参加してから見れば済むため、閉じても開けても要求は成立する。
> かといって**開ける側は機能を1つ増やすため「提案・承認済」とも書けない**
> （承認を得ていないものをそう書かない）。
> **よって区分は付けず、「暫定で閉じている」ことが分かる形で残す。**
> **決めるのは人間である。** 開けると決めたらこの但し書きを書き換え、
> 承認の日付を入れて「提案・承認済」とすること。
>
> 判定は `visibility` を見ない。パブリックであっても、参加していないメンバーは
> 参加者一覧を取得できない。**閉じる側を既定にするのは、この場で開ける判断だけが
> 承認を経ずに確定してしまうのを避けるためである**（[CLAUDE.md](../CLAUDE.md) 1。
> 開ける側は機能を1つ増やすことになるため、提案して承認を得る手順が要る）。
>
> **代償: 参加する前に、そのチャンネルに誰がいるかを見られない。**
> パブリックチャンネルは「メンバーなら誰でも一覧に見え、自由に参加・退出できる」ため
> 実害は小さいが、**参加してからでないと分からない**という不便は残る。
>
> **緩めるなら、この行を書き換えて承認を得ること。** 緩めたときに気づけるよう、
> 「パブリックでも非参加者は取得できない」ことをテストで固定してある
> （固定していないと、条件を緩めても1件も落ちない）。

> **オーナーには、管理のためのチャンネル一覧を返す**（**派生**。2026-09-05 決定）。
>
> **区分は「派生」である**（[CLAUDE.md](../CLAUDE.md) 1）。
> 判定基準に答えられる。**これが無いと F-09 が成立しない。**
> オーナーは「参加していないプライベートチャンネルの参加者一覧を取得できる」
> 権限を持つ（[要件定義書](requirements.md) 3.5.1）。しかし一覧にも出さず、
> 取得も 404 にすると、**オーナーはそのチャンネルの `id` を知る手段を持たない。**
> **権限はあるが、行使する経路が1つも無い**状態になる。
>
> | 項目 | 決定 |
> |---|---|
> | 返すもの | チャンネルの **`id` / 名前 / 種別 / 参加者数**、および**参加者一覧** |
> | 返さないもの | **メッセージ・添付ファイル・未読数・在席。** 会話の中身は一切返さない |
> | 使える人 | **そのワークスペースのオーナーのみ** |
> | アーカイブ済み | **含める。** 含めないと**復元の経路が無くなる**（下記） |
>
> **アーカイブ済みのチャンネルも返すこと。** 一般の一覧（参加者向け）は
> `archivedAt IS NULL` で絞るが、**この管理用の一覧で同じ条件を写してはならない。**
> アーカイブすると一覧から外れる（下記 3.2）以上、絞ると**オーナーは
> アーカイブ済みチャンネルの `id` を知る手段を失い、「オーナーが復元できる」（F-35。Must）が
> 成立しなくなる。** これは上で塞いだのとまったく同じ失敗の形である。
>
> **代償**（[CLAUDE.md](../CLAUDE.md) 4）
>
> - **オーナーには、プライベートチャンネルの存在と名前が見える。**
>   参加者から見た「プライベート」は**会話の秘匿であって、存在の秘匿ではない**
> - 一般のチャンネル一覧（参加者向け）と、この管理用の一覧とで
>   **返すものが違う2つの経路ができる。** 片方だけ直すと食い違う
>
> **境界は変えていない。** 「人の出入りの管理」は見せ、「会話の閲覧」は見せない
> （上の但し書きと同じ線である）。

### 3.2 チャンネルのアーカイブと復元（F-35）

**削除ではなくアーカイブとする。** オーナーは参加していないプライベートチャンネルのメッセージを
閲覧できないため、削除を認めると **中身を一切知らないまま他人の会話をまるごと失わせる**
操作が成立してしまう。

| 項目 | 決定 |
|---|---|
| 実行できる人 | **オーナーのみ**（課題文の権限要件どおり） |
| アーカイブ後 | チャンネル一覧から外れる。**参加者は読めるが、投稿はできない** |
| 復元 | **オーナーが復元できる。** 復元すると投稿可能な状態に戻る |
| 物理削除 | **行わない**（[要件定義書](requirements.md) 3.4） |

**受け入れ条件**

- メンバーがアーカイブ・復元 API を呼ぶと 403 が返る
- **アーカイブされたチャンネルに投稿しようとすると拒否される**
- アーカイブされたチャンネルの**過去のメッセージは検索結果に出る**（参加者に限る）
- 復元後、投稿できる状態に戻る

> **課題文の「チャンネルの追加・削除」との関係。** 利用者から見た「チャンネルを消す」操作は
> アーカイブとして提供する。**要求は満たしつつ、取り返しのつく形にした**という位置づけである。

#### アーカイブ時に名前へ振り分け番号を付ける（**提案・承認済。2026-09-04**）

**F-35 の実現方式についての決定であり、新しい機能ではない。** よって機能番号は与えない。

アーカイブしたチャンネルが名前を抱えたままだと、**同じ名前で新しいチャンネルを作れない。**
`general` をアーカイブした組織は、二度と `general` を作れないことになる。

| 項目 | 決定 |
|---|---|
| 採番 | **アーカイブの時点で、システムが自動的に番号を付ける**（`general` → `general-1`） |
| 番号の付け方 | 作成時の名前（基底名）ごとに、**その名前がまだ空いている最小の番号**を採る |
| 復元したとき | **番号は外れない。** `general-1` のままである |
| **再びアーカイブするとき** | **採番も改名も行わない。** 既に持っている番号と名前のままアーカイブする |
| 実行の単位 | **アーカイブ・採番・改名は同一トランザクションで行う。** 片方だけ実行された状態を作らない |

> **「最大の番号 + 1」ではない理由。** チャンネル名に制限は設けていないため、
> **利用者が自分で `general-1` という名前のチャンネルを作れる。**
> その状態で `general` をアーカイブすると、最大 + 1 では 1 を選び、名前が衝突して
> **アーカイブそのものが失敗する。** 改名の機能は無いため、そのチャンネルは
> **永久にアーカイブできない**状態になる。F-35 は Must であり、これは受け入れられない。
>
> 同時に2つをアーカイブすると、両方が同じ番号を選ぶことがある。
> **一意制約違反を捕まえて番号を進め、やり直す。**
>
> **採番するのは、まだ番号を持たないチャンネルだけである。** 復元したチャンネルは番号を
> 持ったままなので、再びアーカイブするときに採番し直さない。し直すと、**自分自身が
> `general-1` を使っているため次は 2 になり、アーカイブと復元を繰り返すたびに
> 名前がずれ続ける。**

**受け入れ条件**

- アーカイブしたあと、**同じ名前で新しいチャンネルを作れる**
- 復元しても名前は元に戻らない
- **まだ採番されていないチャンネルについては、アーカイブだけ、採番だけ、改名だけ、
  のいずれも成立しない**（データベースが拒否する）
- **既に採番されているチャンネル（復元済み）の再アーカイブだけは、その例外である。**
  上の表のとおり採番も改名も行わないため、`archivedAt` だけを更新する。
  **データベースはこれを通す**（通さないと、上の「再びアーカイブするとき」が成立しない）
- **利用者が先に `general-1` を作っていても、`general` をアーカイブできる**

> **この判断の代償を記録する**（[CLAUDE.md](../CLAUDE.md) 4）。
>
> 1. **アーカイブを解除しても名前が元に戻らないため、利用者から見ると
>    「別のチャンネルになった」ように見える。** 復元は名前の復元ではない
> 2. **過去のメンションやリンク、外部に共有された参照が指す名前と、現在の名前がずれる。**
>    参照が ID で解決されていれば辿れるが、名前で書かれたものは辿れない
>
> 採らなかった側の代償も記す。**アーカイブ時に改名しない**方式では、
> チャンネル名の一意制約をアーカイブ済みのものだけ除外する形にせざるを得ず、
> **「一覧に出ないのに、その名前は使えない」**という説明のつかない状態が残る。

## 4. メッセージ

### 4.1 投稿と一覧（F-11 / F-12）

- 投稿: テキスト（最大4000文字）＋ 添付（F-27）
- 一覧: **カーソルページネーション**。上方向に遡って読み込む

**受け入れ条件**

- `OFFSET` を使わない。カーソル（メッセージID または時刻）で位置を指定する
- 過去メッセージを読み込んでも**スクロール位置が飛ばない**
- 参加していないチャンネルのメッセージは取得できない。**応答コードは 3.1 と同じ2段階で決まる**——所属していないワークスペースなら種別によらず 404、所属していればプライベートは 404 / パブリックは 403（404 の本体は 1.4 のとおり）
- **上記の応答コードを検証する自動テストが存在する**——**確かめる3つの場合は、3.1 の2段階のテストと同じである。** ただし**メッセージの取得にはオーナーの例外が及ばない**（オーナーも参加していないプライベートチャンネルでは 404。3.1）

### 4.2 編集と削除（F-13）

**受け入れ条件**

- 自分以外のメッセージを編集・削除しようとすると 403 が返る
- 編集したメッセージには「編集済み」が表示される
- 削除は**論理削除**。表示は「このメッセージは削除されました」に置き換わる
- **スレッドの親メッセージを削除しても、返信は保持される**
- 編集・削除は `message:updated` / `message:deleted` として他の利用者に即時配信される。**DM で起きるときの宛先と関門は 5.2 の DM の箇条による**
- **自分以外のメッセージを編集・削除できないことを検証する自動テストが存在する**
  （[要件定義書](requirements.md) 4.8「必ずテストを書く箇所」の6）

### 4.3 Markdown 対応と XSS 対策（F-14 / F-15）

対応する記法: 太字 / 斜体 / 取り消し線 / リンク / 引用 / 箇条書き / インラインコード / コードブロック

**受け入れ条件**

- **HTML 文字列を生成せず、要素を直接構築する方式で描画する**（`dangerouslySetInnerHTML` を使わない）
- 生の HTML タグを含む入力が、HTML として解釈されない
- **`javascript:` などの危険なスキームのリンクが無効化される**
- **上記を検証する自動テストが存在する**（[要件定義書](requirements.md) 4.8「必ずテストを書く箇所」の5）

## 5. リアルタイム配信（F-16）

**この章が動かないと、以降のほぼ全機能が「リロードしないと反映されない」状態になる。**

### 5.1 配信するイベント

**一覧は [要件定義書](requirements.md) 4.1「リアルタイム配信の対象イベント」にある。ここには置かない。**
**同じ表を2つ持つと、片方だけを直したときに食い違う**——
[CLAUDE.md](../CLAUDE.md) 3 がコードについて禁じているのと同じ形が、その根拠となる仕様の側で起きる。
実際に、寄せる前の2つの表は `message:new` の説明と注記が食い違っていた。

**この7種類以外の変化は即時反映されない。**

### 5.2 受け入れ条件

- **ハンドシェイクのパスは `/api/socket.io/` である**（Socket.IO の `path`。**決定**。#77）。
  **`/api` の外に出ると CloudFront の既定のビヘイビアに落ち、ALB に届かない**
  （[技術スタック](tech-stack.md) の CloudFront の行。**サーバー・クライアントの両方で設定する**）
- **接続確立時にトークンを検証する。** 無効なトークンでは接続できない
- **ハンドシェイクでトークンから利用者を解決する時点で、その利用者が退会していないことを確かめる**
  （1.4。#90）。**「無効なトークンでは接続できない」は退会済みを落とさない**——
  **アクセストークンは短命 JWT であり、失効前であれば署名も期限も有効である**
- **イベントの1件ごとの確認でも、送信元が退会していないことを見る。**
  **参加者であることだけを見ると、`Membership` の消し込みを取りこぼした場合に通る**
  （1.5 が復旧について「塞ぎ方は2段構えにする」としたのと同じく、書き込み側の規約だけに頼らない）
- **ハンドシェイクとイベントの1件ごとで退会済みを落とすことを検証する自動テストが存在する**
- **ハンドシェイク時に `Origin` を検証し、許可リストにないもの・`Origin` を持たないものを拒否する**
  - 許可リストは web の origin（環境変数 `WEB_ORIGIN`）の1つだけである（**派生**。#284）。web と api は同じ origin から配信する（#77）ため、正規のブラウザが送る `Origin` はこれ以外に無い。**これが無いと、上の「許可リストにないものを拒否する」の許可リストが決まらない**
  - **クライアントは WebSocket だけで繋ぐ**（**派生**。#284。`packages/shared` の `REALTIME_TRANSPORTS`）。ブラウザは同一 origin の GET に `Origin` を付けないため、socket.io-client の既定（polling のハンドシェイクから始める）では、上の「`Origin` を持たないものを拒否する」によってハンドシェイクが断られる。**代償: polling へのフォールバックが無く、WebSocket を通さない経路からは繋がらない**
- **認証情報を Cookie で渡さない**（ハンドシェイクの `auth` で渡す）
- **上記2点を検証する自動テストが存在する**（[要件定義書](requirements.md) 4.8「必ずテストを書く箇所」の4）——許可外の Origin から接続できないこと
- **チャンネル本体のイベントは、そのチャンネルの部屋へ送る**（下記 9.2「部屋（Socket.IO の room）」。**`unread:updated` は除く**——その宛先は `unread:updated` の箇条で定める）
- **メッセージが本人に届く必要があるとき——個人メンション・`@channel`・`@here`——は、
  `message:new` の宛先に対象の利用者の部屋を加え、チャンネルの部屋と合わせて1回で送る。**
  **Socket.IO は複数の部屋へ1回で送ると和集合をとり、両方に入っている接続にも1回だけ届ける**
  （公式文書 Rooms）——**そのチャンネルを開いている本人に2回届くことはない。**
  **チャンネルの部屋と利用者の部屋へ分けて2回送ってはならない**（本人に2回届き、一覧に同じメッセージが2行出る）。
  **個人メンション・`@channel` で本人の部屋を加えるのは、そのチャンネルを開いていない利用者にも届く必要があるためである**
  （9.1・10.2 のバッジとブラウザ通知。F-16 が派生である根拠そのものが「F-25 のブラウザ通知も実現できない」である）。
  **`@here` で加えるのは、取り直しに失敗したときに、そのタスクの一覧に載っている全員へ送るためである**（9.2「タスクをまたぐ在席」）——**一覧に載っていてもすでに部屋を出た利用者にも届け、開いていない利用者の側で弾いて通知を出さない**（10.2）。
  **一覧に載っていない在席者には、合わせて送るチャンネルの部屋の側で届く**——`@here` でもチャンネルの部屋へ送ることは省かない
- **DM で起きるイベントは、`unread:updated` を除き、すべて当事者2人の利用者の部屋へ1回で送る（`message:new` に限らない。`unread:updated` は下の箇条のとおり、持ち主の利用者の部屋へだけ送る）。DM はチャンネルの部屋を持たない**——
  **DM はチャンネルではない**（3.1 の種別はパブリックとプライベートの2つであり、DM は 8 で別立てである）。
  **Socket.IO の公式文書（Private messaging）の形である**——各接続を利用者の部屋に入れ、宛先と送信者の部屋へ送る（送信者の他のタブにも届く）
- **`unread:updated` は、その未読の持ち主の利用者の部屋へだけ送る（DM の未読でも、相手には送らない）**——未読はその利用者の値である（3.1 がオーナーにも渡さない対象としている）。未読は開いていないチャンネルと DM で発生する（10.1）
- **チャンネルのイベントを受け付けるたびに、送信元が該当チャンネルの参加者であることを確認する。** **送る部屋を決めるとき、利用者の部屋を宛先に加えるなら（経路によらない）、加える利用者がその値を受け取る資格を持つことを確認する**——チャンネルに属する値（個人メンション・`@channel`・`@here` の `message:new`、`unread:updated` など）は、そのチャンネルの参加者であること。DM に属する値（DM の `unread:updated` を含む）は、その DM の当事者であり、そのワークスペースのメンバーであること（下の箇条の確認）。**在席の一覧に載っていることを資格の根拠にしない**——一覧は古くなりうる（9.2「タスクをまたぐ在席」）。
  **チャンネルの部屋への配信では、受信側を判定しない**——受け取れるのは部屋に入っている接続であり、入室が関門である（9.2「部屋（Socket.IO の room）」。参加者でなくなった接続は 2.2 のとおり部屋から外す）。
  **DM では、イベントの送受信のたびに、送信元と宛先が当事者であり、ともにそのワークスペースのメンバーであること（`Membership` があり、退会していないこと）を確認する**——
  **DM はチャンネルの部屋への入室という関門を通らないため、送受信ごとの確認が関門である**（8「相手は同一ワークスペースのメンバーに限る」）。
  **ワークスペースからキック・退出した利用者には、この確認で DM が届かなくなる**（2.2「そのワークスペースのデータに一切アクセスできなくなる」）
- **非参加者に、プライベートチャンネルのイベントが配信されない**
- **非参加者をチャンネルの部屋に入れない**（9.2「部屋（Socket.IO の room）」。断り方も同じ箇所）
- **上記を検証する自動テストが存在する**（[要件定義書](requirements.md) 4.8「必ずテストを書く箇所」の3。
  **上の Origin の自動テストとは別項である**——あちらはハンドシェイク、こちらは配信先である）
- 通信が切れた場合、自動的に再接続する
- 再接続後、切断中に発生したメッセージが補完される。
  **ただしこの補完は「クライアントの再接続」が条件であり、Valkey の停止では発火しない**
  （切れるのはタスクと Valkey の間であり、**クライアントの接続は維持される**）。
  **停止中に他タスクで投稿されたメッセージは、利用者が読み込み直すまで欠けたまま残る**——
  [要件定義書](requirements.md) 4.2「フェイルオーバーを行わない」の代償（#162）
- **複数のサーバーインスタンスに分かれて接続していても、全員にイベントが届く**
  （**Valkey が動いている間**。停止中はタスク間の配信共有が止まる——上と同じ 4.2 の代償）
- イベント定義の型がフロントエンドとバックエンドで共有されている（2箇所に書かない）

> **WebSocket は同一オリジンポリシーの対象外であり、CORS でも守られない。**
> Socket.IO の `cors` オプションが効くのは HTTP long-polling のみである。
> 対策がなければ **Cross-Site WebSocket Hijacking（CSWSH）** が成立し、悪意あるサイトから
> 利用者のセッションで接続を確立される。**`allowRequest` による Origin 検証が必須である**
> （[要件定義書](requirements.md) 4.3）。

## 6. スレッド（F-17）

- 任意のメッセージに返信をぶら下げる。**1階層のみ**
- 親メッセージに「◯件の返信」と参加者のアバターを表示する

**受け入れ条件**

- スレッドの返信は、チャンネル本体の一覧に混ざって表示されない
- 返信件数がカウンタ列として保持され、一覧取得時に `COUNT` を発行しない
- **返信に対してさらにスレッドを作ることはできない**

## 8. ダイレクトメッセージ（F-19）

## 9. メンション

### 9.1 個人メンション（F-20）

- 入力欄で `@` を打つと候補が補完される
- **ユーザーID で解決する**（表示名は重複しうるため）。
  **解決は大文字小文字によらない**（上記 1.1 の決定）

**受け入れ条件**

- メンションされた利用者に F-24 のバッジと F-25 のブラウザ通知が届く。**宛先と関門は 5.2 の箇条（本人の部屋を加えて1回で送る箇条と、利用者の部屋を加えるときの資格の確認）による**
- **`@owner` と `@Owner` が同じ利用者に解決される。**
  一意索引が担保するのは「共存できないこと」だけであり、
  **素の等値比較で実装すると、メンションが誰にも当たらないまま静かに落ちる**
  （上記 1.1 の決定が「派生」である根拠のうち、F-20 側がこれである）。
  **これは Prisma のクライアントの等値比較では満たせない**（`schema.prisma` の
  `loginId` に理由を記した。`$queryRaw` で書く）
- **そのチャンネルに参加していない利用者はメンションできない**
- 補完候補に、そのチャンネルの参加者以外が出ない。
  **候補は、この節の経路1（投稿時の宛先解決）で宛先として解決できる利用者と一致させる**——
  対象側も要求する側も、そのチャンネルの参加者かつ `deletedAt IS NULL` である。
  経路1 と違うのは、`@` に続く文字列との照合が前方一致であることだけである（#90）。
  **候補に出たのに投稿で解決されない利用者を作らない。** 候補の提示は解決ではないため、
  「メンションの解決には2つの経路があり」の2つには数えない
- **メンションの解決には2つの経路があり、退会済みの扱いが逆になる。経路ごとに書き分けること**（#57）。

  1. **投稿時の宛先解決**（`@ユーザーID` から新しいメンションの対象を引く経路。
     「そのチャンネルに参加していない利用者はメンションできない」の判定もここで行う）。
     **そのチャンネルの参加者（`ChannelMember` が存在すること）に限る。**
     参照実装は [prisma-schema.test.ts](../apps/api/src/prisma-schema.test.ts) の
     `mentionTargetByLoginId` であり、`ChannelMember` を内部結合する。
     1.5 の決定（退会は削除と同一トランザクションで `Membership` を消し、
     `ChannelMember` は外部キーで連鎖して消える）により、**正しく退会した利用者は
     通常この結合に現れず、新しい宛先としては解決されない**（退会後に新しく `@` で
     指定することはできない）。**加えて、対象側にも `deletedAt IS NULL` を当てる**
     （決定・2026-09-10。#191）——**消し込みを取りこぼした場合の備えである。**
     取りこぼしても、退会済みが新しい宛先として解決されることはない。
     **足せるようになったのは、経路2（表示時の参照先解決）が別の問い合わせとして立ったためである**
     ——表示は経路2 が担うので、**足しても「退会した人へのメンションが本文から消える」は起きない。**
     **要求する側も同じく `deletedAt IS NULL` を条件に持つ**
     （この節の「**経路1の参照実装（`mentionTargetByLoginId`）は、要求する側の条件を持つ**」。
     根拠は 1.4 の決定である）
  2. **表示時の参照先解決**（既に投稿され、対象が確定しているメッセージ本文中のメンションを
     描画する経路）。**対象の `User."id"`（UUID。ログイン識別子である `loginId` の列名
     `userId` とは別物）から `User` の行を直接引き、`ChannelMember` の有無を
     条件にしない**（対象が現在そのチャンネルに参加しているかを問わない）。
     `User` の行は退会しても論理削除で残る（`deletedAt` が入るだけ）ため、
     この経路が 1.5 の「表示名は削除済みの利用者として表示する」を成立させる。
     参照実装は [prisma-schema.test.ts](../apps/api/src/prisma-schema.test.ts) の
     `mentionDisplayTarget` である（#78）。**`mentionTargetByLoginId` は経路1のものであり、
     経路2には使えない**——`ChannelMember` を内部結合するため、正しく退会した利用者は1件も返らない。
     **転用すると、退会した人へのメンションが本文から消えて見える。**
     `mentionDisplayTarget` は `deletedAt` で絞らず、**その有無を返す**——
     **示すこと自体は 1.5 の決定であり、呼ぶ側の裁量ではない。呼ぶ側が決めるのは文言だけである**
     （表示の文言は表示層の関心である）。**返した真偽値を無視して表示名だけを描くと、
     退会した利用者へのメンションが現役の利用者と見分けが付かなくなる。**
     **要求する側の条件を持たない。** 呼ぶ側が「そのメッセージを読んでよいか」を先に決めており、
     読んでよいメッセージの本文に現れる参照先だけを引く前提である。
     **単独の API として公開してはならない**——公開すると、UUID を1件ずつ試すことで
     利用者の存在と表示名を引ける（存在の探索。経路1 で塞いだものと同じ形）

  **経路1の参照実装（`mentionTargetByLoginId`）は、要求する側の条件を持つ**
  （**派生**。#82。これが無いと、非参加者が `@ユーザーID` を1件ずつ試して
  プライベートチャンネルの参加者を探れ、3.1 の隠蔽が成立しない）。
  兄弟の `channelMemberList` / `workspaceMemberList` と同じく引数に要求者
  （`viewerId`）を取り、**要求する側がそのチャンネルの参加者であること**
  （`ChannelMember` の結合）と、**要求する側の `deletedAt IS NULL`**（1.4 が可視性を
  判定する問い合わせに求める条件）の両方を SQL の条件に持つ。これを欠くと
  **非参加者が `@ユーザーID` を1件ずつ試すことで、そのプライベートチャンネルに
  誰が参加しているかを探れてしまう**（存在の探索。#78 に記録済み・#82 で対応済み）。
  **対象側の扱いは 2.1 と揃う**: 2.1 は対象側（一覧に載る利用者）を
  `deletedAt IS NULL` で除くが、経路1 も対象側（宛先）を `ChannelMember` の
  有無に加えて `deletedAt IS NULL` で絞る。

  **経路1 の対象側に `deletedAt IS NULL` を足す**（**決定・2026-09-10。#191**）。
  経路2 が別の問い合わせとして立った時点（#78・PR #190）で、**足しても「退会した人への
  メンションが本文から消える」は起きなくなっていた**——表示は経路2 が担うためである。
  残っていたのは「消し込みを取りこぼすと、退会済みが新しい宛先として解決されうる」
  という片側の穴だけであり、足すことに代償が無いと分かったため、対象側にも
  `deletedAt IS NULL` を足すことに決めた。

### 9.2 `@here` / `@channel`（F-21）と在席表示（F-22）

| 記法 | 通知先 |
|---|---|
| `@here` | そのチャンネルの**在席中の参加者** |
| `@channel` | そのチャンネルの**参加者全員** |

- **在席状態は、その利用者の接続が1本でもそのチャンネルの部屋に入っているかで判定する**（利用者単位の値）——**そのチャンネルを開いている
  ＝ここに来る話は見る**（決定・2026-09-09。#146）。
  **WebSocket の接続の有無では判定しない。** 接続はアプリ全体に対して1本であり、
  チャンネル単位ではない。**接続で判定すると `@here` は「アプリをどこかのタブで
  開いている参加者」を指し、`@channel`（参加者全員）との差が
  「アプリを開いているか」だけになる**
- メンバー一覧に在席を表示する。**在席を受け取れるのは、そのチャンネルの部屋に入っている参加者だけである**（`presence:changed` はそのチャンネルの部屋へ送る）。
  **在席を画面へ渡す経路は、部屋の側だけにする**——チャンネルの部屋への入室が成功したときの acknowledgement で、その時点でその部屋に入っている参加者を返し
  （タスクをまたぐ分を含む。一覧の持ち方は下記「タスクをまたぐ在席」）、以後の変化は `presence:changed` で届け、5分ごとに取り直して置き換える（同）。
  **参加者一覧の API（参加者もオーナーも同じ問い合わせを使う）と、オーナーの管理用の一覧には在席を乗せない**——3.1 がオーナーに返すのは管理用の範囲（`id` / 名前 / 種別 / 参加者数と参加者一覧）**だけ**であり、
  在席はそこに無い。**在席は「いま誰がそのチャンネルを開いているか」であり、人の出入りの管理ではなく閲覧の痕跡の側にある**（要件定義書 3.5.1 の境界）

**部屋（Socket.IO の room）**

**room は、サーバーが接続をまとめる単位である。この文書では「部屋」と呼ぶ。**
**部屋はサーバー側だけの概念であり、クライアントが自分で入ることはできない。**
**使い方は Socket.IO の公式文書（Rooms）の使用例——利用者の全タブへ送る部屋と、対象ごとの部屋——のとおりである。**

| 部屋 | 誰を入れるか | 何を送るか |
|---|---|---|
| **利用者の部屋** | **接続時の認証を通った接続を、サーバーがその利用者の部屋に入れる** | **その利用者だけに届けるもの。何をここへ送るかは 5.2 が定める**（この表では列挙しない。列挙すると、イベントや例外を足すたびに 5.2 と食い違う） |
| **チャンネルの部屋** | **チャンネルを開いたときの入室要求を受け、サーバーが参加者であることを確かめてから入れる** | チャンネル本体のイベント（5.2） |

- **接続時の認証は、ミドルウェア（`io.use`）で接続ごとに1回行う。** 断ると接続が拒否され、
  クライアントに `connect_error` が届く（公式文書 Middlewares）
- **チャンネルの部屋への入室を断るときは、acknowledgement（`emit` のコールバック）で応答を返す**
  （公式文書 Emitting events の request-response の形）。
  **コードは 3.1 と同じ2段階**——所属していなければ種別によらず 404、
  所属していれば パブリックは 403 / プライベートは 404。
  **404 の本体は 1.4 と同じ「見つかりません」に揃える。403 の本体は権限不足を示す文言とし、「見つかりません」にしない**——
  パブリックチャンネルは一覧に出ており、存在を隠す対象ではない（3.1）。**どちらも横断的な例外処理で揃え、入室の処理で個別の文言を書かない。**
  **入室が認可の関門である**（[CLAUDE.md](../CLAUDE.md) 2）——これが無いと、
  **非参加者がチャンネル ID を1件ずつ入室要求して、成功と失敗の差からプライベートの存在を引ける**
  （9.1 の経路1 で塞いだのと同じ形）。さらに**非参加者の入室がそのまま在席としてメンバー一覧に現れる**
- **クライアントとサーバーの間でやりとりするもの（配信イベントのほか、入室要求・退室要求とその acknowledgement、`@here` の受け取りの返事）の名前と型は、共有の型定義（`packages/shared`）に置く**
  （[CLAUDE.md](../CLAUDE.md) 3。フロントとバックで二重に書かない）。
  **配信の対象イベントの一覧（[要件定義書](requirements.md) 4.1「リアルタイム配信の対象イベント」）には足さない**——あちらはサーバーが自発的に配るイベントの一覧であり、要求とその応答（acknowledgement）・`@here` の受け取りの返事はそこに属さない
- **1本の接続が、複数のチャンネルの部屋に入りうる**
- **部屋から出すのは、次のすべてのときである**
  - **チャンネルを閉じた**——クライアントの退室要求で出す
  - **切断した**——**全部の部屋から自動で出る**（公式文書 Rooms。**部屋から外す後始末は要らない**——**在席の変化を配ることは要る**）
  - **チャンネルまたはワークスペースからのキック・退出で参加者でなくなった**（処理の側の義務は 2.2 の受け入れ条件）——**サーバーが、その利用者の部屋に入っている接続を
    チャンネルの部屋から外す**——ワークスペースから外れたときは、そのワークスペースの全チャンネルの部屋に当てる（`io.in(利用者の部屋).socketsLeave(チャンネルの部屋)`。
    **Redis アダプタ経由で他のタスクの接続にも効く**。公式文書 Server instance「Utility methods」）。
    **外さないと、参加者でなくなったあとも受信が続く**
  - **退会した**——**その利用者の接続を切る**（`io.in(利用者の部屋).disconnectSockets()`）。
    切断により全部の部屋から出る
- **在席の変化は利用者単位で配る**——**その利用者の接続が部屋に1本も無い状態から1本入ったとき**と、**最後の1本が部屋から外れたとき**に、
  その部屋へ `presence:changed` を配る。**同じ部屋に同じ利用者の別の接続が残っている間は、在席は変わらないので配らない**
  （1利用者が複数のタブ・端末で接続しうるため。タスクをまたぐ接続の数え方は「タスクをまたぐ在席」による）。**外れる契機はどれでも同じである**——
  サーバーが外す契機（キック・退出）では、外す処理の側が配る。**切断（退会による切断を含む）では、部屋から外れる前に配る**——
  Socket.IO の `disconnecting` は「fired a bit earlier, when the Socket#rooms set is not empty yet」（公式文書 Server socket instance）であり、
  その時点で入っていたチャンネルの部屋を取り出して配る。**`disconnect` を待つと、入っていた部屋を取り出せない**
- **部屋に入っている接続は、自タスクの分は部屋から、タスクをまたぐ分は問い合わせで取れる**（`io.in(チャンネルの部屋).fetchSockets()`）——
  **Redis アダプタは部屋の情報を Redis に保存しない**（公式文書 Redis adapter「there are no keys stored in Redis」）が、
  **`fetchSockets` を含む Utility methods は、Redis アダプタでサーバーをまたいで動く**（公式文書 Server instance「they are also compatible with the Redis adapter (starting with `socket.io-redis@6.1.0`), which means that they will work across Socket.IO servers」）。
  **在席の一覧の持ち方と更新の仕方は、下記「タスクをまたぐ在席」による**

**受け入れ条件**

- 在席状態を**色や記号だけで伝えない**。テキストの代替を併せて提供する
- 在席の変化が `presence:changed` として、そのチャンネルの部屋へ配信される（参加していないオーナーには届かない）。**在席は利用者単位であり、その利用者の最初の接続が入ったときと最後の接続が外れたときに、どの契機でも配られる**
- **上記の在席の配信を検証する自動テストが存在する**——切断・キックで部屋から外れた利用者が、他の参加者のメンバー一覧で在席のまま残らないこと。**同じ利用者のもう1本の接続が部屋に残っている間は、在席が消えないこと**
- **入室が成功したときの acknowledgement で、その時点でその部屋に入っている参加者の在席が返る**
- **参加者一覧の API のレスポンスに在席が含まれない**（参加者が求めた場合も、オーナーが求めた場合も）。**これを検証する自動テストが存在する**（参加者が求めた場合を含む）
- **`@here` の宛先は、送信の時点で一覧を取り直した結果の、そのチャンネルの部屋に入っている参加者である**（タスクをまたぐ分を含む。**取り直しに失敗したときは、そのタスクが持っている一覧の全員へ送り、開いていない利用者の側で弾く**。下記「タスクをまたぐ在席」）
- **`@here` の通知（通知一覧・バッジ）は、受け取りを返した利用者にだけ作られる。これとは別に、送った宛先と受け取りを返した利用者が一致しないときは、その `@here` の送った宛先の一覧と受け取りの一覧が残る**（通知ではなく、届いていないかもしれない利用者を後から確かめるための記録）
- **開いているチャンネルの在席が、5分ごとに取り直されて置き換わる**（通知を取りこぼしても、表示のずれは最大5分に収まる）
- **他のタスクに接続している参加者が入室の acknowledgement の在席と `@here` の宛先に含まれること、取り直しに失敗したときに一覧の全員へ送ること、開いていない利用者が `@here` を弾くこと、受け取りを返した利用者にだけ通知が作られること、送った宛先と受け取りが一致しないときに両方の一覧が残ることを検証する自動テストが存在する**（サーバーを2つ立て、アダプタを通して確かめる——1つのプロセスでは落ちない）
- **`@channel` は在席を見ない**（そのチャンネルの参加者全員）

> **離席の自動判定は行わない**（決定・2026-09-09。#146）。
> 「**いま対応できるか**」は**手動のステータス（F-04。絵文字＋テキスト）**が表す。
> **在席（自動）とステータス（手動）は別物であり、両方を持つ。**
> **在席が答えるのは「このチャンネルを見ているか」だけである。**

**タスクをまたぐ在席**（決定・2026-09-11・依頼側。#146）

**[要件定義書](requirements.md) 4.2 の「在席の自動判定は Valkey に保持しない」の項がこの節に委ねたものは、次のとおり決めた。**
**4.2 のその項を開いて、項全体を制約として受ける**——**ここに数えて写さない**（4.2 自身の指示。**列挙で閉じると、足した分が届かない**）。

- **各タスクは、チャンネルごとの在席の一覧を自分のメモリに持つ**（Valkey には置かない）
- **入室・退室（在席の変化）は、全体へ知らせる**——クライアントへは `presence:changed` をチャンネルの部屋へ、他のタスクへはサーバー間の通知（`serverSideEmit`。上記の Utility methods の1つ）で送り、受け取った側が一覧を更新する
- **各タスクは5分ごとに一覧を取り直す**——`fetchSockets` で全タスクへ問い合わせる。**取りこぼした通知によるずれは、最大5分で直る。** 開いている画面の在席も5分ごとに取り直す
- **`@here` の送信時にも一覧を取り直す。取り直しに失敗したときは、そのタスクが持っている一覧の全員へ送る**——
  Redis アダプタは、期限（`requestsTimeout`。既定 5,000 ミリ秒）までに応答が揃わないと問い合わせを打ち切る（公式文書 Redis adapter「After this timeout the adapter will stop waiting from responses to request」）。**失敗を未処理の例外にしない**（4.2）
- **受け取った側は、そのチャンネルを開いていなければ弾き、開いていれば受け取りを返す**（acknowledgement 付きの送信。Redis adapter の公式文書は、acknowledgement 付きのブロードキャストに 7.2.0 から対応すると書いている）。
  **送る相手が参加者であることは、サーバーが送る部屋を決めるときに確かめる**（5.2）——弾く判定はクライアントに任せるが、参加者でない利用者には送らない
- **`@here` の通知（通知一覧・バッジ）は、受け取りを返した利用者にだけ作る。これとは別に、送った宛先と受け取りを返した利用者が一致しないときは、送った宛先の一覧と受け取りの一覧を残す**——通知ではなく、届いていないかもしれない利用者を後から確かめるための記録である

**代償**（[CLAUDE.md](../CLAUDE.md) 4）

- **一覧に載っていない在席者には、`@here` は届かず、送った宛先の一覧にも受け取りの一覧にも残らない**——通知を取りこぼしてから次の取り直しまで（最大5分）の間に起きうる
- **Valkey が停止している間の `@here` の代償は、[要件定義書](requirements.md) 4.2 の「在席の自動判定は Valkey に保持しない」の項による**（ここに写さない）
- **弾く判定はクライアントに任せる**——改変したクライアントは、開いていないチャンネルの `@here` も受け取れる（影響はその利用者自身の通知だけである）

**判断が必要な点（実装時に決める）**

- **受け取りを待つ期限**（期限までに返らなかった利用者は、受け取らなかったとして扱う）
- **送った宛先の一覧と受け取りの一覧を、誰が確かめられるか**——**そのチャンネルの参加者の範囲を超えない**（在席は閲覧の痕跡であり、オーナーの例外は及ばない。3.1）
- **5分ごとの取り直しの契機**（画面の側は、クライアントの要求で行うか、サーバーから配るか）。**クライアントの要求で行う場合、チャンネルの部屋に入っていない接続からの取り直しの要求は、入室要求として扱う**——入室の関門と断り方（上記「部屋（Socket.IO の room）」）を通し、取り直しのための別の断り方は作らない
- **Valkey が停止しているとき、`fetchSockets` がどう返るか**——**未確認**。アダプタのソース（main ブランチ）で確かめたのは、期限切れで reject すること（「timeout reached while waiting for fetchSockets response」）と、購読者が1つ以下なら自タスクの分だけを返すことまでである。
  **失敗として返らず自タスクの分だけが返る場合は、取り直しに成功したように見えて宛先が欠ける**——導入する版で確かめる

`#146` は、上の実装時に決める点を持つため開いたまま残す。

> **4.2 の項が決めているもの**（保持先と一覧の持ち方・可用性の側の決定・代償）は、
> **その項全体がここの設計に効く**——**数えて列挙しない**（列挙で閉じると、足した分が届かない）。

## 10. 未読と通知

### 10.1 未読管理（F-23）

- チャンネルと DM ごとの未読を、サイドバーで太字表示する
- メッセージ一覧に「ここから未読」の区切り線を表示する
- **「利用者 × チャンネル」「利用者 × DM」と、スレッド内の未読の設定に要る「利用者 × スレッド」の既読位置を保持し、そこからの差分で未読を求める**（都度集計しない）
- **未読の単位はチャンネルと DM である**（決定・2026-09-11・依頼側。課題文「未読メッセージ通知」はチャンネルに限らない）

**受け入れ条件**

- **スレッド内の未読をチャンネルと DM の未読に含めるかを、利用者が設定で切り替えられる。既定は「含める」**
- 未読の変化が `unread:updated` として即時配信される。**宛先は 5.2 の `unread:updated` の箇条、関門は 5.2 の利用者の部屋を加えるときの資格の確認の箇条による**（その未読の持ち主の利用者の部屋へだけ送り、チャンネルの部屋へは配らない。送るときは、持ち主がいまもそのチャンネルの参加者であること——DM の未読なら、その DM の当事者であり、そのワークスペースのメンバーであること——を確かめる）
- **設定を「含めない」→「含める」に切り替えると、過去のスレッド返信のうち未読のものが未読として現れる**

> **設定の切替時は未読が復活する。** 既読位置を「利用者 × チャンネル」（DM では「利用者 × DM」）と「利用者 × スレッド」の
> 2系統で持つため、切り替えた瞬間に集計対象が変わる。**切替時に一括で既読扱いにすると、
> 読んでいないものが読んだことになる**ため、未読として現れる側を採る
> （[要件定義書](requirements.md) 3.5.2）。

### 10.2 メンション通知とブラウザ通知（F-24 / F-25）

**受け入れ条件**

- ブラウザ通知が出るのは**メンションと DM のみ**。通常のメッセージでは出さない
- **`@here` は、受け取った側がそのチャンネルを開いていなければ、ブラウザ通知もバッジも出さない**（受け取りを返さずに弾く。9.2「タスクをまたぐ在席」）
- **通知の許可を求めるのは、利用者が明示的に有効化したときのみ**（初回訪問でいきなり求めない）
- **許可が拒否された場合も、画面内のバッジで未読とメンションが分かる**
- タブを開いている間のみ通知される（プッシュは対象外）

### 10.3 通知一覧画面（F-26）

- 受け取ったメンション・DM を時系列で一覧表示する
- 既読化できる

**受け入れ条件**

- オフライン中に受けたメンションが、次回ログイン時に一覧で確認できる
- **`@here` が一覧に載るのは、受け取りを返した利用者だけである**（そのチャンネルを開いていなかった利用者には載らない。9.2「タスクをまたぐ在席」）
- 通知から該当メッセージに移動できる

## 11. 添付ファイル

### 11.1 アップロード（F-27 / F-28）

> **DM の添付に、この節の判定（チャンネルの参加者判定）とキーの構造（`workspace/{ws}/channel/{ch}/...`）を流用しない。** DM への当て方は 8 と #239 で決め、決まるまで DM の添付を実装しない。

**許可リスト方式とする。列挙した形式のみを受け入れる。**

| 種別 | 上限 | 許可する形式（これ以外は受け付けない） |
|---|---|---|
| 画像 | 10 MB | jpeg / png / gif / webp（**SVG は含めない**） |
| 動画 | 100 MB | mp4 / webm |
| 文書 | 25 MB | pdf / txt / csv / md / docx / xlsx / pptx |
| 圧縮 | 25 MB | zip |

**受け入れ条件**

- **サーバー側で中身から形式を検証する。** 拡張子や申告された Content-Type を信用しない——
  **マジックバイトを持つ形式（画像・動画・pdf・zip と、zip を容器とする docx / xlsx / pptx）はマジックバイトで、
  持たないテキスト系（txt / csv / md）は UTF-8 として正しく NUL を含まないことで検証する**（決定・2026-09-11・依頼側。
  BOM の無いテキストには決まった先頭バイト列が無い——ファイル署名の一覧）
- **UTF-8 の検証は HTML を止めない**——中身が HTML でも UTF-8 としては正しい（Node の `TextDecoder` の `fatal` で実測）。
  **HTML として解釈させないのは、配信ヘッダーの箇条の役目である**
- 上限を超えるファイルは拒否される
- **許可リストに無い形式は拒否される**（拒否リストではない）
- **SVG がアップロードできない**
- **署名付き URL の発行は、要求している利用者がそのチャンネルの参加者であるときだけ行う**
  （**派生**。#176。**これが無いと非参加者がプライベートチャンネルのキー配下に置け、
  署名付き Cookie はパス単位であるため、置かれたものが参加者に配信される**）
- **署名付き URL に焼き込むキーは、すべてサーバー側で組み立てる**——`{ws}/{ch}` は参加者判定を通したチャンネル、`{UUID}` はサーバーが発行する値、
  `{ファイル名}` は許可リストで置換した値（キーの形式の行）である。**クライアントが指定したキー・パスをそのまま使って署名しない**（**派生**。#176。署名付き PUT は署名の時点でキーに束縛されるため、
  **これが無いと、自分が参加しているチャンネルで判定を通し、別のプライベートチャンネルの接頭辞に署名させて、参加者判定を迂回できる**）
- **アップロードの経路（発行・確定）で参加者判定に落ちたときは、3.1 と同じ2段階のコードを返す**——所属していないワークスペースなら種別によらず 404、所属していればプライベートは 404 / パブリックは 403（404 の本体は 1.4 のとおり）。
  **確定の要求で、識別子が本人に払い出されたものでないときは 404 を返す**（識別子の存在を認めない。要求はチャンネルを持たないため、他の利用者の識別子——別のチャンネルの隔離用のキーを指すものを含む——はすべてこれに当たる）
- **上記の参加者判定・応答コード・署名するキーの出所を検証する自動テストが存在する**（[要件定義書](requirements.md) 4.8「必ずテストを書く箇所」の2）——
  **参加者であっても、判定を通したチャンネル以外の接頭辞に署名させられないこと**を含む（非参加者の拒否のテストだけでは、この組み立ては緑のまま通る）
- **アップロード用の署名付き URL の発行にレート制限がかかる**（投稿しなくても S3 の操作と行の追加が起きるため）
- **アップロードの確定の要求にもレート制限がかかる**——確定はオブジェクトを読んで検証し、コピーと削除を行う、サーバー側で最も重い段であり、
  **発行のレート制限の内側で繰り返し起こせないようにする**（要件定義書 4.3 のレート制限の行）
- **配信用の S3 のオブジェクトキーが `workspace/{ws}/channel/{ch}/{UUID}/{ファイル名}` の形式である**（隔離用のキーは下の隔離の箇条が定め、この形式の外にある）。
  **`{ファイル名}` は許可リストで置換した値であり、配信用のキーでは、その拡張子を確定の段で検証した形式のものに付け替える**（下の保存名の箇条）——利用者のファイル名のうち英数字・`.`・`_`・`-` だけを残し、それ以外の文字と先頭の `.` を `_` に置き換え、
  **発行の段で書く隔離用のキー（`quarantine/` を含む）全体が** S3 の上限（1,024 バイト）に収まるよう末尾を切り詰める——配信用のキーは `quarantine/` の 11 バイトだけ短く、確定の段の拡張子の付け替えで伸びるのは許可する形式の拡張子の最長（`.docx` などの 5 バイト）までであるため、配信用のキーも収まる。**元のファイル名は表示用にデータベースに保持する**
  （決定・2026-09-10・依頼側。OWASP File Upload Cheat Sheet「Restrict characters to an allowed subset」。残す文字は S3 の公式文書「Object key naming guidelines」の safe characters に含まれる）
- **検証を通るまで、配信できるキーに置かない**（#211）——署名付き URL の宛先は**隔離用のキー**（**ブラウザが書けるのはここだけである。配信用のキーへ書くのは、確定を行うサーバーの権限だけ**。**アップロード URL の署名には `quarantine/` にだけ書ける専用の資格情報を使い、確定（隔離用のキーの読み出し・削除と、配信用のキーへのコピー）の資格情報と分ける**——署名付き URL への PUT は署名したプリンシパルとして認証されるため。[技術スタック](tech-stack.md) の添付ファイルの行）
  `quarantine/workspace/{ws}/channel/{ch}/{UUID}/{ファイル名}` とし、
  サーバーが形式・サイズ・中身（形式ごとの検証）を検証してから、**検証で読んだ版（`versionId`）に固定して配信用のキー（キーの形式の行）へコピーし、隔離用のキーを削除する**
  （S3 に移動の操作は無く、コピーと削除で行う。公式文書「Copying, moving, and renaming objects」）
- **コピー元は、検証で読んだ版に固定する**——バージョニングが有効なバケットでは、コピー元の指定は既定で現行の版を指す
  （公式文書 CopyObject「If your source bucket versioning is enabled, the `x-amz-copy-source` header by default identifies the current version of an object to copy. … To copy a different version, use the `versionId` query parameter.」）。
  **版の固定は多層の防御である**——下の条件付き書き込みにより、検証の後・コピーの前は現行の版があるため、同じ URL での差し替えは拒否される。**固定しておけば、その前提が崩れても（署名に `If-None-Match` を含め忘れた実装など）、検証していないバイト列は配信用のキーへコピーされない**
- **検証に通らなかったものは配信用のキーへ移さず、隔離用のキーを削除する**
- **隔離用のキーは、添付の署名付き Cookie の対象に一致しない**（`/avatars/*` の Cookie の URL と `/files/*` の URL から、要件定義書 4.3 の「確かめる URL の形」で `quarantine/` のキーに届かないかは未確認であり、実際に配信して確かめる。[要件定義書](requirements.md) 4.3）——配信 URL は `/files/quarantine/...` になり、
  Cookie の対象 `/files/workspace/{ws}/channel/{ch}/*` の前方に一致しない
- **アップロード用の署名付き URL の有効期限は5分とする**（決定・2026-09-10・依頼側）——
  S3 は期限をリクエストの開始時に確かめるため、期限内に始めた PUT は完走する（AWS 公式「Amazon S3 checks the expiration date and time of a signed URL at the time of the HTTP request」）。
  **期限内は同じ URL で何度でも PUT できる**（同「You can use the presigned URL multiple times, up to the expiration date and time」）——**ただし下の条件付き書き込みにより、書けるのはそのキーに現行の版が無いか、現行の版がデリートマーカーである間だけである**
- **署名付き URL には `If-None-Match: *` を署名して含め、同じ発行のキーへの上書きを拒否する**（決定・2026-09-11・依頼側）——
  S3 の条件付き書き込みは「If there's an existing object, the write operation fails, resulting in a `412 Precondition Failed`」であり、
  バージョニングが有効なバケットでも、現行の版がデリートマーカーでない限り拒否される（公式文書「How to prevent object overwrites with conditional writes」。条件付き書き込みには SigV4 の署名が要る）。
  **キーは発行ごとに新しい `{UUID}` で組み立てるため、同じ画像でも別の投稿としてなら何度でも上げられる。拒否するのは、1回の発行の URL で同じキーへ書き直すことだけである**。
  **これにより1回の発行で書けるのは1版（確定の後にもう1回）に限られ、発行のレート制限が S3 への書き込みの回数の上限として働く**（量の上限ではない——1回の PUT の大きさは署名付き URL では強制されず、確定の段の検証で拒否するまで隔離用のキーに書かれる）
- **`quarantine/` の接頭辞にだけライフサイクルを置く**（決定・2026-09-11・依頼側。[要件定義書](requirements.md) 4.2 の「ライフサイクルは置かない」の例外）——
  確定されずに放置されたもの（`Expiration`）と、上書きや削除で古くなった版（`NoncurrentVersionExpiration`）を失効させる。
  **確定で隔離用のキーを削除した後は現行の版がデリートマーカーになるため、期限内に同じ URL でもう1回だけ書ける**
  （公式文書「if the current object version is a delete marker, the write operation succeeds」）——その1回分は確定できず、ライフサイクルで消える。
  **フィルターは `quarantine/` を明示し、配信用のキーに掛からないことを確かめる**——ライフサイクルの削除はバケットポリシーでは止められない
  （公式文書「You can't use a bucket policy to prevent deletions or transitions by an S3 Lifecycle rule」）
- **確定の要求が指定できるのは、サーバーが署名付き URL の発行時に払い出したアップロードの識別子だけであり、確定を求められるのはその識別子を払い出された利用者本人だけである。**
  **隔離用のキー・コピー先の配信用のキー・やり直す参加者判定の対象チャンネルは、すべてサーバーがその識別子に紐づけて保持する `{ws}/{ch}/{UUID}/{ファイル名}` から組み立てる**（配信用のキーの `{ファイル名}` は、保持している名前の拡張子を、確定の段で検証した形式のものに付け替えてから使う）
  （**派生**。#211。クライアントが渡したキーやチャンネルでコピー先を決めない——決めると、自分が参加するチャンネルで判定を通し、
  **非参加のプライベートチャンネルの隔離用のキーを自分のチャンネルの配信用のキーへ移させて、その添付を取得できる**）
- **確定は識別子ごとに1回だけ行う**——同じ識別子の2回目以降の確定の要求には、コピーも削除もやり直さず、1回目の結果を返す
  （検証に通らなかった場合も同じであり、やり直すには発行からやり直す）。
  （**派生**。再び確定できると、確定で隔離用のキーを削除した後の1回の書き込み（上のデリートマーカーの箇条）を確定させ、
  **投稿の後に配信用のキーのバイト列を差し替えられる**。上の「1回の発行で書けるのは1版」もこの箇条を前提にする）
- **アップロードを確定する（隔離用のキーから配信用のキーへ移す）時点で、その識別子を払い出された利用者の参加者判定をやり直す**（決定・2026-09-10・依頼側）——
  **発行後にキック・退出した利用者の PUT は、期限内であっても確定で拒否され、配信用のキーに届かない**
- **確定時の参加者判定のやり直し、検証に通らないものが配信用のキーに移らず、隔離用のキーが削除されること、配信用のキーには検証した版のバイト列だけが載ること（検証の後に隔離用のキーを差し替えても載らないこと）、他の利用者に払い出された識別子（別のチャンネルの隔離用のキーを指すものを含む）で確定させられないこと、隔離用のキーを署名付き Cookie で取得できないこと、ブラウザに払い出した署名付き URL で配信用のキーへ PUT できないこと、識別子を払い出された本人以外が確定を求められないこと、同じ識別子の2回目以降の確定がコピーも削除も行わないこと、確定で拒否するときの応答コード、発行と確定の要求のレート制限、発行した署名付き URL が `If-None-Match: *` を署名に含むことを検証する自動テストが存在する**
- **配信するオブジェクトの `Content-Type` は、検証した形式からサーバーが決める**（決定・2026-09-11・依頼側）——
  確定のコピーでメタデータを置き換え（`x-amz-metadata-directive: REPLACE`。既定の `COPY` ではアップロード時の値が引き継がれる。S3 公式 CopyObject）、
  テキスト系は `text/plain; charset=utf-8` に固定する
- **`Content-Disposition` は、画像・動画は `inline`、それ以外は `attachment` とする**（決定・2026-09-11・依頼側）——
  画像のプレビューと動画の `#t=30` 表示のため。**テキスト系・pdf・Office・zip はアプリ内で描画しない**
- **保存名の拡張子は、検証した形式のものに付け替える**——キーの `{ファイル名}`（キーの形式の行）と、`Content-Disposition` の `filename` / `filename*` の両方
  （両方あると `filename*` が優先される。MDN）。**元のファイル名は表示用に DB に持ち、保存名には使わない**——
  二重拡張子（`.jpg.php`）や `.txt` を名乗る HTML が、保存したときに元の拡張子で開かれることを防ぐ（OWASP File Upload Cheat Sheet の Extension Validation）
- **`/files/*` のビヘイビアに CloudFront の SecurityHeadersPolicy を付け、すべての応答に `X-Content-Type-Options: nosniff` を返す**（CloudFront 公式）——
  宣言した `Content-Type` 以外として解釈させない（MDN「prevents a browser from treating a response as text/html when … the Content-Type header … indicates a non-HTML type」）
- **上記の形式ごとの検証・配信の `Content-Type` と `Content-Disposition`・拡張子の付け替え・`nosniff` を検証する自動テストが存在する**
- **ライフサイクルのフィルターと、確定のプリンシパルの権限（`GetObjectVersion`・`DeleteObject` を含む）は Terraform の定義であり、先にテストを書く対象ではない**（[要件定義書](requirements.md) 4.8「この方式を適用しない範囲」。**TDD の対象外であって、自動テストの対象外ではない**）——**Terraform の実装時に、plan の出力で、フィルターが `quarantine/` だけに掛かることと、権限の列挙が [技術スタック](tech-stack.md) の添付ファイルの行と一致することを確かめる**

**判断が必要な点（実装時に決める）**

- **確定の API の形**——クライアントが確定を求める経路と、2回目以降の確定の要求に返す応答の形（1回だけ行うことは上の箇条で決めた）
- **レート制限の数値**（発行・確定）と、`quarantine/` のライフサイクルの日数

> **踏むと壊れる: サーバーが multipart を受け取る経路を実装する前に、`scripts/audit-allowlist.json` の `multer` 3件を外し、
> `multer` 2.3.0 を取り込めることを確認する（#166）。**
> あの3件は**サーバーが multipart を受け取る経路にしか効かない**ため、「動く経路が無い」ことを理由に通してある。
> **添付のアップロードはブラウザから S3 へ直接 PUT するため、この経路に当たらない**（#176）。
> **アバター画像（F-04）も直接 PUT であり、この経路に当たらない**（1.3。#227）。**サーバーが multipart を受け取る経路を1つでも実装した時点で、その理由は失効する。**

> **隔離用のキーに残るものの代償**（#211）。S3 に移動の操作は無くコピーと削除で行うため、
> **バージョニングにより、隔離用のキーには旧バージョンとデリートマーカーが残る。**
> **PUT したまま確定を求めずに放置されたものも、許可する形式の上限に関わらない大きさ（1回の PUT で S3 に書ける大きさまで）のバイト列も残る**（署名付き URL でサイズの上限を強制する手段は、公式文書で確認できていない。上限は確定の段の検証で拒否する）。**どれも `quarantine/` のライフサイクルで失効するまで残る**——
> 失効は日数単位であり、さらに遅れがありうる（公式文書「There may be a delay between the expiration date and the date at which Amazon S3 removes an object」）。
> **4.2 の「ライフサイクルは置かない」の例外は `quarantine/` だけである**（2026-09-11。配信用のキーには置かない）

> **検証の範囲の代償**（2026-09-11）。**中身の安全までは確かめない。**
> - **docx / xlsx / pptx は zip と同じ先頭バイト列（`50 4B 03 04`）を持つ**（ファイル署名の一覧）ため、マジックバイトでは zip や他の zip 形式と区別できない。**容器の中身は検査しない**
> - **マクロを保存できるのは m で終わる拡張子（.docm / .xlsm / .pptm）だけ**であり（Microsoft 公式「Open XML Formats and file name extensions」）、許可リストはそれを含まない。**ただし中身を検査しないため、拡張子を偽ったものは検出しない**
> - **ウイルス対策・CDR（無害化）は行わない**（OWASP File Upload Cheat Sheet が手段として挙げる）。入れるなら新しい機能であり、提案と承認が要る
> - **csv の式の実行（CSV injection）は防がない**——利用者のファイルを書き換えないため。表計算ソフトで開いた側で式が動きうる（**出典の OWASP の本文は取得できず、検索結果の要約での確認にとどまる**）
> - **UTF-16 のテキストは NUL を含むため拒否される**（Node で実測）

> **拒否リストを採らない理由。** 「実行形式を除く」という書き方では、`.exe` を弾いても
> `.dll` `.jar` `.ps1` `.scr` `.msi` `.lnk` が残る。**拒否リストは必ず抜ける。**
> さらに「任意の形式」ではマジックバイトの検証がかけられない。

> **SVG を受け付けない理由。** SVG は画像ではなく **XML** であり、`<script>` を内包できる。
> 受け入れると保存型 XSS と XXE の経路になる。サニタイズによる受け入れも可能だが、
> それは**保険的対策**であり、**受け付けない構造にすることが根本対策**である
> （[要件定義書](requirements.md) 3.4）。

> **動画のサムネイルは生成しない。** `<video src="...#t=30">` により 30 秒地点の映像を
> 表示させる（[要件定義書](requirements.md) 3.5.2）。サーバー側に動画処理の基盤を持たない。
> **一覧では Intersection Observer で遅延読み込みし、画面外の `<video>` 要素は生成しない。**
> `#t=30` の表示にはブラウザが 30 秒地点までシークする必要があるため、画面外の分まで
> 要素を作るとスクロールのたびに読み込みが走る。

### 11.2 配信の認可（F-29）

> **DM の添付に、この節の判定（チャンネルの参加者判定）と署名付き Cookie の対象（`/files/workspace/{ws}/channel/{ch}/*`）を流用しない。** DM への当て方は 8 と #239 で決め、決まるまで DM の添付を実装しない。

**CloudFront の署名付き Cookie をチャンネル単位で発行する。**

```
① ブラウザがチャンネルを開く
② サーバーが「この利用者は、このチャンネルの参加者か」を判定する
③ OK なら /files/workspace/{ws}/channel/{ch}/* に限って有効な署名付き Cookie を返す（Cookie の Path 属性は /files）/ NG なら 3.1 と同じ2段階のコード（404 / 403）
④ ブラウザは、そのチャンネルの添付を CloudFront から直接取得する
⑤ 期限が切れたら、チャンネルを開いている限りサーバーが Cookie を再発行する
```

**受け入れ条件**

- **非参加者がファイルの URL を直接指定しても取得できない**
- **参加者が、そのチャンネルの添付を取得できる**——**署名付き Cookie の `Path` 属性は `/files` である**（`Path` を省くと既定値が発行時の URI のディレクトリ（`/api/...`）になり、`/files/...` に一度も送られない。[要件定義書](requirements.md) 4.3 の表）
- **`/files` を外した URL（S3 のキーと同じ形）では取得できない**——
  **既定のビヘイビアは署名を要求しないため、そこから添付へ到達できてはならない**（[要件定義書](requirements.md) 4.3）
- **`/avatars/*` の URL（[要件定義書](requirements.md) 4.3 の「確かめる URL の形」を含む）では、添付（`workspace/{ws}/channel/{ch}/...` と、隔離用の `quarantine/...` のキー）を取得できない**——
  **アバターの署名付き Cookie はログインしている利用者なら誰にでも発行するため、そこから添付へ到達できてはならない**（[要件定義書](requirements.md) 4.3・1.3）
- **`/files/*` の URL（[要件定義書](requirements.md) 4.3 の「確かめる URL の形」を含む）でも、署名付き Cookie の対象の外のキー（別のチャンネルの `workspace/...` と `quarantine/...`）を取得できない**——
  **`/files/*` は正規化の後も `/files/*` のビヘイビアに当たり、オリジンへは正規化の前のパスが渡る**（[要件定義書](requirements.md) 4.3）
- **非参加者に対して、そのチャンネルのパス配下に有効な Cookie が発行されない**
- **配信は CloudFront 経由のみであり、S3 の URL を直接開いても取得できない**
  （**アップロードは別の経路であり、ブラウザから S3 の隔離用のキーへ直接 PUT する（11.1）。#176**。
  上流は [要件定義書](requirements.md) 4.3 の「**パブリックアクセスの全面遮断**」であり、
  **署名付き PUT はパブリックアクセスではないため両立する**）
- Cookie は期限切れ後に無効になる
- **チャンネルから外れた（キック・退出した）利用者は、次の再発行を受けられない**
- **NG のときの③の応答コードは 3.1 と同じ2段階で決まる**——所属していないワークスペースなら種別によらず 404、所属していればプライベートは 404 / パブリックは 403（404 の本体は 1.4 のとおり）
- **上記を検証する自動テストが存在する**（[要件定義書](requirements.md) 4.8「必ずテストを書く箇所」の2）——**確かめる3つの場合は、3.1 の2段階のテストと同じである**

> **配信で、署名付き URL ではなく Cookie を採る理由と、その代償**は
> [要件定義書](requirements.md) 4.3 に記す。要点は、**署名付き URL では
> 「長い動画を見ていて巻き戻すと 403 で止まる」**という壊れ方が起き、その回避実装が重いこと、
> および Cookie ならチャンネル単位で1回の発行に集約できることである。

> **認可の粒度がパス単位になる。** そのため **配信用の S3 のキー設計が認可の一部**になっている（隔離用のキーは配信 URL を持たず、この構造の外にある。`/avatars/*` と `/files/*` の URL から、正規化の前のパスで届かないかは未確認である。11.1・[要件定義書](requirements.md) 4.3）。
> `workspace/{ws}/channel/{ch}/...` の構造を崩すと認可が崩れる。
> **Cookie が対象にするのは配信 URL のパス（`/files/` を前置したもの）であり、S3 のキーではない**。**Cookie の `Path` 属性も `/files` である**
> （[要件定義書](requirements.md) 4.3 の表）。

**判断が必要な点（実装時に決める）**

- **Cookie の有効期限を何分にするか。** 再発行はサーバー側で完結するため、
  短めに設定できる（15〜30 分を想定）
- **`/files` を剥がす手段をどちらにするか**（CloudFront Functions / Lambda@Edge）。
  **関数を置かないという選択肢は無い**（[要件定義書](requirements.md) 4.3）
- **署名付き Cookie の `Resource` の照合が、URI の書き換えの前と後・正規化の前と後のどちらのパスで行われるかを、
  [要件定義書](requirements.md) 4.3 の「確かめる URL の形」の URL を含めて、実際に配信して確かめる**（[要件定義書](requirements.md) 4.3。**文書からは決まらなかった**）

> **踏むと壊れる: 両立しなかった場合に、`Resource` を `/*` へ広げてはならない。**
> **1枚の Cookie で全チャンネルの添付が取れる。**
> **その場で直さず依頼側へ上げる**——4つの値と CloudFront のビヘイビア分割を動かす設計判断である
> （[要件定義書](requirements.md) 4.3）。

## 14. 運用

### 14.1 死活確認（F-39）

**利用者に価値を提供する機能ではなく、ALB のターゲットグループがヘルスチェックに使う
運用エンドポイントである。** 機能一覧に置くのは、他の機能と同じく区分（要求 / 派生 /
提案・承認済）を明記して管理するためである。**画面を持たない点は 1.4（F-05）と同じだが、
1.4 は利用者の操作に伴って働く横断的な仕組みであるのに対し、F-39 は利用者ではなく
ALB のために存在する**点で性質が異なる（#15）。

| 項目 | 内容 |
|---|---|
| エンドポイント | `GET /api/health` |
| 認証 | **不要**（[要件定義書](requirements.md) 2 のとおり、アプリケーションの内容を返さないため「非ログインでの閲覧」には当たらない） |
| 応答 | 200 と、アプリケーションが起動していることを示す最小限の内容。**DB 等への問い合わせは行わない** |

**受け入れ条件**

- `GET /api/health` は、認証情報（`Authorization` ヘッダー・Cookie）が無くても 200 を返す
- 応答にパスワード・トークン・セッション情報等の秘密を含まない
- **DB・Redis 等への問い合わせを行わない**（依存先が止まっていても 200 を返す。代償は下記）

> **浅い死活確認（DB・Redis 等への問い合わせを行わない）を採ったことの代償。**
> アプリのプロセスが起動してさえいれば、DB や Redis に繋がっていなくても `healthy` と
> 判定される。**ALB は壊れたタスクにもリクエストを振り分け続けうる。**
>
> **依存先を確認する側は採らなかった。** DB・Redis への問い合わせを含めると、
> **依存先の一過性の不調で、アプリ自体は無事なタスクまで切り離され全断になる。**
> 学習用途の構成（RDS は Single-AZ で冗長化しない。[要件定義書](requirements.md) 4.2）
> ではこちらの代償の方が大きいと判断し、浅い死活確認を採る。
