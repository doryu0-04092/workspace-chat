# 要件定義書

## 1. 目的と背景

ワークスペース単位でチャンネルを持つ、Slack 風のチャットアプリケーションを作る。

汎用のメッセージングアプリと異なり、会話を **チャンネル** と **スレッド** の二軸で構造化する。
これにより、1つのチャンネルで複数の話題が同時進行しても発言が混ざらず、
過去の会話を後から検索して掘り起こせる。会話を流れて消えるもの（フロー型）ではなく、
**検索可能な資産（ストック型）** として扱うことが、この種のアプリケーションの中核にある。

スクール課題であり、**学習目的の構成**である。可用性やコストの面で本番運用には適さない
割り切りを複数含む。該当箇所は本書および [技術スタック](tech-stack.md) に明記する。

## 2. 想定利用者

同一の組織・チームに属し、業務上の連絡を行う個人。
アカウントを持つ利用者のみが閲覧・投稿できる（非ログインでの閲覧は提供しない）。

1人の利用者は複数のワークスペースに所属できる。ワークスペースを作成した利用者が
そのワークスペースのオーナーとなり、管理者権限を持つ。

## 3. スコープ

### 3.0 機能の区分について

本書および [機能一覧](features.md) では、**各機能がどこから来たのかを3つに区分して表記する。**
「顧客が求めた機能」と「実装側の判断で加えた機能」を混同しないためである。

| 区分 | 定義 | 判定基準 |
|---|---|---|
| **要求** | 課題文に明記されている機能 | 課題文に書かれている |
| **派生** | 要求を満たすために技術的に不可避な機能 | **これが無いと、どの要求が成立しないか答えられる** |
| **提案・承認済** | 無くても要求は満たせるが、**提案し、承認を得た上で実装する**機能 | 無くても要求は満たせる |

**「派生」と「提案・承認済」を分ける理由**は、両者の性質がまったく違うためである。
派生機能は要求から論理的に導かれるものであり、実装側が勝手に加えたものではない。
一方、提案・承認済の機能は要求の外にあるため、**提案し承認を得たという事実を記録する**
必要がある。無断で追加すれば要求の逸脱であり、承認を得ずに「承認済」と書けば虚偽になる。

各機能の区分と根拠は [機能一覧](features.md) の一覧表に記載する。

### 3.1 顧客要求に基づく機能

課題文に明記された機能。全19件。

| 領域 | 機能 |
|---|---|
| **認証・ユーザー管理** | 新規登録（ユーザーID とパスワードのみ）/ ログイン / ログアウト / プロフィール設定（アバター画像・表示名・ステータス） |
| **メッセージング** | テキストの投稿 / 編集 / 削除 / Markdown 基本対応 / 画像・動画・ファイルの添付 / 絵文字リアクション / メンション / メッセージ検索 / スレッドの作成と返信 / ダイレクトメッセージ |
| **ワークスペース・チャンネル管理** | ワークスペース / チャンネル作成（パブリック・プライベート）/ 招待機能 / 管理者権限（オーナーによる招待・キック・チャンネルの追加削除。メンバーは不可） |
| **通知** | 未読メッセージ通知 / メンション通知 / ブラウザ上の通知 |

**メール認証は要求の時点で対象外とされている。** 検証に複数のメールアドレスが必要となり、
手元で確認できなくなるためである。本来はメール認証を行うか、ユーザーID をメールアドレスに
する方が望ましいという判断も、要求時に併せて示されている。この帰結は 3.4 に記す。

### 3.2 要求の実現に必要となる派生機能

**課題文には書かれていないが、書かれている要求を満たすために技術的に不可避な機能。** 全9件。

各項目に「**これが無いと、どの要求が成立しないか**」を明記する。これが派生機能の正当性の根拠であり、
実装側の判断で機能を膨らませたものではないことの証明になる。

| # | 機能 | これが無いと成立しない要求 |
|---|---|---|
| 派-1 | **リアルタイム配信（WebSocket）** | **テキストチャット**。相手の発言を見るのに毎回リロードが必要なものはチャットとして成立しない。加えて**ブラウザ通知**も、サーバーからの能動的な配信なしには実現できない |
| 派-2 | **サーバー側での認可検証** | **「メンバーはこれらができない状態にすること」**。画面上でボタンを隠すだけでは、API を直接呼ばれれば通ってしまう。権限の根拠はサーバー側の検証にある |
| 派-3 | **検索の認可（参加チャンネルへの限定）** | **プライベートチャンネル**。検索を素直に実装すると、非参加者に対してプライベートチャンネルの本文が検索結果として露出する |
| 派-4 | **メッセージのカーソルページネーション** | **メッセージの表示**。全件を返す実装では、メッセージが数千件に達した時点で応答が破綻する |
| 派-5 | **ワークスペース／チャンネルのメンバー管理** | **招待・キック・管理者権限・プライベートチャンネルのすべて**。「誰がどのワークスペースの、どのチャンネルに所属しているか」という構造が無ければ、これらは判定できない |
| 派-6 | **添付ファイルの保存先とサイズ・形式の検証** | **画像・動画・ファイルの添付**。保存先が無ければ添付は成立せず、上限が無ければ動画1本でストレージが破綻する |
| 派-7 | **パスワードのハッシュ化** | **新規登録・ログイン**。平文または可逆な形での保存は、認証機能として成立していない |
| 派-8 | **添付ファイル配信の認可** | **プライベートチャンネル**。ファイルの URL を直接開かれると、非参加者が中身を取得できてしまう。派-3 と同じ構造の問題であり、画面に出さないだけでは不十分である |
| 派-9 | **Markdown の XSS 対策** | **Markdown 基本対応**。利用者の入力を描画する以上、無対策ではスクリプトを注入される。安全に描画できて初めて要求を満たす |

> **派-3 と 派-8 は同じ性質の問題である。** どちらも「画面に表示しない」だけでは不十分で、
> **データを返す経路そのものに認可が必要**になる。プライベートチャンネルという要求は、
> **一覧・取得 API / 検索 / 添付ファイルの配信 / WebSocket の配信の4経路**すべてを塞いで
> 初めて成立する（[コードレビュー観点](../REVIEW.md) 2.1）。
> **このうち上の表に挙げているのは 派-3（検索）と 派-8（添付ファイルの配信）の2件である。**
> 残る2経路は、**一覧・取得 API を 派-2、WebSocket の配信を 派-1 の受け入れ条件**
> （[機能一覧](features.md) F-16）で担保する。**4経路のうち1つでも担保先を示せない状態にしない。**

### 3.3 提案し、承認を得て実装した機能

**課題文には無く、無くても要求は満たせるが、価値があると判断して提案し、承認を得た上で実装する機能。**
全10件。**提-1 〜 提-6 は 2026-09-03、提-7 〜 提-10 は 2026-09-04 に提案し、いずれも同日承認を得ている。**

提-7 以降は、ドキュメント完成後に実施した総点検（矛盾・ユーザビリティ・セキュリティ・法令）で
**要求どおりに作ると成立しない、あるいは利用者が詰む状態になる**と判明した箇所への対応である。

| # | 機能 | 提案理由 |
|---|---|---|
| 提-1 | **コードスニペット**（バッククォート3つによるシンタックスハイライト） | Markdown 対応の延長線上にあり、追加コストが小さい。業務での利用を想定すると使用頻度が高い |
| 提-2 | **ピン留め** | 重要なメッセージをチャンネルに固定する。過去の発言を探す手間を減らす |
| 提-3 | **入力中インジケータ**（「○○さんが入力中…」） | リアルタイム配信の基盤を流用でき、追加コストが小さい。相手が応答中であることが分かり、待ちの体験が改善する |
| 提-4 | **@here と @channel** | 要求のメンションは個人宛のみだが、それだけでは「チャンネル全員に知らせる」手段が無い。段階を持たせることで、無用な通知を避けながら周知ができる |
| 提-5 | **在席状態の表示**（メンバー一覧に接続中を示す） | 提-4 の `@here` を成立させるために在席の判定自体は必要になる。判定結果を画面に出さない理由が無く、誰に届くかが利用者から見えるようになる |
| 提-6 | **通知一覧画面** | 通知を永続化する方針を採ったため、蓄積した通知を見返す画面が無いと永続化の意味が失われる。オフライン中に受けたメンションを後から辿れる |
| 提-7 | **チャンネルのアーカイブと復元** | オーナーは参加していないプライベートチャンネルのメッセージを閲覧できない（3.5.1）。にもかかわらず削除はできるため、**中身を一切知らないまま他人の会話をまるごと失わせる**操作が成立してしまう。削除ではなくアーカイブとし、復元できるようにする |
| 提-8 | **アカウントの削除（退会）** | 登録した利用者が自分のアカウントを消す手段を持たない状態を避ける。個人情報の削除の求めに応じる手段でもある（6.2） |
| 提-9 | **リカバリーコード** | メール送信を行わないため、パスワードを忘れると復旧手段が一切ない（3.4）。登録時にリカバリーコードを発行して控えさせ、**オフラインの復旧手段を1つだけ**用意する |
| 提-10 | **招待の承諾と、ワークスペースからの退出** | 招待が即時参加で退出手段が無いと、**「勝手に追加されるのに自分では抜けられない」**状態になる。承諾フローと退出の導線を設ける |

> **提-4 について補足する。** `@here` は「在席中の参加者」に通知する機能であり、
> 在席状態の判定を必要とする。リアルタイム配信の接続状況から判定できるため追加コストは小さいが、
> **この判定なしには `@here` と `@channel` が同じ動作になってしまう**点を確認の上で採用している。
>
> **提-4 と 提-5 は依存関係にある。** `@here` の判定に必要な在席状態を、画面にも表示するのが 提-5 である。
> 提-4 を採らない場合、提-5 は単独では価値が薄い。

### 3.4 実装しない機能（意図的な対象外）

| 対象外 | 理由 |
|---|---|
| **ボイスチャンネル・音声/ビデオ通話** | **課題文で明示的に対象外**とされている。加えて WebRTC という別種のリアルタイム技術が必要になり、本題から外れる |
| **メール送信全般** | ユーザーID をメールアドレスにしない方針のため。**結果としてメールによるパスワードリセットは提供しない。** 代替として**リカバリーコード**（提-9）を発行するが、**そのコードを紛失した場合、アカウントは復旧できない。** 学習用途として許容し、登録画面に明示する |
| **モバイルへのプッシュ通知** | **課題文で明示的に対象外**とされている。Service Worker と Web Push の基盤が必要になる。**その結果、ブラウザのタブを閉じている間は通知が届かない** |
| **Bot / Incoming Webhook / スラッシュコマンド** | 外部連携は本題ではなく、Bot 用の認証設計が別途必要になる |
| **既読者一覧（誰が読んだか）** | **Slack にそもそも存在しない機能**であり、「Slack 風」という要求に含まれない。既読の可視化は業務上の圧力になるという設計判断が Slack 側にあり、それを踏襲する |
| **ファイルの外部共有リンク** | 派-8 でファイル配信に認可をかける以上、URL を第三者に渡して閲覧させる機能は、プライベートチャンネルという要求と矛盾する。**その結果、ワークスペース外の相手にファイルを見せたい場合は、ダウンロードして別途送る必要がある** |
| **グループ DM（3人以上）** | 要求は「特定ユーザーへの送信」であり、1対1で満たせる。参加者管理がチャンネルと重複する |
| **チャンネルごとの通知設定** | 通知の粒度を「メンションと DM のみ」に固定することで代替する。設定の組み合わせが増えるわりに、学習上の主題ではない |
| **スレッドの多階層化** | Slack も1階層のみ。再帰構造の取得と表示は本題ではない |
| **オーナー権限の委譲・ワークスペースの削除** | 権限の状態遷移が増える。オーナーは作成者に固定する |
| **多言語対応** | UI は日本語のみ |
| **モバイルアプリ** | Web のみ |
| **削除済みメッセージの物理削除** | 削除は論理削除のみとし、物理削除の仕組みは持たない。**その結果、利用者が「削除した」と認識した内容も、データベース上には残り続ける。** 保持期限を設けた物理削除の基盤は、学習上の主題ではないため設けない |
| **SVG の受け入れ**（画像・添付とも） | **SVG は画像ではなく XML であり、`<script>` を内包できる。** 受け入れると保存型 XSS と XXE の経路になる。サニタイズによる受け入れも可能だが、それは保険的対策であり、**受け付けない構造にすることが根本対策**である（IPA の指針に従う）。要求に SVG は含まれておらず、失うものは「ベクタ画像を原寸で貼れない」ことのみ |
| **外部の解析ツールの導入**（Google Analytics 等） | 導入すると電気通信事業法の**外部送信規律**（第27条の12）に基づく通知・公表義務が生じる（6.3）。**導入しないことを明示的な決定として記録する** |
| **Slack のロゴ・アイコン・固有の配色の使用** | 商標・トレードドレスの論点を避けるため。UI の類似は**機能を実現した結果の類似**に留め、Slack の視覚的アイデンティティは模倣しない（6.4） |

### 3.5 設計上の確定事項

要求からは一意に定まらず、判断を要した論点と、その決定を記録する。

#### 3.5.1 ワークスペースとチャンネルは別の階層である

**ワークスペースへの参加**と**チャンネルへの参加**は、独立した2つの層として扱う。

```
ワークスペース              ← 第1層：組織に所属するか。オーナーの招待が必要
 ├─ パブリックチャンネル     ← 第2層：メンバーは自由に参加・退出できる
 └─ プライベートチャンネル   ← 第2層：招待された人だけ
```

課題文の「ユーザーの招待 / キック」は**第1層**を指す。キック（強制退出）と並んでいることから、
ワークスペース単位の管理であると解釈した。

| 論点 | 決定 |
|---|---|
| ワークスペースの作成 | 誰でも作成できる。**作成者がオーナーとなる**。1人が複数のワークスペースに所属できる |
| ワークスペースへの招待 | **オーナーのみ**。ユーザーID を指定して招待する。**招待された利用者が承諾して初めて参加する**（提-10。当初は即時参加としていたが、承諾なしに所属が発生するのは不適切と判断して変更した） |
| **ワークスペースからの退出** | **メンバーは自分の意思で退出できる**（提-10）。オーナーは退出できない（オーナー権限の委譲を行わないため。3.4） |
| チャンネルの作成・アーカイブ | **オーナーのみ。メンバーは作成もアーカイブもできない**（課題文の権限要件どおり）。**削除ではなくアーカイブとし、オーナーが復元できる**（提-7） |
| パブリックチャンネルへの参加 | メンバーなら**自由に参加・退出できる**。招待は不要 |
| プライベートチャンネルへの招待 | **参加者なら誰でも招待できる**。ただし招待先は同一ワークスペースのメンバーに限る |
| チャンネルからのキック | **オーナーのみ** |
| ワークスペースからのキック | オーナーのみ。**キックされた利用者は、所属していた全チャンネルから自動的に外れる** |
| **オーナーの閲覧範囲** | **オーナーは、参加していないプライベートチャンネルの「参加者一覧」は閲覧できる。ただしメッセージと添付ファイルは閲覧できない** |
| キックされた利用者のメッセージ | **残す**。削除すると会話の文脈が壊れるため |

> **プライベートチャンネルへの招待を参加者に開放しつつ、オーナーの監督権が保たれる理由。**
> オーナーはワークスペースからのキックによって、その利用者を全チャンネルから外せる。
> 第1層の権限が第2層を貫くため、参加者による招待を許しても管理は成立する。
>
> 一方で **オーナーに全プライベートチャンネルの閲覧権を与えることはしない。** それを認めると
> 「プライベート」が名目だけのものになる。オーナーの権限は**人の出入りの管理**であって、
> **会話の閲覧ではない**、という線引きを設計上の原則とする。
>
> **この原則から、「参加者一覧は見えるが、メッセージは見えない」という区分が導かれる。**
> キック権限（人の出入りの管理）を行使するには、**誰がいるかが見えなければならない。**
> 参加者一覧を隠すと、オーナーはキックすべき相手を特定できず、**課題文が求める管理者権限が
> 機能しなくなる。** 逆にメッセージまで見せると、上記の原則が崩れる。両者の境界がここにある。

> **チャンネルの作成・アーカイブをオーナーのみに限定したことの代償。**
> 課題文の権限要件どおりの設計であるが、**オーナーが不在・多忙な場合、新しい話題のチャンネルを
> 誰も作れない。** 実運用では組織の活動が止まりうる硬直した設計である。
> 課題文由来のため変更はしないが、**判断して受け入れた代償として記録する。**
> 実運用に移す場合は、チャンネル作成権限をメンバーにも開放するか、権限を委譲できる設計に
> 変更する必要がある。

#### 3.5.2 その他の確定事項

| 論点 | 決定 |
|---|---|
| プロフィールの「ステータス」 | **Slack 型**（絵文字＋テキスト。例: 🍽️ 昼休み）。加えて**在席状態**（接続の有無から自動判定）をメンバー一覧に表示する |
| メンションの種類 | 個人 / `@here`（在席中の参加者）/ `@channel`（参加者全員） |
| ダイレクトメッセージ | **1対1のみ**。同一ワークスペース内のメンバーに限る |
| **スレッド内の未読** | **利用者が設定で切り替えられる。既定は「チャンネルの未読に含める」** |
| **スレッド未読の設定を切り替えたときの挙動** | **未読が復活する。** 「含めない」→「含める」に切り替えると、過去のスレッド返信のうち未読のものが未読として現れる。切替時に一括で既読扱いにすると、**読んでいないものが読んだことになる**ため採らない |
| スレッド親メッセージの削除 | **「このメッセージは削除されました」を残し、返信は保持する** |
| メッセージの削除方式 | 論理削除 |
| 検索の方式 | **全文索引 ＋ 種別分類（メッセージ / チャンネル / ユーザー / ファイル）＋ 絞り込み演算子（`from:` `in:`）**。1回のリクエストで種別ごとに並行検索し、セクションに分けて返す |
| ブラウザ通知の条件 | **メンションと DM のみ**。全メッセージで通知すると実用に耐えないため |
| ブラウザ通知の到達範囲 | **タブを開いている間のみ**（プッシュ通知は 3.4 で対象外） |
| 通知の永続化 | **残す**。オフライン中に受けたメンションを後から確認できるよう、**通知一覧画面を設ける** |
| 動画のサムネイル | **生成しない**。`<video src="...#t=30">` により 30 秒地点の映像を表示させる。サーバー側での動画処理基盤を持たない |
| **動画一覧の読み込み** | **Intersection Observer による遅延読み込みとし、画面外の `<video>` 要素は生成しない。** `#t=30` の表示にはブラウザが 30 秒地点までシークする必要があるため、画面外の動画まで要素を作ると**スクロールのたびに読み込みが走る** |
| **識別子（ID）の方式** | **UUIDv7**。連番は「そのIDの資源が存在すること」自体を漏らすため用いない。UUIDv7 は**先頭が時刻順**であるため、推測困難でありながら索引の局所性を損なわず、カーソルページネーション（派-4）のカーソルとしてもそのまま使える。**S3 のオブジェクトキーも `{UUID}/{ファイル名}` とする**（DB の ID だけ秘匿してもストレージのキーが推測できれば意味がない） |
| メッセージ入力欄 | **プレーンな `textarea` ＋ メンション補完**。入力は Markdown 記法のテキストで行い、表示時に描画する。リッチテキストエディタは用いない |

> **スレッド内の未読を設定で切り替えられるようにした点について。** 既定を「含める」としたため、
> 「利用者 × チャンネル」に加えて「利用者 × スレッド」の既読位置を管理する必要が生じる。
> 実装量は増えるが、**どちらの挙動が正しいかは利用者によって割れる**ため、設定として提供する。

## 4. 非機能要件

### 4.1 性能

| 項目 | 目標 |
|---|---|
| 想定利用者数 | 200 |
| 想定ワークスペース数 | 20 |
| 想定メッセージ数 | 100,000 |
| 同時 WebSocket 接続数 | 50 |
| メッセージ一覧の取得 | p95 で 300ms 未満 |
| WebSocket の配信遅延 | p95 で 500ms 未満 |
| 検索の応答 | p95 で 1,000ms 未満 |

- **索引は初回のマイグレーションから投入する。** 索引の欠落を性能テストで事後に検出する
  手戻りを避けるため
- **一覧の取得はカーソルページネーションとする。** `OFFSET` は深いページで劣化するため使わない。
  メッセージ一覧は「上に遡る」方向のページングになる点に注意する
- **リアクション数・スレッドの返信件数はカウンタ列として保持し、本体の更新と同一トランザクションで
  増減させる。** 一覧の各メッセージに対して `COUNT` を発行すると N+1 の温床になるため
- **未読件数は都度集計しない。** 「利用者 × チャンネル」の既読位置を保持し、そこからの差分で求める

#### リアルタイム配信の対象イベント

配信するイベントを以下に確定する。**この範囲外の変化は画面に即時反映されない。**

| イベント | 内容 |
|---|---|
| `message:new` | メッセージの新規投稿（チャンネル・スレッド・DM） |
| `message:updated` | メッセージの編集 |
| `message:deleted` | メッセージの削除 |
| `reaction:changed` | リアクションの追加・取り消し |
| `unread:updated` | 未読件数の変化 |
| `typing:start` / `typing:stop` | 入力中インジケータ（提-3） |
| `presence:changed` | 在席状態の変化 |

### 4.2 可用性

学習用途のため SLA を定めない。RDS は Single-AZ、ECS タスクは最小構成とする。
**デモ後は `terraform destroy` する運用を前提とする。**

**ただし WebSocket は複数インスタンス構成を前提に設計する。** 同一チャンネルの利用者が
別々のタスクに接続した場合、タスクのメモリ上の接続だけでは相手にメッセージが届かない。
ElastiCache for Redis を介した配信共有により、この問題を構造的に解消する。
タスク数を1に絞る運用でも動作するが、**設計としては複数インスタンスを前提とする。**

### 4.3 セキュリティ

| 項目 | 方針 |
|---|---|
| パスワード | **Argon2id** でハッシュ化して保存する。平文・可逆暗号では保持しない |
| 認証 | アクセストークン（JWT・短命）＋ リフレッシュトークン（opaque・長命）。詳細は [技術スタック](tech-stack.md) |
| **WebSocket の認証** | **接続確立時にトークンを検証する。** 接続後のイベントについても、送信元が該当チャンネルの参加者であることを都度確認する。接続時に一度認証すれば以後は無条件、という扱いにはしない。**認証情報は Cookie ではなくハンドシェイクの `auth` で渡す**（下記 Origin 検証を参照） |
| **WebSocket の Origin 検証** | **WebSocket は同一オリジンポリシーの対象外であり、CORS でも守られない。** Socket.IO の `cors` オプションが効くのは HTTP long-polling のみである。対策がなければ **Cross-Site WebSocket Hijacking（CSWSH）** が成立するため、**`allowRequest` でハンドシェイク時に `Origin` を許可リストと照合し、一致しないものと Origin ヘッダーを持たないものを拒否する。** 併せて認証を Cookie に依存させないことで、「ブラウザが Cookie を自動送信する」という攻撃の前提自体を崩す（多層防御） |
| **CSRF** | 対象は **Cookie を用いる2つのエンドポイント（トークンのリフレッシュとログアウト）のみ**。他の API は `Authorization` ヘッダーで認証しており、ブラウザが認証情報を自動送信しないため CSRF は成立しない。この2つに対し、**① `SameSite=Strict; HttpOnly; Secure; Path=/api/auth` ② カスタムリクエストヘッダーの必須化（CORS のプリフライトを強制する） ③ `Origin` / `Sec-Fetch-Site` の検証（未送信時は `Referer` にフォールバック）** の3層で対処する |
| 認可 | **「自分のメッセージのみ編集・削除できる」「オーナーのみが招待・キック・チャンネル操作を行える」ことをサーバー側で必ず検証する。** フロントエンドの制御は UX のためであり、権限の根拠にはしない（派-2） |
| プライベートチャンネルの秘匿 | **一覧・検索・ファイル配信・WebSocket 配信のすべてにおいて、非参加者にデータを渡さない**（派-3 / 派-8） |
| 添付ファイルの配信 | **認可を判定した上で、CloudFront の署名付き Cookie を発行する。** 対象パスはチャンネル単位（`workspace/{ws}/channel/{ch}/*`）とし、参加者にのみ、そのチャンネルのパス配下に限って有効な Cookie を渡す。**署名付き URL（ファイル単位）は採らない**（理由は下記） |
| **識別子** | ファイルID・メッセージID を含むすべての主キーを **UUIDv7** とし、連番を用いない（3.5.2） |
| **アップロード**（配信とは別の経路） | **S3 への直接アップロード用の署名付き URL** に Content-Type と最大サイズを焼き込む。加えて**サーバー側でマジックバイトを検証**し、拡張子や申告された Content-Type を信用しない。**許可リストに列挙した形式のみを受け入れる**（下表） |
| ストレージ | S3 バケットはパブリックアクセスを全面的に遮断する |
| **XSS** | **Markdown の描画に HTML 文字列を生成しない方式を採る**（派-9）。サニタイズによる後追いの除去ではなく、**危険な HTML を作らない構造**にする |
| レート制限 | ログイン試行・新規登録・**リカバリーコードの照合**（発信元単位・アカウント単位）、メッセージの投稿、**アップロード用の署名付き URL の発行**に上限を設ける |
| 依存の脆弱性 | **`npm audit` を CI で継続的に実行する**（PR・push に加えて毎週の定期実行）。**npm の依存の版は、動くことを確かめた組み合わせで固定し、自動更新は受け取らない**（理由と代償は [README](../README.md) の「依存の版を上げない方針」）。**GitHub Actions の版更新は継続する**（メジャーが実行環境の移行を含むため）。**代償として、脆弱性を直す更新は自動では PR にならない。** 監査が落ちた時点で、直す版を人が選ぶ |

#### CSRF に専用のトークン機構を持たない理由

OWASP は、ステートレスな構成に対して**署名付き Double-Submit Cookie** を推奨している
（素の Double-Submit は、サブドメインに Cookie を書ける攻撃者に破られるため非推奨）。
本プロジェクトでは**これを採らない。**

理由は、**守る対象がリフレッシュとログアウトの2エンドポイントしかない**ことにある。
トークン機構を持つと、サーバー側にトークンの生成・HMAC 署名・セッション値との結合・検証・
**署名鍵の管理とローテーション**が、クライアント側に取得・保持・添付が必要になる。
**2つのエンドポイントのために、アプリ全体を横断する仕組みと鍵管理を1つ増やすことになる。**

採用した3層は、いずれも**新しい機構を持たず、既にある仕組みの設定で完結する**
（Cookie の属性 / CORS のプリフライト / ヘッダーの検証）。

**代償**：
- **SameSite に対応しない古いブラウザでは1層目が効かない**（残る2層は効く）
- **将来 Cookie を使うエンドポイントが増えた場合、この判断は見直しが必要である。**
  「2つだけだから」が前提であり、前提が変われば結論も変わる

#### 署名付き URL ではなく署名付き Cookie を採る理由

**署名付き URL は、100 MB の動画に対して破綻する。** AWS の仕様上、期限直前に再生を開始しても
接続が続いていればストリーミングは継続されるが、**期限を過ぎたあとにシークや一時停止などの
新しい再生イベントが発生すると、そのリクエストが 403 になる。** 長い動画ほどシークされるため、
**「動画を見ていて、巻き戻したら止まる」**という壊れ方が現実に起こる。

期限切れを検知して URL を再発行する方式は、**403 の検知・URL の再取得・再生位置の復元・
Range リクエストの再試行**をクライアントに実装することになり、重い。

**署名付き Cookie はチャンネルを開いたときに1回発行すれば、そのチャンネルの添付すべてに効く。**
署名付き URL がファイル1件ごとの発行と期限管理を要するのに対し、発行も再発行も1箇所で済む。

**代償は2つある。**

1. **認可の粒度が「ファイル単位」から「パス単位」になる。** そのため **S3 のキー設計を
   `workspace/{ws}/channel/{ch}/{UUID}/{ファイル名}` に固定する**必要がある。
   **この構造を崩すと認可が崩れる。キー設計が認可の一部になっている。**
2. **チャンネルから外れた利用者は、Cookie の期限が切れるまでの間、そのチャンネルの添付を
   取得できてしまう。** 発行済みの Cookie を個別に失効させる手段がないためである。
   **有効期限を 15〜30 分と短く設定することで、影響する時間を限定する**（再発行はサーバー側で
   完結するため、期限を短くしても利用者の体験は損なわれない）。

#### 添付ファイルのサイズ・形式の上限

**許可リスト方式とする。拒否リストは採らない。** 「実行形式を除く」という書き方では、`.exe` を
弾いても `.dll` `.jar` `.ps1` `.scr` `.msi` `.lnk` が残る。**列挙した形式のみを受け入れる。**

| 種別 | 上限 | 許可する形式（これ以外は受け付けない） |
|---|---|---|
| 画像 | 10 MB | jpeg / png / gif / webp（**SVG は含めない。3.4 を参照**） |
| 動画 | 100 MB | mp4 / webm |
| 文書 | 25 MB | pdf / txt / csv / md / docx / xlsx / pptx |
| 圧縮 | 25 MB | zip |

いずれも**サーバー側でマジックバイトを検証**し、拡張子と申告された Content-Type は信用しない。

### 4.4 プライバシー

- ログにパスワード・トークン・セッション情報を出力しない。**マスキングではなく、これらを
  ログ出力の経路に構造的に渡さない設計とする**
- **オーナーであっても、参加していないプライベートチャンネルの「メッセージ」と「添付ファイル」には
  アクセスできない**（3.5.1）。**参加者一覧のみ閲覧できる**。キック権限を行使するために必要であり、
  この2つの境界が「人の出入りの管理」と「会話の閲覧」の分かれ目である

### 4.5 アクセシビリティ

| 項目 | 方針 |
|---|---|
| キーボード操作 | チャンネル切替・メッセージ入力・モーダルをキーボードのみで操作できる。モーダルとメンション補完でフォーカスを閉じ込め、フォーカス位置を可視化する |
| **新着メッセージの通知** | **`aria-live` により、スクリーンリーダーへ新着を伝える。** 画面の変化だけで伝えない |
| 在席状態・リアクション | **色や記号だけで情報を伝えない。** テキストによる代替を併せて提供する |
| コントラスト比 | 文字と背景で 4.5:1 以上 |
| 機械的な検証 | **axe-core を E2E に組み込み、CI で継続的に検証する** |

### 4.6 可観測性

- ログは構造化 JSON を標準出力にのみ出す。ファイルには書かない
- リクエストごとに ID を発行し、そのリクエスト中の全ログに付与する
- **WebSocket の接続数・切断率・配信遅延をメトリクスとして記録する。** リアルタイム配信が
  中核機能である以上、これが見えないと障害の切り分けができない
- 監視項目: リクエスト数 / エラー率 / p95 レイテンシ / WebSocket 接続数 / DB 接続プール使用率 / RDS CPU / 5xx 率

### 4.7 保守性

- **WebSocket のイベント定義（4.1 の7種類）は、フロントエンドとバックエンドで型定義を共有する。**
  2箇所に書くと、イベント名や引数の食い違いが実行時まで露見しない
- REST API の仕様を唯一の正とし、そこから型を生成する
- 生成物は CI で**再生成して差分が出ないこと**を検証する
- **既存資産の更新は CI が緑であることを確認してから完了とする**

### 4.8 開発方式 — テスト駆動開発（TDD）

**本プロジェクトはテスト駆動開発で進める。** 実装より先にテストを書き、
**失敗すること（Red）を確認してから**実装に入り（Green）、その後に整理する（Refactor）。

**この方式を採る理由は、[コードレビュー観点](../REVIEW.md) 6 に挙げた
「そのテストは、実装が壊れたときに落ちるか」という問いに直接答えるためである。**
実装のあとに書いたテストは、**すでに通る状態を確認するだけ**になりやすく、
「通るだけで、壊れても落ちないテスト」が混入していても気づけない。
**先に赤を見ることで、そのテストが実際に何かを検証していることが保証される。**

**特に効果が大きいのは、下記「必ずテストを書く箇所」の8項目である。**
たとえば「検索がプライベートチャンネルを漏らさないこと」を後からテストにすると、
**そもそも漏れていない状態でテストを書くため、テストが機能しているかを確認できない。**
先に書いて赤を見れば、認可を外したときに確実に落ちることが分かる。

#### 必ずテストを書く箇所

1. 検索がプライベートチャンネルを漏らさないこと
2. 添付ファイルの配信が非参加者を拒否すること
3. WebSocket が非参加者にイベントを配信しないこと
4. **WebSocket が許可外の Origin からのハンドシェイクを拒否すること**
5. Markdown が HTML として解釈されないこと（XSS）
6. 自分以外のメッセージを編集・削除できないこと
7. メンバーがオーナー専用の操作を実行できないこと
8. **オーナーが、参加していないプライベートチャンネルのメッセージを取得できないこと**

#### この方式を適用しない範囲

**すべてをテストから書くわけではない。** 以下は先にテストを書く意味が薄いため対象外とする。

- **UI の見た目・レイアウト**（アクセシビリティの機械的検証は axe-core が CI で行う。4.5）
- **Terraform によるインフラ定義**
- **E2E テスト**（画面が存在して初めて書けるため、実装後に追加する）

## 5. 前提と制約

- 対象ブラウザは各モダンブラウザの最新版とする。IE は対象外
- クラウドは **AWS** に統一する
- 使用言語は **TypeScript** と **SQL** とする。フロントエンド・バックエンドとも TypeScript を用い、
  WebSocket のイベント型を共有する
- **ブラウザ通知（Notification API）は HTTPS でのみ動作する**（`localhost` を除く）。
  そのためデプロイ先は HTTPS が必須である
- **ブラウザ通知には利用者の許可が必要であり、拒否された場合は通知を出せない。**
  その場合は画面内の未読バッジで代替する
- 提出物は **GitHub のリポジトリ URL と、デプロイ済みの URL** とする
- 明確な期限は設けない。[機能一覧](features.md) の優先度は期限管理ではなく、
  **実装順序の依存関係**を表す

### 5.1 提出時の公開方針

| 項目 | 決定 |
|---|---|
| 新規登録 | **通常どおり開放する。** Basic 認証・IP 制限による封鎖は行わない |
| 評価用アカウント | **2つ用意し、ID とパスワードを提出時に渡す。** 内訳は **① 一般メンバー ② ワークスペースのオーナー**。権限による挙動の差（招待・キック・チャンネルのアーカイブが「できる／できない」）を、評価者が**アカウントを作り分けることなく確認できる**ようにするため |
| 登録の停止 | **設定フラグで新規登録を停止できる作りにする。** 方針を変える際にコード変更を要しない状態にしておく |

> **この方針の代償を記録する。**
> 登録を開放したまま公開するため、**URL を知った者は誰でも登録して利用できる状態**になる。
> 電気通信事業法の該当性は「閲覧者が何人か」ではなく「**他人の需要に応ずるため反復継続して
> 提供しているか**」で判断される（6.1）ため、**「評価者しか見ないから対象外」という整理は
> 法的な根拠にはならない。**
>
> それでもこの方針を採るのは、**実際の利用が評価者に限られる見込みであり、実務上のリスクが
> 小さいと判断したため**である。**判断して受け入れた代償として記録する。**
> 想定を超えて利用が広がった場合は、上記の設定フラグで新規登録を停止する。

## 6. 法令上の位置づけ

**本章は「確認すべき論点」の整理であり、法的助言ではない。作成者は弁護士ではない。**
実際に公開・運用する場合は、総務省の相談窓口（各総合通信局）または弁護士に確認すること。

### 6.1 電気通信事業法 — 実運用では届出が必要になる

#### 該当しうる理由

**ダイレクトメッセージ（F-19）とチャンネル（F-11）は、サーバーを介して他人と他人の通信を
成立させている。** これは同法にいう「**他人の通信の媒介**」に当たりうる。
「電気通信設備を用いて他人の通信を媒介」し、かつ「**他人の需要に応ずるために提供する事業**」
である場合、届出または登録が必要となる。

**有償・無償は判断基準にならない。** 総務省の見解として、有料・無料を問わず対象になり得るとされる。
**「無料の学習用アプリだから不要」という整理は成り立たない。**

#### 必要になるのは「登録」ではなく「届出」

本アプリは自ら電気通信回線設備を設置せず、AWS の設備を借りて提供する構成である。

| | 登録（第9条） | **届出（第16条）** |
|---|---|---|
| 対象 | 回線設備を**自ら設置する**事業者（光ファイバー等） | **設備を借りる事業者**（ISP・SaaS・メッセージングアプリ等） |
| 費用 | 登録免許税 150,000 円 | **無料** |
| 期間 | 審査 30〜60 日。**登録証の交付まで開業できない** | **受理後ただちに事業を開始できる** |

**本アプリが該当するのは届出（第16条）である。**

#### 提出先と必要書類

| 項目 | 内容 |
|---|---|
| 宛先 | **総務大臣** |
| 実際の提出先 | **主たる事業区域を管轄する地方の総合通信局**（全国に窓口が置かれている）。全国展開の場合は総務省本省 |
| 必要書類 | 届出書、提供する役務の概要、法人の場合は登記事項証明書。**個人事業として届け出る場合の必要書類は、管轄の総合通信局に確認すること** |
| 一次資料 | 総務省「**電気通信事業参入マニュアル［追補版］**」（令和5年1月30日改定）／総務省「電気通信事業参入・変更手続の案内」 |

#### 届出後に生じる義務

1. **通信の秘密の保持**（法第4条）。**違反には罰則がある**
2. **業務改善命令**の対象となる
3. **消費者保護規律**の適用を受ける
4. **外部送信規律**（法第27条の12）。利用者の端末から第三者へ情報を送信させる場合、通知または公表が必要（6.3）

#### 本課題での扱い

**今回は届出を行わない。** 5.1 のとおり、実際の利用者が評価者に限られる見込みであることを
前提とした判断である。**この前提が崩れる場合（一般に公開する、継続的に運用する、
第三者に利用を勧める）には、上記の届出が必要になる。**

### 6.2 個人情報保護法

表示名・アバター画像・メッセージ本文は、個人情報に当たりうる。

- ただし**論理削除のみであり、物理削除は行わない**（3.4）。実運用では、削除の求めに応じるための
  物理削除の仕組みが別途必要になる
