# 要件定義書

## 1. 目的と背景

ワークスペース単位でチャンネルを持つ、Slack 風のチャットアプリケーションを作る。

汎用のメッセージングアプリと異なり、会話を **チャンネル** と **スレッド** の二軸で構造化する。
これにより、1つのチャンネルで複数の話題が同時進行しても発言が混ざらず、
過去の会話を後から検索して掘り起こせる。会話を流れて消えるもの（フロー型）ではなく、
**検索可能な資産（ストック型）** として扱うことが、この種のアプリケーションの中核にある。

スクール課題であり、**学習目的の構成**である。可用性やコストの面で本番運用には適さない
割り切りを複数含む。該当箇所は本書および [技術スタック](tech-stack.md) に明記する。

## 2. 想定利用者

同一の組織・チームに属し、業務上の連絡を行う個人。
アカウントを持つ利用者のみが閲覧・投稿できる（非ログインでの閲覧は提供しない）。

1人の利用者は複数のワークスペースに所属できる。ワークスペースを作成した利用者が
そのワークスペースのオーナーとなり、管理者権限を持つ。

**「認証を要さない経路」と「アプリケーションの内容を返す経路」は別の基準である。**
前者は「トークンなしで呼べるか」、後者は「応答にワークスペース・チャンネル・メッセージ等の
内容を含むか」で判定する。

新規登録・ログイン・リカバリーコードの照合・死活確認（F-39）の4経路は、いずれも
**認証を要さない。** しかし新規登録・ログイン・リカバリーコードの照合はアカウントを
得る／取り戻すための経路であり、応答は成否とトークンに限られる。死活確認（F-39。
ALB のターゲットグループがヘルスチェックのパスを必須とするため。[機能一覧](features.md)
14.1）も、応答は稼働の有無のみである。**この4経路はいずれもアプリケーションの内容を
返さないため、「非ログインでの閲覧」には当たらない。** 上記の方針はこの4経路によって
崩れるものではない。

## 3. スコープ

### 3.0 機能の区分について

本書および [機能一覧](features.md) では、**各機能がどこから来たのかを3つに区分して表記する。**
「顧客が求めた機能」と「実装側の判断で加えた機能」を混同しないためである。

| 区分 | 定義 | 判定基準 |
|---|---|---|
| **要求** | 課題文に明記されている機能 | 課題文に書かれている |
| **派生** | 要求を満たすために技術的に不可避な機能 | **これが無いと、どの要求が成立しないか答えられる** |
| **提案・承認済** | 無くても要求は満たせるが、**提案し、承認を得た上で実装する**機能 | 無くても要求は満たせる |

**「派生」と「提案・承認済」を分ける理由**は、両者の性質がまったく違うためである。
派生機能は要求から論理的に導かれるものであり、実装側が勝手に加えたものではない。
一方、提案・承認済の機能は要求の外にあるため、**提案し承認を得たという事実を記録する**
必要がある。無断で追加すれば要求の逸脱であり、承認を得ずに「承認済」と書けば虚偽になる。

各機能の区分と根拠は [機能一覧](features.md) の一覧表に記載する。

### 3.1 顧客要求に基づく機能

課題文に明記された機能。全19件。

### 3.2 要求の実現に必要となる派生機能

**課題文には書かれていないが、書かれている要求を満たすために技術的に不可避な機能。** 全10件。

各項目に「**これが無いと、どの要求が成立しないか**」を明記する。これが派生機能の正当性の根拠であり、
実装側の判断で機能を膨らませたものではないことの証明になる。

| # | 機能 | これが無いと成立しない要求 |
|---|---|---|
| 派-1 | **リアルタイム配信（WebSocket）** | **テキストチャット**。相手の発言を見るのに毎回リロードが必要なものはチャットとして成立しない。加えて**ブラウザ通知**も、サーバーからの能動的な配信なしには実現できない |
| 派-2 | **サーバー側での認可検証** | **「メンバーはこれらができない状態にすること」**。画面上でボタンを隠すだけでは、API を直接呼ばれれば通ってしまう。権限の根拠はサーバー側の検証にある |
| 派-3 | **検索の認可（参加チャンネルへの限定）** | **プライベートチャンネル**。検索を素直に実装すると、非参加者に対してプライベートチャンネルの本文が検索結果として露出する |
| 派-4 | **メッセージのカーソルページネーション** | **メッセージの表示**。全件を返す実装では、メッセージが数千件に達した時点で応答が破綻する |
| 派-5 | **ワークスペース／チャンネルのメンバー管理** | **招待・キック・管理者権限・プライベートチャンネルのすべて**。「誰がどのワークスペースの、どのチャンネルに所属しているか」という構造が無ければ、これらは判定できない |
| 派-6 | **添付ファイルの保存先とサイズ・形式の検証** | **画像・動画・ファイルの添付**。保存先が無ければ添付は成立せず、上限が無ければ動画1本でストレージが破綻する |
| 派-7 | **パスワードのハッシュ化** | **新規登録・ログイン**。平文または可逆な形での保存は、認証機能として成立していない |
| 派-8 | **添付ファイル配信の認可** | **プライベートチャンネル**。ファイルの URL を直接開かれると、非参加者が中身を取得できてしまう。派-3 と同じ構造の問題であり、画面に出さないだけでは不十分である |
| 派-9 | **Markdown の XSS 対策** | **Markdown 基本対応**。利用者の入力を描画する以上、無対策ではスクリプトを注入される。安全に描画できて初めて要求を満たす |
| 派-10 | **死活確認エンドポイント** | **デプロイそのもの（ECS Fargate + ALB 構成）**。ALB のターゲットグループはヘルスチェックのパスを必須とし、無ければタスクが正常と判定されず、3.1 の要求機能を含むすべての機能が提供されない（#15） |

> **派-3 と 派-8 は同じ性質の問題である。** どちらも「画面に表示しない」だけでは不十分で、
> **データを返す経路そのものに認可が必要**になる。プライベートチャンネルという要求は、
> **一覧・取得 API / 検索 / 添付ファイルの配信 / WebSocket の配信の4経路**すべてを塞いで
> 初めて成立する（[コードレビュー観点](../REVIEW.md) 2.1）。
> **このうち 3.2 の表に挙げているのは 派-3（検索）と 派-8（添付ファイルの配信）の2件である。**
> 残る2経路は、**一覧・取得 API を 派-2、WebSocket の配信を 派-1 の受け入れ条件**
> （[機能一覧](features.md) F-16）で担保する。**4経路のうち1つでも担保先を示せない状態にしない。**

> **オーナー向けの管理用一覧（3.5.1「オーナーの閲覧範囲」。[機能一覧](features.md) 3.1
> の但し書き）も派生機能だが、3.2 の表に行を持たない。** 新しい要求ではなく、既存の派生の
> 適用先であるためである。**認可の判定（オーナーであることの確認）は 派-2、判定に使う
> 構造は 派-5 が担保する。**

### 3.3 提案し、承認を得て実装した機能

**課題文には無く、無くても要求は満たせるが、価値があると判断して提案し、承認を得た上で実装する機能。**
全10件。**提-1 〜 提-6 は 2026-09-03、提-7 〜 提-10 は 2026-09-04 に提案し、いずれも同日承認を得ている。**

提-7 以降は、ドキュメント完成後に実施した総点検（矛盾・ユーザビリティ・セキュリティ・法令）で
**要求どおりに作ると成立しない、あるいは利用者が詰む状態になる**と判明した箇所への対応である。

| # | 機能 | 提案理由 |
|---|---|---|
| 提-1 | **コードスニペット**（バッククォート3つによるシンタックスハイライト） | Markdown 対応の延長線上にあり、追加コストが小さい。業務での利用を想定すると使用頻度が高い |
| 提-2 | **ピン留め** | 重要なメッセージをチャンネルに固定する。過去の発言を探す手間を減らす |
| 提-3 | **入力中インジケータ**（「○○さんが入力中…」） | リアルタイム配信の基盤を流用でき、追加コストが小さい。相手が応答中であることが分かり、待ちの体験が改善する |
| 提-4 | **@here と @channel** | 要求のメンションは個人宛のみだが、それだけでは「チャンネル全員に知らせる」手段が無い。段階を持たせることで、無用な通知を避けながら周知ができる |
| 提-5 | **在席状態の表示**（メンバー一覧に接続中を示す） | 提-4 の `@here` を成立させるために在席の判定自体は必要になる。判定結果を画面に出さない理由が無く、誰に届くかが利用者から見えるようになる |
| 提-6 | **通知一覧画面** | 通知を永続化する方針を採ったため、蓄積した通知を見返す画面が無いと永続化の意味が失われる。オフライン中に受けたメンションを後から辿れる |
| 提-7 | **チャンネルのアーカイブと復元** | オーナーは参加していないプライベートチャンネルのメッセージを閲覧できない（3.5.1）。にもかかわらず削除はできるため、**中身を一切知らないまま他人の会話をまるごと失わせる**操作が成立してしまう。削除ではなくアーカイブとし、復元できるようにする |
| 提-8 | **アカウントの削除（退会）** | 登録した利用者が自分のアカウントを消す手段を持たない状態を避ける。個人情報の削除の求めに応じる手段でもある（6.2） |
| 提-9 | **リカバリーコード** | メール送信を行わないため、パスワードを忘れると復旧手段が一切ない（3.4）。登録時にリカバリーコードを発行して控えさせ、**オフラインの復旧手段を1つだけ**用意する |
| 提-10 | **招待の承諾と、ワークスペースからの退出** | 招待が即時参加で退出手段が無いと、**「勝手に追加されるのに自分では抜けられない」**状態になる。承諾フローと退出の導線を設ける |

> **提-4 について補足する。** `@here` は「在席中の参加者」に通知する機能であり、
> 在席状態の判定を必要とする。リアルタイム配信の接続状況から判定できるため追加コストは小さいが、
> **この判定なしには `@here` と `@channel` が同じ動作になってしまう**点を確認の上で採用している。
>
> **提-4 と 提-5 は依存関係にある。** `@here` の判定に必要な在席状態を、画面にも表示するのが 提-5 である。
> 提-4 を採らない場合、提-5 は単独では価値が薄い。

### 3.4 実装しない機能（意図的な対象外）

| 対象外 | 理由 |
|---|---|
| **ボイスチャンネル・音声/ビデオ通話** | **課題文で明示的に対象外**とされている。加えて WebRTC という別種のリアルタイム技術が必要になり、本題から外れる |
| **メール送信全般** | ユーザーID をメールアドレスにしない方針のため。**結果としてメールによるパスワードリセットは提供しない。** 代替として**リカバリーコード**（提-9）を発行するが、**そのコードを紛失した場合、アカウントは復旧できない。** 学習用途として許容し、登録画面に明示する |
| **モバイルへのプッシュ通知** | **課題文で明示的に対象外**とされている。Service Worker と Web Push の基盤が必要になる。**その結果、ブラウザのタブを閉じている間は通知が届かない** |
| **Bot / Incoming Webhook / スラッシュコマンド** | 外部連携は本題ではなく、Bot 用の認証設計が別途必要になる |
| **既読者一覧（誰が読んだか）** | **Slack にそもそも存在しない機能**であり、「Slack 風」という要求に含まれない。既読の可視化は業務上の圧力になるという設計判断が Slack 側にあり、それを踏襲する |
| **ファイルの外部共有リンク** | 派-8 でファイル配信に認可をかける以上、URL を第三者に渡して閲覧させる機能は、プライベートチャンネルという要求と矛盾する。**その結果、ワークスペース外の相手にファイルを見せたい場合は、ダウンロードして別途送る必要がある** |
| **グループ DM（3人以上）** | 要求は「特定ユーザーへの送信」であり、1対1で満たせる。参加者管理がチャンネルと重複する |
| **チャンネルごとの通知設定** | 通知の粒度を「メンションと DM のみ」に固定することで代替する。設定の組み合わせが増えるわりに、学習上の主題ではない |
| **スレッドの多階層化** | Slack も1階層のみ。再帰構造の取得と表示は本題ではない |
| **オーナー権限の委譲・ワークスペースの削除** | 権限の状態遷移が増える。オーナーは作成者に固定する |
| **多言語対応** | UI は日本語のみ |
| **モバイルアプリ** | Web のみ |
| **削除済みメッセージの物理削除** | 削除は論理削除のみとし、物理削除の仕組みは持たない。**その結果、利用者が「削除した」と認識した内容も、データベース上には残り続ける。** 保持期限を設けた物理削除の基盤は、学習上の主題ではないため設けない |
| **SVG の受け入れ**（画像・添付とも） | **SVG は画像ではなく XML であり、`<script>` を内包できる。** 受け入れると保存型 XSS と XXE の経路になる。サニタイズによる受け入れも可能だが、それは保険的対策であり、**受け付けない構造にすることが根本対策**である（IPA の指針に従う）。要求に SVG は含まれておらず、失うものは「ベクタ画像を原寸で貼れない」ことのみ |
| **外部の解析ツールの導入**（Google Analytics 等） | 導入すると電気通信事業法の**外部送信規律**（第27条の12）に基づく通知・公表義務が生じる（6.3）。**導入しないことを明示的な決定として記録する** |
| **Slack のロゴ・アイコン・固有の配色の使用** | 商標・トレードドレスの論点を避けるため。UI の類似は**機能を実現した結果の類似**に留め、Slack の視覚的アイデンティティは模倣しない（6.4） |

### 3.5 設計上の確定事項

要求からは一意に定まらず、判断を要した論点と、その決定を記録する。

#### 3.5.1 ワークスペースとチャンネルは別の階層である

**ワークスペースへの参加**と**チャンネルへの参加**は、独立した2つの層として扱う。

```
ワークスペース              ← 第1層：組織に所属するか。オーナーの招待が必要
 ├─ パブリックチャンネル     ← 第2層：メンバーは自由に参加・退出できる
 └─ プライベートチャンネル   ← 第2層：招待された人だけ
```

課題文の「ユーザーの招待 / キック」は**第1層**を指す。キック（強制退出）と並んでいることから、
ワークスペース単位の管理であると解釈した。

| 論点 | 決定 |
|---|---|
| ワークスペースの作成 | 誰でも作成できる。**作成者がオーナーとなる**。1人が複数のワークスペースに所属できる |
| ワークスペースへの招待 | **オーナーのみ**。ユーザーID を指定して招待する。**招待された利用者が承諾して初めて参加する**（提-10。当初は即時参加としていたが、承諾なしに所属が発生するのは不適切と判断して変更した） |
| **ワークスペースからの退出** | **メンバーは自分の意思で退出できる**（提-10）。オーナーは退出できない（オーナー権限の委譲を行わないため。3.4） |
| チャンネルの作成・アーカイブ | **オーナーのみ。メンバーは作成もアーカイブもできない**（課題文の権限要件どおり）。**削除ではなくアーカイブとし、オーナーが復元できる**（提-7） |
| パブリックチャンネルへの参加 | メンバーなら**自由に参加・退出できる**。招待は不要 |
| プライベートチャンネルへの招待 | **参加者なら誰でも招待できる**。ただし招待先は同一ワークスペースのメンバーに限る |
| チャンネルからのキック | **オーナーのみ** |
| ワークスペースからのキック | オーナーのみ。**キックされた利用者は、所属していた全チャンネルから自動的に外れる** |
| **オーナーの閲覧範囲** | **オーナーが、参加していないプライベートチャンネルについて取得できるのは `id` / 名前 / 種別 / 参加者数と参加者一覧に限られ、メッセージ・添付ファイル・未読数は取得できない。この例外が及ぶのは「一覧・取得 API」だけであり、他の経路には及ばない** |
| キックされた利用者のメッセージ | **残す**。削除すると会話の文脈が壊れるため |

> **プライベートチャンネルへの招待を参加者に開放しつつ、オーナーの監督権が保たれる理由。**
> オーナーはワークスペースからのキックによって、その利用者を全チャンネルから外せる。
> 第1層の権限が第2層を貫くため、参加者による招待を許しても管理は成立する。
>
> 一方で **オーナーに全プライベートチャンネルの閲覧権を与えることはしない。** それを認めると
> 「プライベート」が名目だけのものになる。オーナーの権限は**人の出入りの管理**であって、
> **会話の閲覧ではない**、という線引きを設計上の原則とする。
>
> **この原則から、「参加者一覧と管理用の一覧は見えるが、メッセージは見えない」という
> 区分が導かれる**（内訳は3.5.1「オーナーの閲覧範囲」のとおり）。
> キック権限（人の出入りの管理）を行使するには、**誰がいるかが見えなければならない。**
> 参加者一覧を隠すと、オーナーはキックすべき相手を特定できず、**課題文が求める管理者権限が
> 機能しなくなる。** 逆にメッセージまで見せると、上記の原則が崩れる。両者の境界がここにある。
>
> **管理用の一覧（`id` / 名前 / 種別 / 参加者数）も同じ境界の内側にある。**
> オーナーはキックだけでなく、参加していないプライベートチャンネルも含めた
> チャンネルの管理（アーカイブ・復元）を行う権限を持つが、一覧にも取得にも出さないと
> **`channelId` を知る手段そのものが無く、権限があっても行使できない**（[機能一覧](features.md)
> 3.1 の但し書き）。**代償として、オーナーには参加していないプライベートチャンネルの
> 存在と名前が見える。** 会話の閲覧ではなく存在の可視性であり、上の原則を破らない。
>
> **管理用の一覧はアーカイブ済みも含める。** 含めないと復元の経路が無くなり、
> F-35（Must）が成立しない。**一般の一覧の絞り込み条件をこの管理用の一覧に写しては
> ならない**（[機能一覧](features.md) 3.1 の但し書き）。

> **チャンネルの作成・アーカイブをオーナーのみに限定したことの代償。**
> 課題文の権限要件どおりの設計であるが、**オーナーが不在・多忙な場合、新しい話題のチャンネルを
> 誰も作れない。** 実運用では組織の活動が止まりうる硬直した設計である。
> 課題文由来のため変更はしないが、**判断して受け入れた代償として記録する。**
> 実運用に移す場合は、チャンネル作成権限をメンバーにも開放するか、権限を委譲できる設計に
> 変更する必要がある。

#### 3.5.2 その他の確定事項

| 論点 | 決定 |
|---|---|
| プロフィールの「ステータス」 | **Slack 型**（絵文字＋テキスト。例: 🍽️ 昼休み）。加えて**在席状態**（接続の有無から自動判定）をメンバー一覧に表示する |
| メンションの種類 | 個人 / `@here`（在席中の参加者）/ `@channel`（参加者全員） |
| ダイレクトメッセージ | **1対1のみ**。同一ワークスペース内のメンバーに限る |
| **スレッド内の未読** | **利用者が設定で切り替えられる。既定は「チャンネルの未読に含める」** |
| **スレッド未読の設定を切り替えたときの挙動** | **未読が復活する。** 「含めない」→「含める」に切り替えると、過去のスレッド返信のうち未読のものが未読として現れる。切替時に一括で既読扱いにすると、**読んでいないものが読んだことになる**ため採らない |
| スレッド親メッセージの削除 | **「このメッセージは削除されました」を残し、返信は保持する** |
| メッセージの削除方式 | 論理削除 |
| 検索の方式 | **全文索引 ＋ 種別分類（メッセージ / チャンネル / ユーザー / ファイル）＋ 絞り込み演算子（`from:` `in:`）**。1回のリクエストで種別ごとに並行検索し、セクションに分けて返す |
| ブラウザ通知の条件 | **メンションと DM のみ**。全メッセージで通知すると実用に耐えないため |
| ブラウザ通知の到達範囲 | **タブを開いている間のみ**（プッシュ通知は 3.4 で対象外） |
| 通知の永続化 | **残す**。オフライン中に受けたメンションを後から確認できるよう、**通知一覧画面を設ける** |
| 動画のサムネイル | **生成しない**。`<video src="...#t=30">` により 30 秒地点の映像を表示させる。サーバー側での動画処理基盤を持たない |
| **動画一覧の読み込み** | **Intersection Observer による遅延読み込みとし、画面外の `<video>` 要素は生成しない。** `#t=30` の表示にはブラウザが 30 秒地点までシークする必要があるため、画面外の動画まで要素を作ると**スクロールのたびに読み込みが走る** |
| **識別子（ID）の方式** | **UUIDv7**。連番は「そのIDの資源が存在すること」自体を漏らすため用いない。UUIDv7 は**先頭が時刻順**であるため、推測困難でありながら索引の局所性を損なわず、カーソルページネーション（派-4）のカーソルとしてもそのまま使える。**S3 のオブジェクトキーにも UUID を含める**（DB の ID だけ秘匿してもストレージのキーが推測できれば意味がない）。**キーの全体構造は 4.3 が定める。この構造は認可の一部であり、ここでは繰り返さない** |
| メッセージ入力欄 | **プレーンな `textarea` ＋ メンション補完**。入力は Markdown 記法のテキストで行い、表示時に描画する。リッチテキストエディタは用いない |

> **スレッド内の未読を設定で切り替えられるようにした点について。** 既定を「含める」としたため、
> 「利用者 × チャンネル」に加えて「利用者 × スレッド」の既読位置を管理する必要が生じる。
> 実装量は増えるが、**どちらの挙動が正しいかは利用者によって割れる**ため、設定として提供する。

### 4.1 性能

| 項目 | 目標 |
|---|---|
| 想定利用者数 | 200 |
| 想定ワークスペース数 | 20 |
| 想定メッセージ数 | 100,000 |
| 同時 WebSocket 接続数 | 50 |
| メッセージ一覧の取得 | p95 で 300ms 未満 |
| WebSocket の配信遅延 | p95 で 500ms 未満 |
| 検索の応答 | p95 で 1,000ms 未満 |

- **リアクション数・スレッドの返信件数はカウンタ列として保持し、本体の更新と同一トランザクションで

- **未読件数は都度集計しない。** 「利用者 × チャンネル」の既読位置を保持し、そこからの差分で求める

学習用途のため SLA を定めない。**構成の決定と代償は下の各項に記す。**
**デモ後は `terraform destroy` する運用を前提とする。**

**ただし WebSocket は複数インスタンス構成を前提に設計する。**
タスク数を1に絞る運用でも動作するが、**設計としては複数インスタンスを前提とする。**

**何が問題で、どう解消するかは [技術スタック](tech-stack.md)「WebSocket と複数インスタンスの問題」が持つ。**
**ここには書かない**——同じ説明を2箇所に書くと、片方だけが直る。

#### フェイルオーバーを行わない（決定。2026-09-07）

**RDS を Multi-AZ にせず、ElastiCache Valkey にレプリカを置かない。**
サイジングは [技術スタック](tech-stack.md) の「リソースのサイジング」に記す。

**代償**（[CLAUDE.md](../CLAUDE.md) 4）

- **RDS が落ちると、サービスが止まる。** 待機系へ自動で切り替わる経路が無い。
  **アプリケーション層は別である**——**ECS は複数タスクで動かすため**、
  **1つのタスクの「プロセスが落ちた」場合は** ALB が残りへ振り分ける
  （**プロセスが生きたまま壊れた場合は振り分けられ続ける**——F-39 は浅い死活確認であり、
  DB や Redis に繋がっていなくても `healthy` と判定される。[機能一覧](features.md) 14.1）。
  この節の「設計としては複数インスタンスを前提とする」と対応する
- **RDS は自動で切り替わらないため、Terraform 経由での復元操作が要る**（この節の「復旧手順」）。**所要時間は決めていない**（同じ節の末尾の RTO の項）
- **Valkey にはバックアップも復旧手順も無い。** **持つのは配信の共有だけであり、蓄積しない**ため、
  **作り直して再接続させる**（**在席は下記のとおり配り直しで復帰する。
  停止中のメッセージは復帰しない**——下記の代償）
- **在席の自動判定は Valkey に保持しない**（2026-09-09 の決定）。
  **各タスクは自分に繋がっている利用者の在席について正であり、読み出しは各タスクの中で完結する。**
  **Valkey が停止している間も、在席を読む経路は失敗しない。**
  **タスク間で在席を伝える仕組み**（経路・周期・失効・クライアントへの配り方）は、
  **F-21 / F-22 の実装者が開く [機能一覧](features.md) 9.2 に書く**（#146。この節の目的の外である）。
  **9.2 には、この項（在席についてこの節が決めたもの）全体への参照を置く**——
  **数えて列挙しない。** 保持先の決定・下記の性質・可用性の側で決めたもの・代償の
  **すべてが 9.2 の設計に効く**（**列挙で閉じると、足した分が届かない**）。
  **実装者が開くのは 9.2 であって、可用性の節ではない。**

  **下記の代償が成立するために、9.2 の設計は次の2つの性質を満たさなければならない**
  （**満たし方は 9.2 が決める。ここでは条件を設計しない**）。
    - **Valkey の停止をまたいでも、他タスクの在席を取りこぼさないこと**——
      **Pub/Sub は購読していない間の publish を再生しない**（**この性質は、以降でも同じものを指す**）。
      配り直しが1回では届かない相手が残ると、下記の配り直しが閉じない
    - **停止中と復旧の途中で、すでに受け取っている他タスクの在席を捨てないこと**——
      **publish の途絶だけを根拠に失効させると、この性質を満たさない**——
      途絶だけでは「Valkey が停止している」と「他タスクが全部落ちた」を区別できないためである
      （**区別できる信号はある**。下記の配り直しも、経路が回復したことを検出して発火する）。
      **停止中だけでなく復旧の途中も含む**——先に再接続したタスクは、
      遅れて再接続するタスクの全件をまだ受け取っていない。
      **捨てると、停止前から在席している人を不在として扱うことになる**——
      依頼側が「**代償ではなく壊れた表示である**」として退けた状態であり、下記の代償も偽になる。
      **この性質は「知っているものを捨てない」であって、「知らないものを知る」ではない**——
      **知る経路が無い分は、下記の代償として引き受ける。**

  **可用性の側で決めるのは、停止したときと復旧したときの2つだけである。**
    - **在席を配る publish が失敗しても、例外を投げず、失敗として記録もしない。**
      **経路によっては、Valkey が停止していると publish が失敗する**——
      **アダプタのブロードキャストは例外を投げず静かに縮退する**が、
      専用のチャンネルへ直接 publish する経路では失敗しうる（経路は 9.2 が決める）。
      ここで例外を投げると、
      **未処理の rejection で全タスクが落ちる**（Valkey の停止は全タスクで同時に起きる）。
      **ALB は健全なターゲットが無くなって 503 を返す**——
      下記の「Valkey の停止は検知しない」「5xx も出ない」が**同時に偽になる**
      （**アラートが鳴るかは 5xx 率の取得元による。下記「アラート」**——
      アプリ側で数える形を選ぶと、全断のときは値が欠損する）
    - **在席を配る経路が回復したら、各タスクは自分の在席を全件配り直し、
      受け取った側はそのタスクの分を丸ごと置き換える。**
      **配り直しは、配り終えたことを確認するまで完了にしない**——
      **失敗は記録しないため、取りこぼしを後から拾う手がかりは残らない。**
      完了にしてしまうと、**再送の契機が二度と来ない。**
      **どの信号で「回復した」を検出し、どうやって「配り終えた」を確認するかは 9.2 が決める**
      （経路によって回復の事象も確認の手段も違う）。
      **配り直しは1回では足りない**（上記の Pub/Sub の性質による）——
      **先に再接続したタスクの全件を、遅れて再接続したタスクは取り逃がす。**
      **差分ではなく全件で置き換えるのは、下記の代償のとおり切断が伝わらないためである。**
      **この取りこぼしを埋めるのは、上記の「取りこぼさないこと」の性質を満たす 9.2 の設計である。**
  **代償は、停止している間、ほかのタスクの在席が更新されないことである**（失効の扱いは #146）——
  **他タスクの分は各タスクのメモリに残るため、消えるのではなく古くなる。**
  **停止中に新しく接続した他タスクの利用者は在席として見えず、
  停止中に切断した他タスクの利用者は在席のまま残る。**
  **2つで復旧の仕方が違う。**
    - **F-22（在席の表示）は、復旧すれば上記の配り直しで解消する。** 表示は現在の状態を映すためである
    - **F-21（`@here` の宛先）は解消しない。** 宛先は送信の時点で決まり、**後から補われない**——
      **上記の2つのずれが、そのまま宛先のずれになる。**
      **通知は永続化するため**（3.5.2）、**不在の利用者の通知一覧に `@here` が積まれたまま残る。**
      **足りない側も余分な側も後から補正されない。**
      **`@channel`（参加者全員）は在席を見ないため影響を受けない**（[機能一覧](features.md) 9.2）
  **手動のステータス（F-04。絵文字＋テキスト）はデータベースにあり、影響を受けない**——
  **いま対応できるかどうかは、その間もそちらで分かる**（[機能一覧](features.md) 1.3）
- **Valkey が停止している間は、タスク間の配信共有が止まる。** メッセージはデータベースに
  残るが、**別のタスクに接続している利用者へ即時に届かない。**
  **停止中に他タスクで投稿されたメッセージは、復旧しても届かない**——
  **上記の Pub/Sub の性質により再生されず**、[機能一覧](features.md) 5.2 の
  切断中の補完は**クライアントの再接続**が条件だが、**クライアントの接続は維持される**
  （切れるのはタスクと Valkey の間である）。**「Valkey の停止は検知しない」ため、
  欠けたことに気づく経路も無い。**
  **代償は、その利用者の画面に停止中の投稿だけが欠けたまま残り、
  自分で読み込み直すまで埋まらないことである**——**在席と違い、埋める経路は持たない。**
  **この代償は [機能一覧](features.md) 5.2 の受け入れ条件から参照させる**（#162）——
  **F-16 の実装者とテストを書く側が開くのは 5.2 であり、可用性の節ではない。**

**採らなかった側の代償。** Multi-AZ とレプリカを採ると、**RDS と Valkey の費用がそれぞれ2倍になる**
（Fargate と ALB は変わらないため、合計は2倍にはならない。額は [技術スタック](tech-stack.md) の「概算コスト」による）。
`terraform destroy` を前提とする運用では、可用性の向上より費用が上回ると判断した。

#### バックアップ

| 対象 | 方式 |
|---|---|
| RDS | 自動バックアップを有効にする（**日次スナップショット＋トランザクションログの退避**。保持期間内の任意の時点へ復元できる）。保持期間と取得時間帯は Terraform に置く |
| S3（添付ファイル） | バージョニングで誤削除に備える。ライフサイクルは置かない |
| ElastiCache Valkey | **対象外**（この節の「代償」） |

**S3 のバージョニングは、`terraform destroy` を止める。** バージョニングを有効にしたバケットは、
オブジェクトを消しても**旧バージョンとデリートマーカーが残る**ため、`force_destroy` を指定しない限り
バケットの削除が失敗する。ライフサイクルを置かないので旧バージョンが自動で消えることもない。
**`force_destroy` を指定するか、destroy の前に手で空にするかを Terraform の実装時に決める。**

**旧バージョンが残り続けることの代償**（RDS の最終スナップショットと同じ形で書く）。

- **費用**——ライフサイクルを置かないため、消したオブジェクトの分も課金され続ける
- **個人情報**（[要件定義書](requirements.md) 6.2）——**削除した添付ファイルは無期限に取り出せる。**
  6.2 は「**削除の求めに応じるための物理削除の仕組みが別途必要になる**」としているが、
  **その仕組みを作っても S3 の旧バージョンは残るため、削除は成立しない。**
  **物理削除の仕組みには、旧バージョンとデリートマーカーの削除を含める必要がある**
  （6.2 側の記述と、6.2 の列挙に添付ファイルを足すかどうかは **#161**）

**`terraform destroy` の前に、RDS の最終スナップショットを取るかどうかを決める。**
取らない場合、デモ後にデータは残らない。**取る場合は、そのスナップショットが
`destroy` の対象外として残り続けることを認識しておく**（費用と、個人情報を含む場合の扱い。
[要件定義書](requirements.md) 6.2）。

#### 復旧手順

**対象は3つあり、範囲はそれぞれ閉じている。**

| 対象 | 復旧の方式 |
|---|---|
| **RDS** | 下記の手順 1〜5 |
| **S3（添付ファイル）** | 下記「**S3 の誤削除からの復元**」 |
| **ElastiCache Valkey** | **手順を持たない**（この節の「代償」） |

**RDS の障害から復旧するとき**、次の順で行う。

1. **復元する時点を決める。** RDS の自動バックアップは日次スナップショットに加えて
   トランザクションログを継続的に退避しており、**保持期間内の任意の時点へ復元できる**
   （point-in-time recovery）。**スナップショットからの復元だけを行うと、
   最後のスナップショット以降のデータを余分に失う**
2. 決めた時点へ復元し、新しいインスタンスを作る
3. 接続先（エンドポイント）を差し替える。**復元と差し替えは Terraform 側で行い、state を
   復元後のインスタンスに一致させる**（下記）
4. ECS のタスクを再起動し、新しい接続先を読ませる
5. **復元後のインスタンスへ直接問い合わせ、復元した時点のデータが入っていることを確かめる。**
   **あわせて、アプリケーションが復元後のインスタンスを読んでいることを確かめる**——
   **これを確かめないと、手順 3 の差し替えが誤っていても、手順 4 のタスクが古い接続先を
   読んでいても「復旧できた」と判断してしまう**（直接問い合わせが確かめるのは復元の成否だけであり、
   **手順 3・4 の成否に依存しない**——手順 2 の直後に実行しても同じ結果を返す）。
   **どの信号で確かめるかは実装時に決める**（4.6 の「DB 接続プール使用率」と RDS 側の接続数を
   併せる形なら、運用者の権限だけで確かめられる）。
   **アプリケーションの API では確かめられない**——認証が要り（非ログインでの閲覧は提供しない）、
   **そのチャンネルの参加者でなければメッセージを取得できない**（4.3。**オーナーの例外もメッセージには及ばない**）。
   復元する時点によっては**運用者のアカウントが復元後の DB に存在せず**、ログインが通らない。
   チャンネル作成より前の時点なら **404** が返り、**非参加者に返す 404 と区別できない。**
   **死活確認（F-39）でも確かめられない**——F-39 は浅い死活確認であり **DB 等への問い合わせを行わない**
   （[機能一覧](features.md) 14.1）。手順 3 の差し替えが誤っていても、手順 4 のタスクが
   古い接続先を読んでいても、**F-39 は 200 を返す**
   **代償**（[CLAUDE.md](../CLAUDE.md) 4）——**この手順は、アプリの認可を経ずに
   すべてのチャンネルのメッセージへ到達する経路を1つ作る。**
   **守るのは AWS 側の権限であって、アプリの認可ではない**——
   4.3 の「非参加者にデータを渡さない」も、3.5.1 の「オーナーの例外もメッセージには及ばない」も、
   **この経路には掛からない。**
   **誰がこの経路を使えるかは、ネットワーク構成と AWS の権限を決めるときに定める**（#160）。
   **S3 側の復元手順も同じ経路であり、3つの手順すべてが認可の外に出る。**
   **手順 1・2（デリートマーカーの削除・旧バージョンのコピー）は添付ファイル本体に到達する**——
   **削除済みの旧バージョンを含む。**
   **手順 3（バージョン一覧）も「メタデータ」では済まない**——
   **キーは `workspace/{ws}/channel/{ch}/{UUID}/{ファイル名}` に固定されており**（4.3。
   **この構造は認可の一部である**）、**一覧を引くとプライベートチャンネルの存在と
   添付ファイル名が渡る。** **識別子に連番を使わない理由と同じである**（3.5.2）。
   4.3 の署名付き Cookie による参加者限定の配信も、3.5.1 の「オーナーの例外も添付ファイルには及ばない」も、
   **この経路には掛からない**（#160）。

**手で作って手で差し替えてはならない。** この節はインフラの設定の正本を Terraform に置くと
繰り返し宣言している（保持期間・取得時間帯・アラートの閾値）。手順 2〜3 を Terraform の外で行うと、
**state は壊れた側のインスタンスを指したまま残り**、差し替えた接続先（ECS のタスク定義の環境変数など、
Terraform が管理する対象）は**次の `apply` で元に戻る**。`terraform destroy` を前提とする運用では、
**復旧して作ったインスタンスが state の外にあるため destroy されずに残る**か、逆に state 側の記述で
作り直されて**復旧結果が失われる**。**手順 5 までは通るため、壊れるのはその後の最初の `apply` / `destroy` である。**

**S3 の誤削除からの復元。** バケットはバージョニングを有効にしているため、
オブジェクトを消しても**旧バージョンとデリートマーカーが残る**（上記「バックアップ」の表）。

1. 対象のキーの**デリートマーカーを削除する**。直近の削除であれば、これだけで元のバージョンが現行に戻る
2. 上書きによる喪失であれば、**戻したい旧バージョンを同じキーへコピーする**（新しい現行バージョンになる）
3. **S3 側で、そのキーの現行バージョンが復元したものになっていることを確かめる**（バージョン一覧を引く）。
   **添付ファイルの配信では確かめられない**——配信は参加者にしか成立せず（4.3）、
   **オーナーの例外も添付ファイルには及ばない**（3.5.1）。
   運用者がそのチャンネルの参加者でなければ、**復元が成功していても 404 / 403 が返り、成否と区別できない**

**ライフサイクルを置いていないため、旧バージョンは自動では消えない**（上記「バックアップ」の表）。
**復元できる期間に上限は無い。** これは `terraform destroy` を止める性質と同じ設定に由来する。

- **RTO（復旧までの目標時間）は定めない。** 学習用途であり、停止が業務に影響しないため
- **RDS の RPO（失ってよいデータの範囲）は、トランザクションログの退避の間隔である。**
  日次スナップショットの間隔ではない。**復元する時点を指定しなければ、実際に取れる復旧地点より
  最大で1日分多く失う。** **S3 の側は別である**（上記「S3 の誤削除からの復元」）
- **上の2つの手順（RDS・S3）は、どちらも机上のものであり、実際に復旧を行った記録はまだ無い。**
  実施したら結果をここに追記する

#### アラート

4.6 の監視項目のうち、次をアラートにする。

| 項目 | 意図 |
|---|---|
| 5xx 率 | 利用者に見える失敗が続いていること |
| RDS CPU | 応答が遅くなる前に気づくこと |

**WebSocket の接続数はアラートにしない。** 利用者がいない時間帯は 0 が正常であり、
**最後の1人が切断するたびに発火する。** この構成は `terraform destroy` を前提とし、
**夜間・休日の対応もしない**（下記）。「届かないアラートは無いのと同じ」の裏で、
**鳴り続けるアラートも同じである。**

**タスクの全断は 5xx 率で捕まえる**——ALB は健全なターゲットが無いとき 503 を返す。
**5xx 率をどこで取るか（ALB のメトリクスか、アプリのログか）は Terraform の実装時に決める。**
アプリ側で数えると、**全断のときメトリクスの発行そのものが止まり、値は 0 ではなく欠損になる**
（接続数のメトリクスを発行するのもアプリ自身である。4.6）。

**Valkey の停止は検知しない。** レプリカを置かない決定の代償である（この節の「代償」）。
Valkey が止まっても、**クライアントの WebSocket 接続は維持され**（切れるのはタスクと Valkey の間の Pub/Sub である）、
メッセージの投稿はデータベースへ書けるので **5xx も出ない**。
**在席を読む経路も 5xx にならない**——上記の代償のとおり、**在席は各タスクが自前で持ち、
読み出しが Valkey に到達しない**ためである。
**上の2項目のどちらも発火しない。** 気づく経路は、利用者からの申告だけである。
**レプリカを置かないと決めた唯一のコンポーネントの故障が、検知もされないまま残る。**

- 閾値は Terraform に置く。**文書に数値を書かない**（変えるたびに2箇所を直すことになる）
- 通知先は1箇所に決める。**決めるまではアラートを作らない**（届かないアラートは無いのと同じ）
- **夜間・休日の対応はしない。** 学習用途としての割り切りであり、
  **これがこの構成を本番運用に使えない理由の1つである**（[要件定義書](requirements.md) 1）

#### CSRF に専用のトークン機構を持たない理由

OWASP は、ステートレスな構成に対して**署名付き Double-Submit Cookie** を推奨している
（素の Double-Submit は、サブドメインに Cookie を書ける攻撃者に破られるため非推奨）。
本プロジェクトでは**これを採らない。**

理由は、**守る対象がリフレッシュとログアウトの2エンドポイントしかない**ことにある。
トークン機構を持つと、サーバー側にトークンの生成・HMAC 署名・セッション値との結合・検証・
**署名鍵の管理とローテーション**が、クライアント側に取得・保持・添付が必要になる。
**2つのエンドポイントのために、アプリ全体を横断する仕組みと鍵管理を1つ増やすことになる。**

採用した3層は、いずれも**新しい機構を持たず、既にある仕組みの設定で完結する**
（Cookie の属性 / CORS のプリフライト / ヘッダーの検証）。

**代償**：
- **SameSite に対応しない古いブラウザでは1層目が効かない**（残る2層は効く）
- **将来 Cookie を使うエンドポイントが増えた場合、この判断は見直しが必要である。**
  「2つだけだから」が前提であり、前提が変われば結論も変わる

#### 署名付き URL ではなく署名付き Cookie を採る理由

**署名付き URL は、100 MB の動画に対して破綻する。** AWS の仕様上、期限直前に再生を開始しても
接続が続いていればストリーミングは継続されるが、**期限を過ぎたあとにシークや一時停止などの
新しい再生イベントが発生すると、そのリクエストが 403 になる。** 長い動画ほどシークされるため、
**「動画を見ていて、巻き戻したら止まる」**という壊れ方が現実に起こる。

期限切れを検知して URL を再発行する方式は、**403 の検知・URL の再取得・再生位置の復元・
Range リクエストの再試行**をクライアントに実装することになり、重い。

**署名付き Cookie はチャンネルを開いたときに1回発行すれば、そのチャンネルの添付すべてに効く。**
署名付き URL がファイル1件ごとの発行と期限管理を要するのに対し、発行も再発行も1箇所で済む。

**代償は2つある。**

1. **認可の粒度が「ファイル単位」から「パス単位」になる。** そのため **S3 のキー設計を
   `workspace/{ws}/channel/{ch}/{UUID}/{ファイル名}` に固定する**必要がある。
   **この構造を崩すと認可が崩れる。キー設計が認可の一部になっている。**
   **配信 URL のパスと S3 のキーは別物である。**

   | 対象 | 値 |
   |---|---|
   | S3 のキー | `workspace/{ws}/channel/{ch}/{UUID}/{ファイル名}` |
   | 配信 URL のパス | `/files/workspace/{ws}/channel/{ch}/{UUID}/{ファイル名}` |
   | 署名付き Cookie の対象 | `/files/workspace/{ws}/channel/{ch}/*`（**配信 URL のパス**） |
   | CloudFront のビヘイビア | `/files/*`（[技術スタック](tech-stack.md)。**署名を要求するのはここだけ**） |

   **配信 URL のパス・署名付き Cookie の対象・CloudFront のビヘイビアの3つが `/files/` で揃い、
   S3 のキーだけがそれを持たない。** この形でないと参加者でも 403 になる——
   Cookie の resource と要求 URL が一致しないためである。
   **そこで resource を `/*` へ広げると、1枚の Cookie で全チャンネルの添付が取れる**
   （[REVIEW.md](../REVIEW.md) 2.1 が名指しで禁じている形）。

   **添付のオリジンへは、`/files/*` のビヘイビアからしか到達できないようにする。**
   **署名を要求するのは `/files/*` だけであり、オリジンへ渡る前に `/files` を剥がす。**
   **したがって剥がしたあとのパスは S3 のキーと同じ形であり、
   既定のビヘイビア（`*`。署名を要求しない）が受け取る URL の形と一致する。**
   **添付が既定のビヘイビアのオリジンにも置かれていると、
   `/files` を外した URL で、署名付き Cookie を一切要求されずに取得できてしまう。**

   **そこで、添付のバケットとフロントの静的配信のバケットを分け、
   既定のビヘイビアは静的配信のバケットだけを指す**（[全体構成](tech-stack.md) が元から2つに分けて描いている）。
   **1つのバケットにまとめ、ビヘイビアを足して塞ぐ形は採らない**——
   「**署名を要求するのは `/files/*` のみ**」という上表の決定を動かすことになる。

   **S3 のキーは上表のとおり固定であり、実装時に決めるものではない。**
   実装時に決めるのは **CloudFront が `/files` をどう剥がすか**だけであり、
   **剥がせるのは viewer-request で URI を書き換える手段だけである**
   （CloudFront Functions / Lambda@Edge）。

   > **オリジンパスでは剥がせない。** [AWS の文書](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/DownloadDistValuesOrigin.html)
   > は「**CloudFront appends the directory path to the value of Origin domain**」と定めており、
   > 例として `example.com/acme/index.html` が `バケット/production/acme/index.html` になると示している。
   > **前に付ける設定であって、取り除く設定ではない。**
   > `/files` を指定すると転送先は `/files/files/workspace/...` になる。
   >
   > **「S3 側にその前置きを持つオブジェクトを置かない」も手段ではない。**
   > それは上表が定めた**前提そのもの**であり、CloudFront は `/files/workspace/...` を
   > そのまま投げて `NoSuchKey` になる。

   **「S3 のキーに `/files` を含めるか」という形の二択にしてはならない**——
   含める側を選ぶと、この表と [機能一覧](features.md) 11.1 の受け入れ条件を同時に破る。
   **剥がせない手段を選んで配信が成立しないとき、復旧の圧力はキー側に `files/` を足す方向にかかる。**
   **手段の列挙を通って、この節が閉じたはずの形に戻ることになる。**

   **確認できたこと。** [AWS の文書](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/edge-function-restrictions-all.html)
   は「**If a function changes the URI for a request, that doesn't change the cache behavior for
   the request or the origin that the request is forwarded to**」と定めている。
   **URI を書き換えても、`/files/*` のビヘイビア選択は元の URI のまま維持される。**

   **確認できていないこと。** **署名付き Cookie の `Resource` の照合が、書き換えの前と後の
   どちらの URI で行われるか。** 署名付き Cookie・エッジ関数の制約・トリガーの各文書を引いたが、
   **照合の順序を定めた記述は見つからなかった**（上の一文はビヘイビアとオリジンにしか及ばない）。
   **実装時に、実際に配信して確かめる。**

   > **踏むと壊れる: 両立しなかった場合に、`Resource` を `/*` へ広げる回避を採ってはならない。**
   > **1枚の Cookie で全チャンネルの添付が取れる**——[REVIEW.md](../REVIEW.md) 2.1 が名指しで禁じている形である。
   >
   > **書き換え後の URI で照合されると分かった場合は、その場で直さず依頼側へ上げる。**
   > **上表の4つの値と、[技術スタック](tech-stack.md) のビヘイビア分割を動かすことになり、設計判断だからである。**
2. **チャンネルから外れた利用者は、Cookie の期限が切れるまでの間、そのチャンネルの添付を
   取得できてしまう。** 発行済みの Cookie を個別に失効させる手段がないためである。
   **有効期限を 15〜30 分と短く設定することで、影響する時間を限定する**（再発行はサーバー側で
   完結するため、期限を短くしても利用者の体験は損なわれない）。

#### 添付ファイルのサイズ・形式の上限

**許可リスト方式とする。拒否リストは採らない。** 「実行形式を除く」という書き方では、`.exe` を
弾いても `.dll` `.jar` `.ps1` `.scr` `.msi` `.lnk` が残る。**列挙した形式のみを受け入れる。**

| 種別 | 上限 | 許可する形式（これ以外は受け付けない） |
|---|---|---|
| 画像 | 10 MB | jpeg / png / gif / webp（**SVG は含めない。3.4 を参照**） |
| 動画 | 100 MB | mp4 / webm |
| 文書 | 25 MB | pdf / txt / csv / md / docx / xlsx / pptx |
| 圧縮 | 25 MB | zip |

いずれも**サーバー側でマジックバイトを検証**し、拡張子と申告された Content-Type は信用しない。

### 4.4 プライバシー

- ログにパスワード・トークン・セッション情報を出力しない。**マスキングではなく、これらを
  ログ出力の経路に構造的に渡さない設計とする**
- **オーナーの閲覧範囲の例外**（3.5.1「オーナーの閲覧範囲」のとおり）**は、キック権限の
  行使と、チャンネルの管理（アーカイブ・復元）を行うために必要であり**、
  3.5.1 が返さないと定めたものへのアクセス可否が「人の出入りの管理」と
  「会話の閲覧」の分かれ目である

  > **代償。** オーナーには、参加していないプライベートチャンネルであっても
  > 存在と名前が見える。参加者から見た「プライベート」は**会話の秘匿であって、
  > 存在の秘匿ではない**（[機能一覧](features.md) 3.1 の但し書き）。

### 4.5 アクセシビリティ

| 項目 | 方針 |
|---|---|
| キーボード操作 | チャンネル切替・メッセージ入力・モーダルをキーボードのみで操作できる。モーダルとメンション補完でフォーカスを閉じ込め、フォーカス位置を可視化する |
| **新着メッセージの通知** | **`aria-live` により、スクリーンリーダーへ新着を伝える。** 画面の変化だけで伝えない |
| 在席状態・リアクション | **色や記号だけで情報を伝えない。** テキストによる代替を併せて提供する |
| コントラスト比 | 文字と背景で 4.5:1 以上 |
| 機械的な検証 | **axe-core を E2E に組み込み、CI で継続的に検証する** |

### 4.6 可観測性

- ログは構造化 JSON を標準出力にのみ出す。ファイルには書かない
- リクエストごとに ID を発行し、そのリクエスト中の全ログに付与する
- **WebSocket の接続数・切断率・配信遅延をメトリクスとして記録する。** リアルタイム配信が
  中核機能である以上、これが見えないと障害の切り分けができない
- 監視項目: リクエスト数 / エラー率 / p95 レイテンシ / WebSocket 接続数 / DB 接続プール使用率 / RDS CPU / 5xx 率

### 4.7 保守性

- **WebSocket のイベント定義（4.1 の7種類）は、フロントエンドとバックエンドで型定義を共有する。**
  2箇所に書くと、イベント名や引数の食い違いが実行時まで露見しない
- REST API の仕様を唯一の正とし、そこから型を生成する
- 生成物は CI で**再生成して差分が出ないこと**を検証する
- **既存資産の更新は CI が緑であることを確認してから完了とする**

### 4.8 開発方式 — テスト駆動開発（TDD）

**本プロジェクトはテスト駆動開発で進める。** 実装より先にテストを書き、
**失敗すること（Red）を確認してから**実装に入り（Green）、その後に整理する（Refactor）。

**この方式を採る理由は、[コードレビュー観点](../REVIEW.md) 6 に挙げた
「そのテストは、実装が壊れたときに落ちるか」という問いに直接答えるためである。**
実装のあとに書いたテストは、**すでに通る状態を確認するだけ**になりやすく、
「通るだけで、壊れても落ちないテスト」が混入していても気づけない。
**先に赤を見ることで、そのテストが実際に何かを検証していることが保証される。**

**特に効果が大きいのは、下記「必ずテストを書く箇所」の8項目である。**
たとえば「検索がプライベートチャンネルを漏らさないこと」を後からテストにすると、
**そもそも漏れていない状態でテストを書くため、テストが機能しているかを確認できない。**
先に書いて赤を見れば、認可を外したときに確実に落ちることが分かる。

#### 必ずテストを書く箇所

1. 検索がプライベートチャンネルを漏らさないこと
2. 添付ファイルの配信が非参加者を拒否すること
3. WebSocket が非参加者にイベントを配信しないこと
4. **WebSocket が許可外の Origin からのハンドシェイクを拒否すること**
5. Markdown が HTML として解釈されないこと（XSS）
6. 自分以外のメッセージを編集・削除できないこと
7. メンバーがオーナー専用の操作を実行できないこと
8. **オーナーが、参加していないプライベートチャンネルのメッセージ・添付ファイル・未読数を取得できないこと**

#### この方式を適用しない範囲

**すべてをテストから書くわけではない。** 以下は先にテストを書く意味が薄いため対象外とする。

- **UI の見た目・レイアウト**（アクセシビリティの機械的検証は axe-core が CI で行う。4.5）
- **Terraform によるインフラ定義**
- **E2E テスト**（画面が存在して初めて書けるため、実装後に追加する）

## 5. 前提と制約

- 対象ブラウザは各モダンブラウザの最新版とする。IE は対象外
- クラウドは **AWS** に統一する
- 使用言語は **TypeScript** と **SQL** とする。フロントエンド・バックエンドとも TypeScript を用い、
  WebSocket のイベント型を共有する
- **ブラウザ通知（Notification API）は HTTPS でのみ動作する**（`localhost` を除く）。
  そのためデプロイ先は HTTPS が必須である
- **ブラウザ通知には利用者の許可が必要であり、拒否された場合は通知を出せない。**
  その場合は画面内の未読バッジで代替する
- 提出物は **GitHub のリポジトリ URL と、デプロイ済みの URL** とする
- 明確な期限は設けない。[機能一覧](features.md) の優先度は期限管理ではなく、
  **実装順序の依存関係**を表す

### 5.1 提出時の公開方針

| 項目 | 決定 |
|---|---|
| 新規登録 | **通常どおり開放する。** Basic 認証・IP 制限による封鎖は行わない |
| 評価用アカウント | **2つ用意し、ID とパスワードを提出時に渡す。** 内訳は **① 一般メンバー ② ワークスペースのオーナー**。権限による挙動の差（招待・キック・チャンネルのアーカイブが「できる／できない」）を、評価者が**アカウントを作り分けることなく確認できる**ようにするため |
| 登録の停止 | **設定フラグで新規登録を停止できる作りにする。** 方針を変える際にコード変更を要しない状態にしておく |

> **この方針の代償を記録する。**
> 登録を開放したまま公開するため、**URL を知った者は誰でも登録して利用できる状態**になる。
> 電気通信事業法の該当性は「閲覧者が何人か」ではなく「**他人の需要に応ずるため反復継続して
> 提供しているか**」で判断される（6.1）ため、**「評価者しか見ないから対象外」という整理は
> 法的な根拠にはならない。**
>
> それでもこの方針を採るのは、**実際の利用が評価者に限られる見込みであり、実務上のリスクが
> 小さいと判断したため**である。**判断して受け入れた代償として記録する。**
> 想定を超えて利用が広がった場合は、上記の設定フラグで新規登録を停止する。

## 6. 法令上の位置づけ

**本章は「確認すべき論点」の整理であり、法的助言ではない。作成者は弁護士ではない。**
実際に公開・運用する場合は、総務省の相談窓口（各総合通信局）または弁護士に確認すること。

### 6.1 電気通信事業法 — 実運用では届出が必要になる

#### 該当しうる理由

**ダイレクトメッセージ（F-19）とチャンネル（F-11）は、サーバーを介して他人と他人の通信を
成立させている。** これは同法にいう「**他人の通信の媒介**」に当たりうる。
「電気通信設備を用いて他人の通信を媒介」し、かつ「**他人の需要に応ずるために提供する事業**」
である場合、届出または登録が必要となる。

**有償・無償は判断基準にならない。** 総務省の見解として、有料・無料を問わず対象になり得るとされる。
**「無料の学習用アプリだから不要」という整理は成り立たない。**

#### 必要になるのは「登録」ではなく「届出」

本アプリは自ら電気通信回線設備を設置せず、AWS の設備を借りて提供する構成である。

| | 登録（第9条） | **届出（第16条）** |
|---|---|---|
| 対象 | 回線設備を**自ら設置する**事業者（光ファイバー等） | **設備を借りる事業者**（ISP・SaaS・メッセージングアプリ等） |
| 費用 | 登録免許税 150,000 円 | **無料** |
| 期間 | 審査 30〜60 日。**登録証の交付まで開業できない** | **受理後ただちに事業を開始できる** |

**本アプリが該当するのは届出（第16条）である。**

#### 提出先と必要書類

| 項目 | 内容 |
|---|---|
| 宛先 | **総務大臣** |
| 実際の提出先 | **主たる事業区域を管轄する地方の総合通信局**（全国に窓口が置かれている）。全国展開の場合は総務省本省 |
| 必要書類 | 届出書、提供する役務の概要、法人の場合は登記事項証明書。**個人事業として届け出る場合の必要書類は、管轄の総合通信局に確認すること** |
| 一次資料 | 総務省「**電気通信事業参入マニュアル［追補版］**」（令和5年1月30日改定）／総務省「電気通信事業参入・変更手続の案内」 |

#### 届出後に生じる義務

1. **通信の秘密の保持**（法第4条）。**違反には罰則がある**
2. **業務改善命令**の対象となる
3. **消費者保護規律**の適用を受ける
4. **外部送信規律**（法第27条の12）。利用者の端末から第三者へ情報を送信させる場合、通知または公表が必要（6.3）

#### 本課題での扱い

**今回は届出を行わない。** 5.1 のとおり、実際の利用者が評価者に限られる見込みであることを
前提とした判断である。**この前提が崩れる場合（一般に公開する、継続的に運用する、
第三者に利用を勧める）には、上記の届出が必要になる。**

### 6.2 個人情報保護法

表示名・アバター画像・メッセージ本文は、個人情報に当たりうる。

- **削除の求めに応じる手段として、アカウントの削除（提-8）を実装する**
- ただし**論理削除のみであり、物理削除は行わない**（3.4）。実運用では、削除の求めに応じるための
  物理削除の仕組みが別途必要になる

### 6.3 外部送信規律（2023年6月施行）

**現在の構成では該当しない。** 外部の解析ツールを導入していないためである。
**導入しないことを 3.4 で明示的な決定として記録している。**
後から Google Analytics 等を導入すると該当するため、その時点で通知・公表の対応が必要になる。
