# 技術スタック

## 選定の前提

### このプロジェクト固有の判断

過去のプロジェクト（`sns-application` / `tabi-log`）では「直前のプロジェクトと同じ技術スタックを
使わない」という制約を課していた。ポートフォリオとしての重複を避けるためである。

**今回はこの制約を外した。** 実装内容が重く（機能38件、うちリアルタイム配信が中核）、
学習領域の新規性よりも**このアプリケーションへの適合度**を優先すべきと判断したためである。

### 長期利用を前提としたバージョン選定

**2026-09-03 時点の LTS / 安定版の状況を実際に確認して確定した。** 最新版であることよりも、
サポート期間と枯れ具合を優先する。確認した内容は本書の「LTS の根拠」に記す。

---

## 選定の判断軸 — このアプリ固有の難所5点

汎用的な良し悪しではなく、**チャットアプリでしか出てこない問題**への適合度で選定した。

| # | 難所 | なぜ難しいか |
|---|---|---|
| **難-1** | **上方向の無限スクロール** | メッセージ一覧は「下が最新」。過去を読み込むと**上に要素が挿入され、スクロール位置が飛ぶ**。一般的な無限スクロールと逆向きで、専用の対応が要る |
| **難-2** | **複数インスタンス間の配信** | 利用者が別々のサーバーインスタンスに接続していると、メモリ上の接続だけでは相手に届かない |
| **難-3** | **7種類の WebSocket イベントの型整合** | 定義がフロントとバックでずれると、実行時まで露見せず静かに壊れる |
| **難-4** | **Markdown の XSS** | 利用者の入力を描画する。無対策ではスクリプト注入 |
| **難-5** | **日本語の全文検索** | 単語の区切りが無く、標準の索引が効かない |

**各難所への対応**

| 難所 | 対応 |
|---|---|
| 難-1 | `react-virtuoso` の `firstItemIndex` |
| 難-2 | `@socket.io/redis-adapter` ＋ ElastiCache for Redis |
| 難-3 | フロント・バックとも TypeScript とし、イベント型を共有する |
| 難-4 | `react-markdown`（HTML 文字列を生成しない構造） |
| 難-5 | PostgreSQL ＋ pg_bigm（2-gram 索引） |

## 全体構成

```
[React SPA]  ── REST/JSON ──┐
   CloudFront + S3          ├─ [NestJS]  ── [PostgreSQL 17 + pg_bigm]
             ── WebSocket ──┘   ECS Fargate    RDS
                                   │
                                   ├─ [Redis]  ElastiCache（配信の共有）
                                   └─ [S3]     添付ファイル
                                                └ CloudFront 経由で配信
                                                  （チャンネル単位の署名付き Cookie）
```

フロントエンドは静的配信とし、NestJS を唯一のサーバーとする3層構造。
REST と WebSocket の両方が ALB を経由する。

### リポジトリの構成

npm workspaces で3つに分ける。**共有パッケージを置くのは難-3 の解決のためである。**

```
packages/shared/   WebSocket のイベント定義。フロント・バック共通
apps/api/          NestJS 11
apps/web/          React 19 + Vite 7
```

#### 共有パッケージを CommonJS で出す理由と代償

`packages/shared` の出力は **CommonJS** とする。
**NestJS 11 が CommonJS だからである**（ESM 化は NestJS 12。本書の選定により 11 に留める）。
ESM で出すと `apps/api` から素直に `import` できない。

> **代償を明記する。** `apps/web` は ESM でバンドルするため、CommonJS の共有パッケージを
> 読むことになる。ワークスペースのリンク先は `node_modules` の外にあり、
> Rollup の CommonJS 変換は既定で `node_modules` しか見ないため、
> **`apps/web/vite.config.ts` で対象に含める指定が要る**。
> 指定を外すと**型チェックとテストは通るのにビルドだけが落ちる**。
> NestJS 12 に上げて全体を ESM に寄せた時点で、この指定は不要になる。

#### Socket.IO を選んだ理由

自前実装で重くなるのは機能そのものではなく、**周辺の面倒事**である。

| 自前だと必要になるもの | Socket.IO |
|---|---|
| チャンネル単位の配信管理 | **Room 機能。チャンネルと1対1で対応する** |
| **複数インスタンス間の配信（難-2）** | **公式 Redis アダプタ** |
| 切断検知と自動再接続 | 組み込み |
| 再接続時の取りこぼし | 組み込みバッファ ＋ 自前の差分取得 |
| 在席判定（F-22 / F-21） | 接続イベントから取得できる |

**「Room ＝ チャンネル」の対応が成立する点が決定的**である。

#### Prisma を選んだ理由と代償

**当初は Drizzle ORM を選定していたが、変更した。**

| 方針 | Drizzle | Prisma | Kysely |
|---|---|---|---|
| **長期利用が前提** | ✕ **v1.0.0 未リリース**（`v1.0.0-beta.2` のまま） | **○ 安定版** | △ 1.0 未到達 |
| SQL が見える形 | ○ | **△ 抽象化される** | ○ |

長期利用を前提とする以上、ベータ版と 0.x は外れる。

> **代償を明記する。** 過去のプロジェクトは一貫して「**SQL が見える形を優先する**」方針を採ってきた
> （MyBatis / sqlc）。Prisma を採用すると、**基本的な CRUD は Prisma が生成するクエリに隠れる**。
> 「SQL を自分で書いて理解する」という学習上の狙いは、その範囲で失われる。
>
> ただし**未読件数の集計・pg_bigm による全文検索・認可を伴う検索**は `$queryRaw` で生 SQL を
> 書くことになる。**このアプリで最も複雑なクエリは、いずれにせよ手で書く**ため、
> 「SQL が見える」部分は残る。
>
> Kysely なら方針は守れるが 1.0 に到達していないため、今回は長期利用を優先した。

### データベース

| 項目 | 採用 | バージョン | 理由 |
|---|---|---|---|
| DB | **PostgreSQL** | **17** | 検索以外のクエリが重いため（下記） |
| 全文検索 | **pg_bigm**（2-gram 索引） | — | **難-5 の解決**。Amazon RDS for PostgreSQL が[拡張機能一覧](https://docs.aws.amazon.com/AmazonRDS/latest/PostgreSQLReleaseNotes/postgresql-extensions.html)に挙げている（PostgreSQL 17 を含む。確認日 2026-09-05）。**実インスタンスでの `CREATE EXTENSION` は未確認**（下記） |
| 主キー | **UUIDv7** | — | 連番は資源の存在を漏らすため用いない。**UUIDv7 は先頭が時刻順であるため、UUIDv4 と違って索引の局所性を損なわない。** カーソルページネーションのカーソルにも使える |

> **UUIDv7 の生成は Prisma 側で行う。** `@default(uuid(7))` は **Prisma v5.18.0 以降**で
> 利用できる。**PostgreSQL 17 には組み込みの `uuidv7()` 関数が無い**（PostgreSQL 18 で追加）ため、
> DB 側の関数には依存しない。この構成であれば PostgreSQL 17 のままで UUIDv7 を使える。

**MySQL ではなく PostgreSQL を選んだ理由。** 検索だけなら MySQL 8.4 の ngram 索引も同等だが、
このアプリは**検索以外のクエリが重い**。

| 必要なクエリ | PostgreSQL の優位点 |
|---|---|
| 未読件数（利用者 × チャンネル × スレッド） | `FILTER` 句で条件付き集計を1クエリに畳める |
| スレッドの返信件数・参加者 | CTE と window 関数が扱いやすい |
| 検索の認可（参加チャンネルへの限定） | CTE で先に絞ってから索引検索に渡せる |

> **OpenSearch を使う案**も検討したが、月 $50 以上のコストと DB との同期処理が必要になり、
> 今回の規模には過剰と判断した。

#### WebSocket と複数インスタンスの問題

```
ALB ─┬─ タスク1 ← 利用者A が接続
     └─ タスク2 ← 利用者B が接続

A が投稿 → タスク1 のメモリ上の接続にしか配信できない → B に届かない
```

ALB のスティッキーセッションでは解決しない。**接続先が違えば配信経路が存在しない**ためである。
ElastiCache for Redis の Pub/Sub を介して全タスクが配信を共有することで、構造的に解消する。

タスク数を1に絞る運用でも動作するが、**設計としては複数インスタンスを前提とする。**

#### ALB のアイドルタイムアウト

ALB のアイドルタイムアウトは既定 60 秒である。Socket.IO は既定で 25 秒ごとに ping を送るため
接続は維持されるが、**この前提に依存している**ことを記録しておく。

#### リソースのサイジング（スケール）

[要件定義書](requirements.md) 4.1 の想定規模（**利用者 200 / ワークスペース 20 /
メッセージ 100,000 / 同時 WebSocket 接続 50**）に対して、以下を確定する。

| リソース | サイズ | 根拠 |
|---|---|---|
| **ECS Fargate** | **0.25 vCPU / 0.5 GB × 2 タスク** | **タスク数を 2 にするのは、複数インスタンス構成が実際に動くことを検証するためである。** 1 タスクでは ElastiCache を介した配信共有（難-2）が机上の設計に留まり、**本番で初めて壊れる**。同時接続 50 は Node.js の 1 プロセスで十分に扱える規模であり、vCPU は最小で足りる |
| **RDS PostgreSQL 17** | **db.t4g.micro（2 vCPU / 1 GB）/ gp3 20 GB / Single-AZ** | メッセージ 100,000 件は本文込みでも数十 MB 規模であり、pg_bigm の索引を含めてもストレージ 20 GB に収まる。**Single-AZ は学習用途としての割り切り**（[要件定義書](requirements.md) 4.2） |
| **ElastiCache for Redis** | **cache.t4g.micro（0.5 GB）× 1 ノード** | 用途は Pub/Sub による配信共有と在席状態の保持のみで、データを蓄積しない。**レプリカは置かない**（停止すると複数タスク間の配信が止まる。これも割り切りである） |
| **ALB** | 1 台 | TLS 終端と WebSocket の維持 |
| **S3** | 上限を設けない（実測で監視） | 添付は画像 10 MB / 動画 100 MB / 文書・圧縮 25 MB を上限とする（[要件定義書](requirements.md) 4.3） |
| **CloudFront** | 1 ディストリビューション / **ビヘイビアを2つに分ける** | フロントの静的配信と添付ファイルの配信を兼ねるが、**署名を要求するのは添付のパス（`/files/*`）のみ**とする。ディストリビューション全体に署名を要求すると、**署名付き Cookie を持たない未ログインの利用者がログイン画面すら開けなくなる** |

**この規模を超えた場合に最初に詰まるのは ECS タスクではなく RDS の接続数である。**
`db.t4g.micro` の最大接続数は限られるため、**接続プールの上限をタスク数 × プール数で管理し、
使用率をメトリクスとして監視する**（[要件定義書](requirements.md) 4.6）。

## LTS の根拠（2026-09-03 時点で確認）

| 技術 | 状態 | 確認内容 |
|---|---|---|
| **Node.js 24** | **Active LTS** | EOL **2028-04-30**。Node.js 22 は既に Maintenance LTS（EOL 2027-04-30）であるため 24 を採用 |
| **Node.js のリリースモデル** | 変更予定 | **2026-10 から年1回のリリースに変わり、バージョン番号が暦年に一致し、全リリースが LTS になる。** Node 26（2026-05 リリース）が旧モデル最後の版で、2026-10 に LTS 入り予定。**現時点で確実なのは 24** |
| **NestJS 11** | 採用 | **最新は 12.0.1 だが、リリースから約1週間。** CommonJS から ESM への全面移行に加え、既定ツールも Vitest / oxlint / Rspack へ刷新されており、変更範囲が広い |
| **NestJS の LTS 制度** | **存在しない** | メジャー版ごとに一定期間パッチが出る運用であり、Java の LTS のような明示的な保証はない。**この事実を認識した上で採用している** |
| **React 19.2** | 現行 | 最新パッチは 19.2.8（2026-07）。React 20 の発表なし。19.0 は 2024-12 リリースで十分に枯れている |
| **Vite 7** | 採用 | Vite 8 は 2026-03 に安定版となったが、内部バンドラを Rolldown / Oxc に刷新している。**プラグイン互換の実績を待つ** |
| **Tailwind CSS 4** | 安定 | 2025-01 リリース。1年半以上経過 |
| **PostgreSQL 17** | 採用 | **Amazon RDS でのサポートは 2030-02 まで**。RDS PostgreSQL 18.4 も利用可能（2031-02 まで）だが、**pg_bigm の対応実績を優先して 17 を選ぶ**。<br>**この理由は後日に見直した。下記「PostgreSQL 17 に留める理由（2026-09-05）」を参照** |
| **Socket.IO 4** | 安定 | 2021 年から 4.x 系が継続 |
| **Prisma** | 安定 | メジャーバージョンで管理されている。Drizzle は v1.0.0 が未リリースのため不採用 |

### PostgreSQL 17 に留める理由（2026-09-05）

**選定は変えていない。直したのは記録した理由のほうである。**
採る版は 2026-09-03 と同じく 17 で、`compose.yaml` も `Dockerfile` も動かしていない。
**この PR が新たに引いた出典が、上の表に書いてあった理由（pg_bigm の対応実績）を
成り立たなくした**ため、その理由を事実に合わせた。

**Redis を #24 に切り出したのとは性質が違う。** #24 は
「ElastiCache の Redis OSS が 7.1 で止まっているので Valkey へ移すか」という
**採る版を変えるかどうかの判断**であり、決めれば構成が変わる。
こちらは**版を変えない判断の、根拠の書き直し**である。
**実際に 18 へ動かすなら、それは #24 と同じ性質の判断**であり、
この PR ではなく別に切り出す。

**上の表が挙げている「pg_bigm の対応実績」は、17 と 18 を分ける理由になっていなかった。**
AWS の[拡張機能一覧](https://docs.aws.amazon.com/AmazonRDS/latest/PostgreSQLReleaseNotes/postgresql-extensions.html)
を確認したところ、**pg_bigm は 18 系にも同じ版が同梱されている**（確認日 2026-09-05）。
選定日（2026-09-03）の記述を、後から引いた出典が否定した形である。**表の側は当時の記述のまま残す。**

**それでも 17 に留める。理由は「採る理由」ではなく「動かさない理由」である。**

- **18 へ動かすには、本書の記述と [Dockerfile](../docker/postgres/Dockerfile) の土台を変え、
  pg_bigm のビルドと `CREATE EXTENSION` を 18 で通し直す作業が要る。**
  17 で通した確認結果（下記）は 18 を裏付けない
- **いま 18 に動かす利益が無い。** RDS のサポート期限は 17 が 2030-02 で、
  このプロジェクトの期間に対して十分に長い

**「ローカルが 17 だから 17 を選ぶ」とは書かない。** ローカルが 17 なのは本書が 17 を選んだ結果であり、
**選定の結果を選定の根拠にすると循環する。** 上に書いたのは、
**動かすための費用が、動かして得るものより大きい**という判断である。

> **代償。** 18 の新機能は使えない。また、2030-02 が近づけば移行は必要になる。
> **そのとき動かす費用は、いま動かす費用と変わらない**（同じ再検証が要る）。
> 先送りしているのは費用ではなく、**費用を払う時期**である。

#### TypeScript 7 を採らない理由

TypeScript 7 は**コンパイラを Go で書き直した実装**であり、5.x とは別系統である。
バージョン番号は連続しているが、**中身の入れ替えを伴う変更**という点で、
Vite 8（内部バンドラを Rolldown / Oxc に刷新）や NestJS 12（CommonJS から ESM への移行）と
同じ性質の判断になる。

**採らない理由は3つ。**

| 理由 | 内容 |
|---|---|
| **周辺ツールの対応が揃っていない** | `typescript-eslint` 8.69.0 のピア依存は `>=4.8.4 <6.1.0` であり、**TypeScript 7 を受け入れない**。lint と型チェックのどちらかを捨てることになる |
| **本書の方針と一致しない** | 「最新版であることよりも、サポート期間と枯れ具合を優先する」（本書冒頭）。5.9 は十分に枯れている |
| **利点が今の規模に釣り合わない** | 7 の主な利点は大規模プロジェクトでの型チェック速度である。現時点の型チェックは数秒で終わる |

> **代償を明記する。** 5.x に留まる間、7 で入る言語機能と速度改善は使えない。
> また、周辺ライブラリが 7 を前提に切り替えた時点で追随が必要になる。
> **`typescript-eslint` が TypeScript 7 を受け入れた時点で、再検討する。**

#### テストの変換に SWC を使う理由

**Vitest は既定でテストを esbuild で変換し、esbuild は `emitDecoratorMetadata` を実装していない。**
NestJS のコンストラクタインジェクションは、この指定が出力する `design:paramtypes` で型を解決する。
そのため、テストの中でだけ **Nest が解決に失敗せず `undefined` を注入する**。
`Nest can't resolve dependencies` は出ず、注入されたものを使う瞬間に別の場所で落ちる。
`tsc` のビルドと `node dist/main.js` は正常に動く（再現して確認。#14）。

**api のテストだけを `unplugin-swc` で変換する。** SWC は `emitDecoratorMetadata` に相当する
出力を持つ。変換の設定は `apps/api/tsconfig.json` から読まれるため、指定は1箇所に留まる。

採らなかった案:

| 案 | 採らない理由 |
|---|---|
| ビルド後の `dist/` に対してテストを実行する | テストのたびにビルドが要り、ソースマップ越しの失敗行が読みにくくなる |
| すべてのコンストラクタ引数に `@Inject()` を明示する | **テストの都合で製品コードの書き方が歪む** |

> **代償を明記する。** 製品のビルドは `tsc`、テストの変換は SWC となり、**変換器が2つになる**。
> 両者の差異に由来する「テストは通るのにビルドで落ちる」を、テストでは捕まえられない。
> 捕まえるのは `ci.yml` のビルドのステップである。**これを理由にビルドの検査を外さない。**
> また、依存が2つ増える（`@swc/core` はプラットフォーム別のネイティブバイナリを持つ）。

### 実装時に検証する項目

- **`CREATE EXTENSION pg_bigm` が RDS PostgreSQL 17 で通ること。** pg_bigm は PostgreSQL の
  バージョンごとにビルドが必要なため、最初のマイグレーションで実際に確認する。
  通らない場合は RDS PostgreSQL 18.4、または MySQL 8.4 の ngram 索引に切り替える
- **文字符号化と照合順序が、3つの環境で揃っていること。**
  **pg_bigm の 2-gram 分割は文字符号化に依存する。**
  下の「ローカルでの確認結果（2026-09-04）」で索引が使われることを確かめたのはローカルであり、
  **符号化が違う環境にその結果は移らない。**
  ローカルの実測値は **`UTF8` / `en_US.utf8`**（`pg_database` を引いて確認した。2026-09-05）。
  これはイメージの `LANG=en_US.utf8` を initdb がそのまま採ったものである。
  **RDS と Testcontainers の既定値は未確認**（実インスタンスを持っていない）。
  **違っていたら、揃えるか、揃えない代償を書く。**
  `compose.yaml` は `POSTGRES_INITDB_ARGS` を渡していない。
  **いま固定しないのは、揃える必要があるかどうかがまだ分からないためである**
  （固定すると、RDS 側に合わせ直すときに2箇所を直すことになる）。
  **代償を2つ明記する。**
  1. **後から足しても、既存のボリュームには効かない。** `POSTGRES_INITDB_ARGS` を読むのは
     initdb であり、**走るのはデータ領域が空のときだけ**である
     （`POSTGRES_USER` などと同じ性質だが、帰結は重い）。揃える必要があると分かった時点で、
     **`down -v` からの初期化やり直しか dump/restore が要る**
  2. **ずれてもヘルスチェックは検知しない。** 利用者名・パスワード・DB 名のずれは
     `psql` の実問い合わせで3つとも赤にするところまで作ってあるが、
     **符号化と照合順序はその対象外である。緑のまま、2-gram 索引の挙動だけが環境ごとに変わる。**
     露見するのは検索を実装したあとであり、**本書が繰り返し避けてきた「最も遅い段階」**にあたる
- **その前提として、`shared_preload_libraries` に `pg_bigm` が入っていること。**
  pg_bigm は共有ライブラリの事前読み込みを必須としている（公式ドキュメント）。
  **ローカルは `compose.yaml` が `postgres -c shared_preload_libraries=pg_bigm` で渡しているが、
  RDS には同じ指定が無い。** RDS では DB パラメータグループに書く必要があり、
  **これは静的パラメータであるため、反映にインスタンスの再起動を伴う**（Terraform を書く段の作業）。
  **上の `CREATE EXTENSION` の検証は、この設定が入っていることを前提とする。**
  設定が無い状態で試して落ちても、それは pg_bigm が使えない証拠にはならない
- **テストの実行環境にも同じ前提が要る。** 本書は「テストは Testcontainers で
  実 PostgreSQL に対して検証する」としているが、**`postgres:17` をそのまま渡すと
  pg_bigm が無い。** Testcontainers に渡すのは
  [開発環境と同じイメージ](../docker/postgres/Dockerfile)（または同等の pg_bigm 入りイメージ）とし、
  `shared_preload_libraries=pg_bigm` も渡す必要がある。
  **環境は「ローカル・RDS」の2つではなく、テストを含めて3つある**
- **ElastiCache で AUTH トークンと転送時暗号化（`rediss://`）を使うかを決め、
  `@socket.io/redis-adapter` がその接続で動くことを確認する。**
  **ローカルの Redis は無認証の `redis://` であり、この経路を一度も通らない**
  （下記「ローカルの Redis に認証を掛けない」）

> **代償を明記する。** **テストの実行環境の項目**は**まだ決めていない**。Testcontainers に
> ビルド済みのイメージをどう渡すか（毎回ビルドするか、名前で参照するか）を
> 決めないまま検索の実装に入ると、**検索のテストだけが動かない**か、
> **2-gram 索引が効いていることを検証しないテスト**になる。
> どちらもこの構成で最も避けたい「遅い段階で露見する」形である。

どの版かを知りたいときは、その SHA-1 を上流で引く。
同じ Dockerfile が「更新は手で `ARG` を上げる」と明記している以上、**書き写すと更新のたびに
片方だけが古くなる経路ができる。** `scripts/check-docs.sh` は版番号を照合しないため、
**ずれても CI は緑のまま本書だけが古い版を主張する。**
件数の表記で同じ失敗が起きた記録が、その検査自身のコメントに残っている。

**土台のイメージはタグで指しており、ダイジェストで固定していない。**
上の 17.11 は「確認した時点の版」であり、タグの指す先が変われば動く。
固定しない理由と代償は [Dockerfile](../docker/postgres/Dockerfile) に記した。

> **RDS では話が変わる。** RDS は利用者が拡張をビルドして持ち込めない。
> 使えるのは AWS が同梱した拡張だけである。
> **同梱されていること自体は確認済みである。** AWS の
> [PostgreSQL の拡張機能一覧](https://docs.aws.amazon.com/AmazonRDS/latest/PostgreSQLReleaseNotes/postgresql-extensions.html)
> は PostgreSQL 17 の各マイナー版に対して pg_bigm を挙げている（確認日 2026-09-05。
> 版番号は上の方針どおり本書に書き写さない。確認した時点では
> [Dockerfile](../docker/postgres/Dockerfile) が固定している版と一致していた）。
>
> **それでも上の「未確認」は消せない。** 残っているのは同梱の有無ではなく、
> **RDS の実インスタンスで `CREATE EXTENSION pg_bigm` を叩いていない**ことと、
> **`shared_preload_libraries` をパラメータグループで設定していない**ことである。
> ローカルで通ったことは、そのどちらも裏付けない。
> **消してよいのは、RDS の実インスタンスで実行したときだけである。**

#### Redis の版（ローカル）

ローカルは `redis:7.2-alpine` とする。**ElastiCache の Redis OSS は 7.1 が上限であり、
7.2 以降は Valkey としてのみ提供される**（2026-09-04 に確認）。本番と同系統に寄せた暫定である。

**版を 7.1 に揃えることはできない。** upstream の Redis に 7.1 は存在せず、
7.0 の次が 7.2 である（Docker Hub のタグを検索し、`7.1` が0件・`7.0` と `7.2` が存在することを確認した）。
ElastiCache の「7.1」は AWS 側の版番号であり、upstream の版番号と1対1に対応しない。

> **代償を2つ明記する。**
>
> 1. **ローカルだけが本番の上限より新しい。** `redis:7.2` は ElastiCache の Redis OSS 7.1 より後の版であり、
>    **7.2 で入った機能や挙動に依存すると、手元では通って ElastiCache で落ちる。**
>    露見するのは Terraform で環境を作ったあと、つまり最も遅い段階である。
>    本書がローカルと本番の差を潰してきた方針と、ここだけ逆向きになっている。
>    **緩和は「使う機能を絞る」ことしかない。** 用途は Socket.IO の Redis アダプタ
>    （Pub/Sub）と在席状態の保持だけであり、いずれも 7.0 の範囲に収まる。
>    **7.2 固有の機能を使いたくなったら、その時点で ElastiCache 側の版を確認する。**
> 2. Redis OSS 7.x は AWS 側で新機能の開発対象から外れている。
>    Valkey へ移すかどうかは決めていない。**決めるまで、本書の「ElastiCache for Redis」は
>    上限 7.1 の意味で読む必要がある。**

#### ローカルの Redis に認証を掛けない

`compose.yaml` の redis は `requirepass` を設けず、`redis://` で繋ぐ。
**127.0.0.1 にだけ束縛しており、ローカルでは守るものが無い**ためである。

> **代償を明記する。** 本番の ElastiCache は **AUTH トークン**と**転送時暗号化**（`rediss://`）を持つ。
> ローカルが無認証の `redis://` だと、**アプリの Redis クライアント設定に認証と TLS の経路が
> 一度も現れない。** PostgreSQL 側はパスワードのずれをヘルスチェックが検知するところまで
> 作ってあるが、**Redis にはそれに対応するものが無く、作りようもない**（掛ける認証が無いため）。
> 露見するのは Terraform で環境を作ったあと、**版差と同じく最も遅い段階**である。
>
> **ローカルにも `requirepass` を掛ける案は採らなかった。** 掛けても TLS は再現できず、
> 「本番に近づけた」という誤った安心だけが残る。**近くない、と書くほうを選ぶ。**

#### ローカルの Redis に永続化を持たせない

`compose.yaml` の redis は `--save '' --appendonly no` で RDB・AOF の両方を切り、
`/data` に `tmpfs` を当てる。用途は Pub/Sub による配信共有と在席状態の保持だけで、
**データを蓄積しない**ためである。

**`tmpfs` は書き込みを切ったうえでさらに要る。** 匿名ボリュームを作るのは redis の設定ではなく
**イメージの `VOLUME /data` 宣言**であり、その位置にマウントが無いと
**コンテナを作るたびに Docker が匿名ボリュームを作る**。
`docker compose down`（`-v` 無し）は匿名ボリュームを消さないため、
`down` → `up` を繰り返すだけで積み上がる（実際に増えることを確認した）。

> **代償を明記する。** **再起動で在席状態が消える。** 上の「ElastiCache for Redis」の行は
> 用途を「Pub/Sub による配信共有と**在席状態の保持**」と書いているが、
> **ローカルではその保持が再起動をまたがない。** 在席は接続から作り直せる情報であり、
> 再接続で復元されるため許容する。**メッセージのように作り直せない情報を Redis に置いたら、
> この判断は成り立たなくなる。** 置く先は PostgreSQL である。

#### ローカルの PostgreSQL の `/dev/shm` を広げない

`compose.yaml` は db に `shm_size` を指定していない。**`/dev/shm` は Docker 既定の 64MB のままである**
（`df -h /dev/shm` で確認した）。

PostgreSQL の動的共有メモリはここを使う（`dynamic_shared_memory_type = posix`）。
**並列プランのワーカー間通信に要るものであり**、`max_parallel_workers_per_gather` の既定は 2 である
（どちらも実際に問い合わせて確認した）。**pg_bigm を使う全文検索は、並列プランが効く経路である。**

**踏むまで `shm_size` を足さない。** 開発規模では 64MB で足りると判断した。
**足りないという証拠がまだ無いものに対して設定を足すと、なぜ足したかが残らない。**

> **代償を明記する。** 足りなくなると
> **`could not resize shared memory segment ...: No space left on device`** で問い合わせが落ちる。
> **64MB という上限は、コンテナ側の既定であって PostgreSQL の性質ではない。**
> RDS も Linux 上の PostgreSQL であり `/dev/shm` は存在するが、
> **上限がインスタンスのメモリ側で決まるため、Docker 既定の 64MB より広い。**
> **実際の上限値と算出規則は未確認である**（RDS の実インスタンスで確かめていない。
> 本書の他の RDS 記述と同じく、確かめたときに書き足す）。
> それでも向きは変わらない。**本番では通る検索が、ローカルだけで落ちる**側である。
> 本書がローカルと本番の差を潰してきた方針に対して、**ここは差を1つ残す側の判断**になっている。
> 露見するのは検索を実装したあと、**並列プランが選ばれるだけのデータ量が入ってから**であり、
> 版差や無認証と同じく遅い段階である。**踏んだら `shm_size` を足す**（そのときは証拠が手元にある）。

## 検討したが採らなかった案

### Elixir + Phoenix — 技術的にはこれが最適解

**このアプリに対して技術的に最も適合するのは Phoenix である。**

| Phoenix が持っているもの | 意味 |
|---|---|
| Phoenix Channels | チャットのために設計された WebSocket 抽象 |
| **Phoenix PubSub** | **Redis 不要**で複数ノード間の配信が成立する（Erlang 分散が担う） |
| **Phoenix Presence** | **在席管理が標準機能**。分散環境で自動的に整合する |

**難-2 と在席管理が、追加インフラゼロで解決する。** ElastiCache も不要になる。

**それでも採らなかった理由は1点。** 関数型言語と OTP（アクターモデル）という
二重に新しいパラダイムを同時に学ぶことになり、**動かなくなったときの原因究明が
経験の無い領域では極端に難しくなる**。技術的な最適解と、完遂できる選択は別物である。

### Java + Spring Boot + STOMP

既知の技術で確実に進められるが、2点で劣る。

- STOMP というプロトコル層が挟まるぶん、Socket.IO より記述量が増える
- **フロントと型を共有できない**（難-3）。7種類のイベント定義を2回書くことになる

### Go + gorilla/websocket

性能は最良だが、**Room 管理・再接続・複数インスタンス配信をすべて自前実装**することになる。
実装量が最も多くなる。
